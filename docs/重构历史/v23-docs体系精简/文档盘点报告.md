## 主要审计发现

### P1: 主文档数量过多，削弱 SSOT

- Type: redundant content
- Location: `docs/` 主文档体系
- Evidence:
  - `docs/README.md` 已声明同一主题只能有一个 SSOT。
  - 但 PostgreSQL 事实源、Markdown 派生备份、Action success 不等于业务成功、Telegram/飞书通道一致性等事实在多个目录重复。
- Impact: 一次事实变更需要同步多个短文档，容易产生漂移。
- Repair: merge
- Recommendation: 按主题保留一个主文档，其它文档只作为章节或表格存在。

### P2: 归档目录正确，但主文档仍保留历史命名债解释过多

- Type: stale signal
- Location: `总览/系统导览.md`、`数据模型/ingest层.md`、`消息链路/双通道一致性.md`
- Evidence: 多处解释 `telegram_*` 是历史命名、飞书通过 `source_channel` 区分。
- Impact: 该事实重要，但多处重复会增加维护面。
- Repair: merge
- Recommendation: 仅在数据模型和消息链路主文档保留一次，其它文档链接。

### P2: 运维、部署、故障排查边界不清

- Type: misplaced content
- Location: `部署运维/`、`运维手册/`、`故障排查/`
- Evidence: GitHub Actions、Cloudflare Worker、AI、DB、Markdown backup 的配置、判断口径和排障分别出现在 2 到 4 个文件。
- Impact: 运维人员排障时需要在多个目录来回跳转。
- Repair: merge
- Recommendation: 部署文档只写“如何配置/部署”，运维手册写“日常操作/恢复”，故障排查写“症状到处理”。
