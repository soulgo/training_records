# 训练记录生成与解析

本文说明训练记录 Markdown、Telegram 图片识别、PostgreSQL 和 Hexo 页面之间的真实生成与解析逻辑。

## 1. 核心结构

系统统一使用 `TrainingSnapshot` 表达训练数据。它由 `tools/training-domain.mjs` 生成，主要字段包括：

- `generatedAt`：快照生成时间。
- `latest.measurement`：最新体脂秤记录。
- `latest.daily`：最新训练日。
- `daily[]`：按日期升序排列的每日记录。
- `daily[].sleep` / `daily[].sleepSummary`：睡眠明细和日级睡眠汇总。
- `charts`：体重、体脂、骨骼肌、基础代谢、饮食热量、训练热量和骑行距离图表序列。
- `bodyFeedback`：身体反馈随想，来自 `source/_posts` 或 `core.thought`。

## 2. Markdown 格式要求

`训练记录.md` 的解析入口是 `tools/training-parser.mjs`。

解析器依赖以下结构：

```markdown
### YYYY-MM-DD

#### 当日体脂秤截图记录

#### 当日运动截图记录

##### 当日活动总览

##### 活动明细

#### YYYY-MM-DD 饮食截图记录

##### 餐次汇总

##### 餐次明细

#### 当日睡眠截图记录
```

解析规则：

- 日期区块只识别 `### YYYY-MM-DD`。
- 每天内部只解析四级标题 `####`。
- 标题中包含“体脂秤”会按体脂秤记录解析。
- 标题中包含“运动截图记录”会按运动记录解析。
- 标题中包含“饮食截图记录”会按饮食记录解析。
- 标题中包含“睡眠截图记录”会按睡眠记录解析。
- 体脂秤记录必须包含 `- 测量时间：...`，否则该体脂块会被忽略。
- 活动明细只识别形如 `- HH:mm 类型：详情` 的行。
- 饮食餐次识别早餐、午餐、晚餐、加餐、建议范围和 `##### 餐次明细`。
- 睡眠记录识别总睡眠、夜间睡眠、午睡、深睡、浅睡、REM、清醒、睡眠评分、平均心率、HRV、血氧、呼吸率、阶段明细、解读和建议等字段。

不要随意修改这些标题层级、中文字段名或日期格式。

## 3. Telegram 图片归档逻辑

Telegram 图片批次由 `tools/telegram-sync.mjs` 调度，`tools/telegram-sync-lib.mjs` 归一，`src/ai/recognition-service.mjs` 调用 AI 识别。

图片批次处理顺序：

1. `groupTelegramUpdates` 按命令、单图和相册分组。
2. 图片消息调用 AI 识别，生成体脂、运动、饮食或睡眠结构化结果。
3. `analyzeTelegramBatch` 按图片内日期和文件名日期确定 `archivedDate`。
4. 睡眠图片使用醒来日期减一天作为归档日；无法确认醒来日期或截图日期时跳过。
5. 普通图片同一批次出现多个图片内日期时跳过。
6. 普通图片没有图片内日期时尝试 Telegram 原始文件名日期。
7. 没有可靠日期时跳过。
8. `status=ready` 的图片批次写 PostgreSQL；正常 `ready + stored` 成功路径不会写入或覆盖 `训练记录.md`。
9. Markdown 由独立备份 workflow 从数据库导出。
10. PostgreSQL 写入失败时追加 pending 队列，等待后续重放。
11. 页面生成优先读取数据库；严格数据库模式下，数据库快照不可用或不完整会阻止发布旧 Markdown 页面。

详细日期规则见 [Telegram 图片日期归档](Telegram图片日期归档.md)。

## 4. PostgreSQL 写入逻辑

数据库写入入口是 `tools/training-db-write.mjs`，facade 是 `tools/training-db-core.mjs`。

当前数据库分三层：

- `ingest.*`：Telegram 批次、消息和 AI 原始识别结果。
- `core.*`：页面和分析使用的主结构化数据层；其中 `core.sleep` 保存睡眠明细，和 `core.training_day` 的睡眠汇总字段一起使用。
- `archive.*`：构建快照归档和运行留痕；其中 `archive.training_day` 现在包含睡眠汇总字段，`archive.training_sleep` 保存睡眠明细。

写入要点：

- `persistNormalizedBatch` 用批次 JSON 的 SHA-256 作为 `payload_hash`。
- 相同 `batch_id` 且 hash 未变时返回 `unchanged`。
- 每个批次写入在事务中完成，失败会 rollback。
- 图片批次会先写入 `ingest.telegram_batch`、`ingest.telegram_message` 和 `ingest.telegram_recognition`；只有审计层和业务层都成功才提交事务。
- Telegram 普通图片成功路径只 upsert 本批次包含的 `core.measurement`、`core.activity`、`core.meal`、`core.sleep`，不会删除同日其它模块的数据。
- 图片批次写完子表后刷新当前 `archivedDate` 的 `core.training_day` 汇总；饮食 `nutrition.details` 只在本批次包含明细时更新，否则保留既有值。
- Telegram 睡眠图片正常路径只写 `core.sleep` 和 `core.training_day` 汇总；`archive.training_sleep` 保留给历史归档和回填维护。
- 随想批次写入或更新 `core.thought`。
- 显式 Markdown 导入和手工对账保留整日替换语义，会按日期替换 `core.*` 对应日数据；默认 `sync:db` 不执行 Markdown 对账。

## 5. 页面数据生成

`npm run build:data` 执行 `tools/generate-training-data.mjs`。

生成流程：

1. 读取 `TRAINING_SNAPSHOT_SOURCE`，线上推荐 `database`。
2. 调用 `buildTrainingSnapshot`。
3. 写出 `source/_data/training.json`。
4. 调用 `buildDashboardViewModel` 写出 `source/_data/dashboardView.json`。
5. 写出 `训练数据解析.md`。
6. 尝试写入 `archive.*`；失败时追加 `runtime/training-db-sync.ndjson`，不阻断构建。

`训练数据解析.md` 是排查输出，下一次 `build:data` 会覆盖。

## 6. Markdown 与数据库互导

| 命令 | 行为 |
| --- | --- |
| `npm run import:markdown` | 显式人工维护：解析当前 `训练记录.md`，写入 PostgreSQL `core.*` |
| `npm run sync:db` | CI/部署推荐入口：执行 archive 回填、ingest 睡眠修复和随想同步，不做 Markdown 对账 |
| `npm run reconcile:markdown` | 显式人工维护：把提交的 Markdown 回写到 `core.*` |
| `npm run export:markdown` | 从数据库快照导出 `训练记录.md`，包含睡眠段落和餐次明细 |
| `npm run backfill:core` | 从最新 `archive.*` 快照补齐缺失的 `core.*` 日期，包括 archive-only 睡眠记录回填到 `core.sleep` |
| `npm run backfill:thoughts` | 把历史 Telegram 随想 Markdown 镜像到 `core.thought` |

## 7. 维护建议

- 手工补录优先写数据库或通过 Telegram 入库；只有确认 Markdown 是完整可信快照时才运行 `import:markdown`。
- 导出 Markdown 前先确认数据库快照可读，导出失败时不使用旧 Markdown 兜底。
- 修改 Markdown 格式后至少运行 `node --test test/training-parser.test.mjs test/training-snapshot.test.mjs`。
- 修改 Telegram 图片识别、睡眠归档或数据库结构后至少运行 `node --test test/telegram-sync.test.mjs test/telegram-sync-runner.test.mjs`。
