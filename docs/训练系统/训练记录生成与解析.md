# 训练记录生成与解析

本文说明训练记录 Markdown、Telegram 图片识别、PostgreSQL 和 Hexo 页面之间的真实生成与解析逻辑。

## 1. 核心结构

系统统一使用 `TrainingSnapshot` 表达训练数据。它由 `tools/training-domain.mjs` 生成，主要字段包括：

- `generatedAt`：快照生成时间。
- `latest.measurement`：最新体脂秤记录。
- `latest.daily`：最新训练日。
- `daily[]`：按日期升序排列的每日记录。
- `charts`：体重、体脂、骨骼肌、基础代谢、饮食热量、训练热量和骑行距离图表序列。
- `bodyFeedback`：身体反馈随想，来自 `source/_posts` 或 `core.thought`。

## 2. Markdown 格式要求

`训练记录.md` 的解析入口是 `tools/training-parser.mjs`。

解析器依赖以下结构：

```markdown
### YYYY-MM-DD

#### 当日体脂秤截图记录

#### 当日运动截图记录

##### 当日活动总览

##### 活动明细

#### YYYY-MM-DD 饮食截图记录

##### 餐次汇总

##### 餐次明细
```

解析规则：

- 日期区块只识别 `### YYYY-MM-DD`。
- 每天内部只解析四级标题 `####`。
- 标题中包含“体脂秤”会按体脂秤记录解析。
- 标题中包含“运动截图记录”会按运动记录解析。
- 标题中包含“饮食截图记录”会按饮食记录解析。
- 体脂秤记录必须包含 `- 测量时间：...`，否则该体脂块会被忽略。
- 活动明细只识别形如 `- HH:mm 类型：详情` 的行。
- 饮食餐次只识别早餐、午餐、晚餐、加餐及其建议范围。

不要随意修改这些标题层级、中文字段名或日期格式。

## 3. Telegram 图片归档逻辑

Telegram 图片批次由 `tools/telegram-sync.mjs` 调度，`tools/telegram-sync-lib.mjs` 归一，`src/ai/recognition-service.mjs` 调用 AI 识别。

图片批次处理顺序：

1. `groupTelegramUpdates` 按命令、单图和相册分组。
2. 图片消息调用 AI 识别，生成体脂、运动或饮食结构化结果。
3. `analyzeTelegramBatch` 按图片内日期和文件名日期确定 `archivedDate`。
4. 同一批次出现多个图片内日期时跳过。
5. 没有图片内日期时尝试 Telegram 原始文件名日期。
6. 没有可靠日期时跳过。
7. `status=ready` 的图片批次优先写 PostgreSQL。
8. PostgreSQL 写入失败时，回退写 `训练记录.md` 并追加 pending 队列。
9. 页面生成优先读取数据库；如果数据库快照不可用或不完整，会自动回退到 `训练记录.md`，避免页面只剩“已写入 Markdown、等待数据库重放”而无法展示数据。

详细日期规则见 [Telegram 图片日期归档](Telegram图片日期归档.md)。

## 4. PostgreSQL 写入逻辑

数据库写入入口是 `tools/training-db-write.mjs`，facade 是 `tools/training-db-core.mjs`。

当前数据库分三层：

- `ingest.*`：Telegram 批次、消息和 AI 原始识别结果。
- `core.*`：页面和分析使用的主结构化数据层；其中 `core.sleep` 保存睡眠明细，和 `core.training_day` 的睡眠汇总字段一起使用。
- `archive.*`：构建快照归档和运行留痕；其中 `archive.training_day` 现在包含睡眠汇总字段，`archive.training_sleep` 保存睡眠明细。

写入要点：

- `persistNormalizedBatch` 用批次 JSON 的 SHA-256 作为 `payload_hash`。
- 相同 `batch_id` 且 hash 未变时返回 `unchanged`。
- 每个批次写入在事务中完成，失败会 rollback。
- 图片批次写入 `ingest.*` 后合并到对应日期的 `core.training_day`、`core.sleep`、`core.measurement`、`core.activity`、`core.meal`。
- 随想批次写入或更新 `core.thought`。
- Markdown 导入数据库会按日期替换 `core.*` 对应日数据。

## 5. 页面数据生成

`npm run build:data` 执行 `tools/generate-training-data.mjs`。

生成流程：

1. 读取 `TRAINING_SNAPSHOT_SOURCE`，默认 `markdown`。
2. 调用 `buildTrainingSnapshot`。
3. 写出 `source/_data/training.json`。
4. 调用 `buildDashboardViewModel` 写出 `source/_data/dashboardView.json`。
5. 写出 `训练数据解析.md`。
6. 尝试写入 `archive.*`；失败时追加 `runtime/training-db-sync.ndjson`，不阻断构建。

`训练数据解析.md` 是排查输出，下一次 `build:data` 会覆盖。

## 6. Markdown 与数据库互导

| 命令 | 行为 |
| --- | --- |
| `npm run import:markdown` | 解析当前 `训练记录.md`，写入 PostgreSQL `core.*` |
| `npm run sync:db` | CI/部署推荐入口：顺序执行 archive 回填、Markdown 对账和随想回填，单段失败时降级返回 |
| `npm run reconcile:markdown` | CI 中把提交的 Markdown 回写到 `core.*` |
| `npm run export:markdown` | 从快照导出 `训练记录.md`；存在 pending 队列时优先保留 Markdown 源 |
| `npm run backfill:core` | 从最新 `archive.*` 快照补齐缺失的 `core.*` 日期 |
| `npm run backfill:thoughts` | 把历史 Telegram 随想 Markdown 镜像到 `core.thought` |

## 7. 维护建议

- 手工补录优先改 `训练记录.md`，再运行 `npm run build:data` 检查解析结果。
- 数据库为主时，导出 Markdown 前先确认 pending 队列为空。
- 修改 Markdown 格式后至少运行 `node --test test/training-parser.test.mjs test/training-snapshot.test.mjs`。
- 修改 Telegram 图片识别、睡眠归档或数据库结构后至少运行 `node --test test/telegram-sync.test.mjs test/telegram-sync-runner.test.mjs`。
