# 多模块随想维护说明

这份文档说明当前随想系统的页面、消息通道同步、Markdown 兼容层和 PostgreSQL 镜像口径。当前有三个随想模块：

- 锻炼随想：路径 `/thoughts/`，模块键 `workout`
- 杂七杂八：路径 `/misc/`，模块键 `misc`
- 身体反馈：路径 `/body-feedback/`，模块键 `body_feedback`

三个模块共用同一套消息通道写入、带图、pending queue 和 DB 镜像逻辑，只在命令解析和页面过滤时按模块分流。Telegram 当前支持新建、编辑、删除、移动和 Markdown 文档附件；飞书当前支持新建 `/随想`、图片随想 artifact、显式 ID 删除和回复原随想消息删除，均走 DB-first 入库。

## 1. 页面结构

- `source/thoughts/index.md`：锻炼随想页面，`layout: thoughts`，未声明模块时默认 `workout`
- `source/misc/index.md`：杂七杂八页面，`layout: thoughts`，`thought_module: misc`
- `source/body-feedback/index.md`：身体反馈页面，`layout: thoughts`，`thought_module: body_feedback`
- `themes/cactus/layout/thoughts.ejs`：共用列表 layout，读取 `page.thought_module || 'workout'` 过滤文章
- `themes/cactus/source/css/thoughts.styl`：共用卡片样式
- `_config.yml` 和 `themes/cactus/languages/zh-CN.yml`：导航入口和中文文案

列表页只展示短内容卡片：时间、标签、Telegram message id、正文和图片预览。不再展示顶部截图式说明区，也不展示“阅读全文”。详情页对没有 `title` 的 Telegram 随想做兼容，不渲染空 H1。

首页和归档继续把带 `随想` 标签的文章排除在普通文章列表之外，因此三个随想模块都不会混入首页文章流。

## 2. 消息通道命令

Telegram 和飞书都支持新建随想命令：

新建随想：

```text
/随想 正文
/thought 正文
/随想 锻炼 正文
/thought 锻炼 正文
/随想 杂七杂八 正文
/thought 杂七杂八 正文
/随想 身体反馈 正文
/thought 身体反馈 正文
```

路由规则：

- `/随想 正文` 和 `/thought 正文` 默认进入 `workout`
- 命令后的第一个空格分隔 token 是 `锻炼` 或 `锻炼随想` 时进入 `workout`
- 命令后的第一个空格分隔 token 是 `杂七杂八` 时进入 `misc`
- 命令后的第一个空格分隔 token 是 `身体反馈` 时进入 `body_feedback`
- 只识别第一个 token；未识别 token 会被当作正文，模块仍为 `workout`
- 图片 caption 和相册 caption 走同一套解析；识别为随想后不会进入训练截图 AI 识别
- Telegram 文档附件 caption 也走同一套解析；当附件是 Markdown 文档时，caption 只负责命令和模块，正文优先来自附件内容
- 飞书文本 `/随想` 走 DB-first 新建路径；飞书图片随想可保存图片 artifact，但当前不支持 Markdown 文档附件

Telegram Markdown 附件随想：

```text
/随想
/随想 杂七杂八
/随想 身体反馈
```

支持 `.md`、`.markdown`、`text/markdown`、`text/x-markdown`，以及 `text/plain` 且文件名为 Markdown 扩展名的 Telegram document。同步流程会下载第一个 Markdown 附件，按 UTF-8 解码、去 BOM、trim 后写入 `core.thought.body`；如果 caption 同时包含正文，附件正文优先。单个附件上限为 5MB，空文件、下载失败和超限都会在入库前失败并保留 `failureReason`。Markdown 附件不进入 `photos`，因此不会触发训练图片识别，也不会新增附件表、下载链接或附件卡片。

Telegram 编辑随想：

```text
/随想编 <id> <完整正文>
/随想编 <id> 杂七杂八 <完整正文>
/随想编 <id> 身体反馈 <完整正文>
/随想编 <id>                 + Markdown 文档附件
/随想编 <id> 杂七杂八        + Markdown 文档附件
/随想编 <id> 身体反馈        + Markdown 文档附件
```

支持三种编辑入口：直接编辑原 Telegram 消息、回复已有随想发送 `/随想` 或 `/thought` 修订版、使用 `/随想编 <id>` 显式按 ID 编辑。显式编辑时可以只在 caption 写 `/随想编 <id>` 或 `/随想编 <id> <模块>`，并附带 Markdown 文档；系统会把附件内容作为新的完整正文替换 `core.thought.body`。如果 caption 同时写了正文和 Markdown 附件，附件正文优先，不会与 caption 正文拼接。编辑时如果没有显式模块 token，会保留目标 Markdown 里的 `thought_module`；如果显式写了 `锻炼`、`锻炼随想`、`杂七杂八` 或 `身体反馈`，会同步更新 `thought_module` 和 tags。

删除随想：

```text
/随想删
/随想删 <id>
```

`/随想删` 需要回复原随想消息；`/随想删 <id>` 直接按页面显示的 `#id` 定位。删除不需要模块参数，会按 `telegram_message_id` 把 DB 行标记为 `deleted`；Markdown 备份和页面展示会在下一次严格数据库快照导出/部署后移除。飞书回复删除会把飞书原始 `message_id` 转成同一套稳定数字代理 ID 后定位目标；如果既没有 id 也没有可解析回复目标，同步会返回失败原因，不会误报删除成功。

Telegram 移动随想：

```text
/移动 锻炼
/移动 杂七杂八
/移动 身体反馈
/移动 <id> 锻炼
/移动 <id> 杂七杂八
/移动 <id> 身体反馈
/随想 <id> 锻炼
/随想 <id> 杂七杂八
/随想 <id> 身体反馈
```

`/移动 锻炼`、`/移动 杂七杂八` 和 `/移动 身体反馈` 需要回复原随想消息；`/移动 <id> 锻炼`、`/移动 <id> 杂七杂八` 和 `/移动 <id> 身体反馈` 直接按页面显示的 `#id` 定位。`/随想 <id> 锻炼`、`/随想 <id> 杂七杂八` 和 `/随想 <id> 身体反馈` 是兼容旧使用习惯的移动写法，等价于 `/移动 <id> ...`。移动只更新 Markdown front matter 的 `thought_module` 和 tags，不改正文、图片、日期和文件名；DB 镜像同步更新 `core.thought.thought_module`。如果只发送 `/移动 <id>` 或 `/随想 <id>` 而没有目标模块，系统不会生成移动批次。

## 3. Markdown Front Matter

Telegram 随想导出：

```text
source/_posts/YYYY-MM-DD-telegram-thought-<messageId>.md
```

锻炼随想示例：

```yaml
---
date: 2026-05-14 10:30:00
tags:
  - 训练
  - 随想
  - Telegram
thought_module: workout
telegram_message_id: 501
telegram_chat_id: 42
---
```

杂七杂八示例：

```yaml
---
date: 2026-05-14 10:30:00
tags:
  - 杂七杂八
  - 随想
  - Telegram
thought_module: misc
telegram_message_id: 503
telegram_chat_id: 42
---
```

身体反馈示例：

```yaml
---
date: 2026-05-14 10:30:00
tags:
  - 身体反馈
  - 随想
  - Telegram
thought_module: body_feedback
telegram_message_id: 504
telegram_chat_id: 42
---
```

历史 Telegram 随想如果没有 `thought_module`，运行时默认视为 `workout`，不会批量改写旧文件。图片继续写到 `source/images/thoughts/YYYY/MM/`，front matter 的 `photos` 保存 `/images/thoughts/...` 引用。

飞书随想导出使用：

```text
source/_posts/YYYY-MM-DD-feishu-thought-<proxyMessageId>.md
```

飞书原始 `message_id` 是字符串，当前 `core.thought.telegram_message_id` 仍是 bigint 主键，因此系统会生成稳定数字代理 ID。飞书 Markdown front matter 会额外保留真实来源：

```yaml
---
date: 2026-06-14 10:30:00
tags:
  - 训练
  - 随想
  - 飞书
thought_module: workout
source_channel: feishu
source_message_id: om_xxx
source_chat_id: oc_xxx
telegram_message_id: 123456789
telegram_chat_id:
---
```

这里的 `telegram_message_id` 是历史兼容字段名，不代表来源一定是 Telegram；判断真实通道应优先看 `source_channel`。

## 4. 数据库镜像

`core.thought` 是随想正文镜像表，保存正文、模块、消息通道元数据、Markdown 路径和图片引用，不保存图片二进制。关键字段：

- `telegram_message_id`：稳定定位 ID，也是页面显示的 `#id`；Telegram 使用原始 message id，飞书使用稳定数字代理 ID
- `thought_module`：`workout`、`misc` 或 `body_feedback`，默认 `workout`
- `tags_json`：页面标签镜像
- `markdown_path`：对应 Markdown 路径
- `image_refs_json`：有序图片引用
- `status`：`active` 或 `deleted`

Markdown 文档附件不会新增数据库字段；附件内容会在持久化前写入 `body`，后续仍由 DB -> Markdown 导出生成 `source/_posts/*telegram-thought-*.md` 或 `source/_posts/*feishu-thought-*.md` 并交给 Hexo 渲染。导出前会先清理旧的 Telegram 和飞书派生随想 Markdown，避免已删除随想继续残留在页面。

生产库兼容迁移：

```sql
alter table core.thought
  add column if not exists thought_module text not null default 'workout';

update core.thought
set thought_module = 'workout'
where thought_module is null;
```

`tools/backfill-thoughts-to-core.mjs` 会读取 Markdown front matter 的 `thought_module`；缺失时按 `workout` 导入。
