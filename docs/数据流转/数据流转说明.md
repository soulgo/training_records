# 数据流转说明

本文按链路说明系统中数据如何从输入进入 Markdown、数据库、静态页面和 Telegram 回复。

## 1. 页面构建链路

```mermaid
flowchart TD
  A["训练记录.md"] --> B["tools/training-parser.mjs"]
  DB["PostgreSQL core.*"] --> C["tools/training-db-read.mjs"]
  B --> S["TrainingSnapshot"]
  C --> S
  S --> D["source/_data/training.json"]
  S --> V["tools/dashboard-view.mjs"]
  V --> E["source/_data/dashboardView.json"]
  D --> H["Hexo"]
  E --> H
  H --> P["public/"]
  P --> G["GitHub Pages"]
```

数据源由 `TRAINING_SNAPSHOT_SOURCE` 决定：

- `markdown`：从 `训练记录.md` 构建。
- `database`：从 PostgreSQL `core.*` 构建。

## 2. Telegram 图片同步链路

```mermaid
flowchart TD
  T["Telegram 锻炼/体脂秤/饮食/睡眠图片或相册"] --> W["Cloudflare Worker"]
  W --> R["GitHub repository_dispatch"]
  R --> A["telegram-sync.yml"]
  A --> S["npm run sync:telegram"]
  S --> G["groupTelegramUpdates"]
  G --> AI["AI 图片识别 imageType"]
  AI --> N["analyzeTelegramBatch"]
  N --> I["事务内先写 ingest.* 审计层"]
  I --> DB["增量 upsert core 子表"]
  DB --> D["刷新目标 core.training_day"]
  DB -. "失败" .-> M["回退写 训练记录.md"]
  DB -. "失败" .-> Q["runtime/telegram-sync-pending.ndjson"]
```

相册由 Cloudflare Durable Object `TELEGRAM_ALBUM_BUFFER` 缓冲约 3 秒后统一派发。没有绑定时，Worker 会退回逐条 dispatch。

当前图片识别支持四类训练数据：

| 截图类型 | 识别字段 | 主要落点 |
| --- | --- | --- |
| 锻炼 | 活动总览、活动明细、热量、时长、距离、心率 | `core.training_day`、`core.activity` |
| 体脂秤 | 体重、BMI、体脂、骨骼肌、基础代谢等 | `core.measurement` |
| 饮食 | 餐次、总摄入、餐次明细 | `core.meal`、`core.training_day` |
| 睡眠 | 入睡/起床、睡眠阶段、睡眠评分、心率、HRV、血氧、呼吸率 | `core.sleep`、`core.training_day` |

睡眠图片的归档日期按醒来日期减一天计算；普通图片仍按图片内日期优先、文件名日期兜底的规则归档。

V9 以后，正常 `ready + stored` 图片批次以数据库为主事实源：只 upsert 本批次识别出的子表行，并刷新当前目标日期汇总，不会整日删除同日其它模块。需要更新人工账本时，只对目标日期做 Markdown 增量合并；数据库失败时仍使用 Markdown fallback 和 pending replay。

## 3. Telegram 随想链路

```mermaid
flowchart TD
  T["/随想 或 /thought"] --> S["npm run sync:telegram"]
  S --> P["source/_posts/*.md"]
  S --> I["source/images/thoughts/**"]
  S --> DB["core.thought"]
  DB -. "失败" .-> Q["pending 队列"]
```

随想 Markdown 是站点展示的直接内容源。数据库失败不会删除已经写出的 Markdown；待补偿记录会在后续同步启动时重放。

## 4. Telegram 分析与 AI Agent 链路

`/分析` 和 `/ai` 都只读现有数据，不写训练记录、随想或数据库。

```mermaid
flowchart TD
  Q["/分析 或 /ai 问题"] --> S["npm run sync:telegram"]
  S --> T["TrainingSnapshot / MCP tools"]
  T --> AI["AI Chat Completions"]
  AI --> R["Telegram sendMessage"]
```

差异：

- `/分析` 专注训练、饮食、体脂和身体反馈建议。
- `/ai` 会按问题选择 MCP 查询工具，例如历史搜索、同步状态、配置或训练分析。

## 5. 数据存储分层

| 存储 | 职责 |
| --- | --- |
| `训练记录.md` | 人工可读记录、默认页面源、数据库故障回退 |
| `source/_posts` | Hexo 文章和 Telegram 随想 |
| `source/images/thoughts` | Telegram 随想图片 |
| `source/_data/*.json` | 页面构建数据产物 |
| `runtime/telegram-sync-pending.ndjson` | PostgreSQL 写入失败后的待重放队列 |
| `runtime/training-db-sync.ndjson` | archive 写入失败日志 |
| `ingest.*` | Telegram 批次、消息和识别原始记录 |
| `core.*` | 主结构化训练数据，包含训练日、体脂、活动、餐次、睡眠和随想 |
| `archive.*` | 构建快照和运行留痕，包含 `archive.training_sleep` 睡眠明细 |

## 6. 失败与补偿

- 图片批次写库失败：回退写 `训练记录.md`，并写 pending 队列。
- 随想批次写库失败：保留 `source/_posts` 和图片，写 pending 队列。
- archive 写入失败：写 `runtime/training-db-sync.ndjson`，不阻断页面构建。
- 数据库恢复后：下一次 `npm run sync:telegram` 会先重放 pending 队列。
- archive 中已有但 core 缺失的睡眠记录：`npm run backfill:core` 会补写 `core.sleep` 并更新训练日睡眠汇总。
- GitHub Actions 的 Telegram dispatch 会写 step summary，按 batch 输出 `taskStatus`、`persistenceStatus`、`archivedDate`、图片计数、pending 状态、`failureDisposition` 和失败 message id，便于区分可自动重试和需要人工修正的失败。
