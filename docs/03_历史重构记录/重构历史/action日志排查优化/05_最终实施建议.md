# 最终实施建议

> **第三轮修订（2026-06-28）**：基于真实运行日志复核，新增 P0-0（dispatch payload 泄漏合并），并扩大 P0-1 范围至两个 deploy。带 ⚠️ 的条目为第三轮修订。

## 总体判断

本轮不建议改业务逻辑、数据库结构、Prompt 或 AI 识别规则。优先做日志安全和结构化，因为当前由源码与**真实运行日志**共同验证的主要问题是：

1. ⚠️ **生产 main 分支仍把完整 dispatch payload 写入 `$GITHUB_ENV` 并重复打印**（dev 已修复未合并）。
2. `export:markdown` 会把完整训练快照输出到 Action 日志，且**两个 deploy workflow 同样泄漏**（不止 backup）。
3. Trace 上下文没有贯穿 Worker、Queue、Action、AI、DB、Deploy。
4. AI 和 DB 的关键上下文没有进入最终 summary。
5. 部署等待、DB 查询、pending replay 的可观测性不足。

⚠️ 原先”Action 日志已打印原始 dispatch payload”被前两轮判为”无源码证据、不实施”——**该判断错误**，实测 main 分支真实泄漏，已回退为 P0。

## P0：立即实施

### P0-0 ⚠️ dispatch payload 泄漏合并（第三轮新增，最高优先）

目标：

- 生产 main 的同步日志不再出现完整 `SYNC_DISPATCH_PAYLOAD` 原文、`file_id`、`from.id/username`、`chat.id`。

现状（实测）：

- `main` 的 `sync.yml:89-91`、`sync-dev.yml:83-85` 仍执行 `echo "SYNC_DISPATCH_PAYLOAD<<...>>$GITHUB_ENV"` + `echo "$DISPATCH_PAYLOAD">>$GITHUB_ENV"`。
- 实测 Sync Main #112 日志同一条 payload 重复 4+ 次。
- dev 已修复（`026ef49 修复同步队列日志泄露` + `2d45b74 fix: restore queued sync payload consumption`），**未合并 main**。

实施建议：

1. 将 dev 的 `026ef49`+`2d45b74` 合并到 main（已是 dev 验证过的修复，改用 `ORIGINAL_GITHUB_EVENT_PATH` 读取，只写 `SYNC_DISPATCH_EVENT_PATH`，不再写原文 env）。
2. 合并后用一次真实 webhook 触发的 main 同步 run 校验。

验收标准：

- `gh run view <latest-main-sync-run> --log | grep -c "SYNC_DISPATCH_PAYLOAD\|file_id\|\"from\""` 期望 0。
- 同步仍能读取 event 文件并完成。
- run name 仍含 `queue_task_id`。

### P0-1 Markdown 导出只输出 compact summary

目标：

- deploy 和 markdown-backup 日志不再打印完整训练快照。
- 不再输出 `weightKg`、`bodyFatPct`、`sleepStageText`、`analysisText` 等健康明细。

涉及位置：

- `tools/export-training-markdown.mjs:18-51`
- `tools/training-maintenance.mjs:87`
- `tools/training-maintenance.mjs:672-696`
- `.github/actions/site-build/action.yml:109-121`
- `.github/workflows/markdown-backup.yml:82-84`
- ⚠️ **第三轮补充（高频泄漏点）**：`.github/workflows/deploy-pages.yml:74-78`（site-build `run_tests:'true'`，实测 Deploy #350 含 399 处 snapshot 字段）、`.github/workflows/deploy-cloudflare-pages-dev.yml:68-72`（实测 Deploy CF #233 含 223 处）。deploy 是每次同步后触发，比 backup（每日）更频繁。

实施建议：

1. `runExportMaintenance()` 默认返回 summary，不把 `snapshot` 放入 stdout payload。
2. 若本地确实需要完整 payload，增加显式 `--debug-json`。
3. GitHub Actions 环境中禁止 `--debug-json`。
4. Summary 字段包含：status、mode、target、outputPath、dailyCount、thoughtExportedCount、thoughtRemovedCount、durationMs。

验收标准：

- `rg "weightKg|bodyFatPct|sleepStageText|analysisText" <deploy-log>` 无命中。
- `npm run export:markdown` 仍生成 `训练记录.md` 和 `source/_posts`。
- Markdown backup summary 能判断 changed/commit/conclusion。

风险：

- 如果某个维护脚本依赖 `training-maintenance export` 的完整 stdout，需要改为读生成文件或使用显式 debug 参数。

## P1：第一轮结构化

### P1-1 新增统一 action logger

目标：

- 所有新增日志使用统一 JSON schema。
- 保留可 grep 前缀，例如 `[action-log] {...}`。

建议文件：

- `tools/lib/action-logger.mjs`

核心能力：

- `info(domain, event, fields)`
- `warn(domain, event, fields)`
- `error(domain, event, fields)`
- `hashSensitive(value)`
- `buildTraceContext(env)`

验收标准：

- Sync、AI、DB、Markdown、Deploy 至少各有一个结构化 summary。
- 日志字段名稳定：`traceId`、`domain`、`event`、`durationMs`、`outcome`。

### P1-2 traceId 贯穿

目标：

- 任一同步 run 可用一个 `traceId` 串起 Worker、Queue、Action summary、AI call log、DB pending、Deploy。

涉及位置：

- `cloudflare/sync-dispatch-queue.mjs:451-485`
- `.github/workflows/sync.yml:2`、`:68-115`
- `.github/workflows/sync-dev.yml:2`、`:62-109`
- `src/app/use-cases/telegram-sync.use-case.mjs:95-552`
- `src/db/training/pending-recognition.mjs`
- `src/adapters/postgres/telegram-batch-repository.pg.mjs`

实施建议：

1. 从 `queue_task_id` 派生 `traceId = "tr_" + sha256(queue_task_id).slice(0,16)`。
2. workflow output/env 传递 `TRACE_ID`，但不传原始 payload。
3. result JSON 和 Action summary 增加 `traceId`。
4. AI call log 与 pending batch 增加可选 trace 字段时保持 additive；如不改 DB schema，先写入 JSON summary。

验收标准：

- Worker tail 能看到 `queue.task.enqueued` 与 `traceId`。
- GitHub Step Summary 能看到同一 `traceId`。
- AI/DB/Deploy summary 均能反查同一 trace。

### P1-3 抽取 sync summary 脚本

目标：

- 删除 `.github/workflows/sync.yml` 和 `sync-dev.yml` 中重复的大段 inline Node summary。
- Telegram / 飞书共用同一 summary formatter。

建议文件：

- `tools/action-sync-summary.mjs`

输入：

- `--channel telegram|feishu`
- `--result-path <path>`
- `--trace-id <traceId>`
- `--queue-task-id <queueTaskId>`
- `--workflow <name>`
- `--run-id <id>`

输出：

- GitHub Step Summary Markdown。
- 一行 compact JSON `ACTION sync.summary.completed`。

验收标准：

- Main/Dev 两个 workflow summary 内容一致。
- 飞书仍保留 `sourceId` 但支持 hash/截断。
- business incomplete warning 逻辑与现状一致。

### P1-4 AI 调用 summary

目标：

Action summary 能回答：

- 用了哪个 provider/model。
- Prompt/schema 版本是什么。
- 是否 response_format fallback 或 provider fallback。
- HTTP retry 几次。
- AI 耗时和 token 用量。
- 成功还是失败。

涉及位置：

- `src/app/use-cases/image-recognition.use-case.mjs:146-155`
- `src/app/use-cases/image-recognition.use-case.mjs:196-244`
- `src/app/use-cases/image-recognition.use-case.mjs:788-861`
- `src/adapters/ai/openai-compatible.adapter.mjs:115-145`
- `src/db/training/pending-recognition.mjs:402-442`
- `src/adapters/postgres/telegram-batch-repository.pg.mjs:284-327`
- `tools/training-analysis.mjs:116-128`、`:335-362`

验收标准：

- 成功图片 batch summary 出现 `provider`、`model`、`promptVersion`、`attemptKinds`、`durationMs`。
- fallback 演练时 summary 明确 `fallbackUsed=true`。
- provider 返回 usage 时 summary 出现 token totals。
- 日志不包含 Prompt 全文、用户 caption/text、图片 data URL、API Key。

### P1-5 DB 写入 summary 与慢查询观测

目标：

Action summary 能回答：

- DB 是否写入成功。
- 是否 unchanged。
- 写了哪些表的大概行数。
- rollback/pending 是否发生。
- DB 阶段耗时。
- 是否有慢查询。

涉及位置：

- `src/db/training/write.mjs:41-151`
- `src/adapters/postgres/telegram-batch-repository.pg.mjs:13-230`
- `src/adapters/postgres/incremental-write.pg.mjs:15-36`
- `src/db/training/pending-recognition.mjs:13-287`
- `src/db/training/read-client.mjs:37-73`

验收标准：

- `persistenceStatus=stored` 时有 `DATABASE batch.persist.completed`。
- `unchanged` 时说明 `payload_hash_unchanged`。
- 失败时记录 rollbackStatus 和 pendingStatus。
- 慢查询超过阈值时输出 `DATABASE query.slow`。
- 不输出 SQL 参数和 DB URL。

### P1-6 Deploy wait 状态日志

目标：

长等待时不再静默。

涉及位置：

- `.github/workflows/sync.yml:521-629`
- `.github/workflows/sync-dev.yml:507-615`

验收标准：

- 每隔固定 attempt 输出 deploy run status。
- 超时日志包含 deployRunId、lastStatus、elapsedMs、workflowFile。
- 成功 summary 包含 deploy duration 和 URL。

## P2：第二轮治理

### P2-1 dispatch payload 防回归（⚠️ 第三轮修订：从"防回归"改为"P0-0 合并后的回归校验"）

⚠️ 原文"当前 workflow 只写 `SYNC_DISPATCH_EVENT_PATH`，没有 echo 原始 payload"——**该前提仅在 dev 成立，生产 main 仍泄漏**（见 P0-0）。因此本项不再是"防未发生的回归"，而是"确保 P0-0 合并后不再回退"。

当前状态（合并 P0-0 后）：

- workflow_dispatch input 仍接收 `dispatch_payload`。
- `Determine sync channel` 将 payload 转成 runner temp event file。
- workflow 只写 `SYNC_DISPATCH_EVENT_PATH`，不再 echo 原始 payload，也不再把原文写入 `$GITHUB_ENV`。

建议：

1. 保持当前传递方式。
2. 新增安全摘要：channel、messageCount、imageCount、payloadHash。
3. 在测试或脚本检查中禁止新增 `echo "$dispatch_payload"`。
4. failure monitor 继续从 event path 读取目标，不打印 payload。

验收标准：

- `rg "DISPATCH_PAYLOAD|SYNC_DISPATCH_PAYLOAD" .github/workflows` 不出现把原文写 `$GITHUB_ENV` 或 echo 的代码。
- 同步仍能读取 `SYNC_DISPATCH_EVENT_PATH` 并完成。
- run name 仍能通过 `queue_task_id` 关联 Worker 队列。

### P2-2 CI 降噪与去重

涉及位置：

- `.github/workflows/ci-tests.yml:65-87`
- `.github/workflows/ci-tests.yml:89-106`

建议：

1. schedule/workflow_dispatch 时跳过 fast job 或让 full-test 覆盖 fast。
2. 测试模拟日志加 `[test-fixture]` 前缀。
3. 失败时才展开模拟 stderr。

验收标准：

- `rg "primary AI recognition failed|retrying|timeout" ci-log` 能区分测试模拟与真实脚本日志。

### P2-3 依赖 warning 治理

建议：

2. 新增 dependency audit workflow 或定期任务。
3. 逐步处理 npm deprecated package。

验收标准：

- routine sync 日志不再被 npm audit 淹没。
- 依赖风险仍有独立告警入口。

## 风险控制

| 风险 | 控制方式 |
| --- | --- |
| 导出 stdout 变更影响维护脚本 | 搜索 `export:markdown` stdout 使用方，必要时加兼容 flag |
| traceId 传递影响同步读取 payload | 先在 dev workflow 验证 workflow_dispatch 与 repository_dispatch |
| AI/DB summary 字段改变测试 | 新增字段保持 additive，不改现有业务字段 |
| 脱敏后排障信息不足 | 保留 hash、traceId、batchId、messageId 摘要 |
| 日志 JSON 太吵 | INFO 只输出阶段开始/结束，DEBUG 默认关闭 |

## 最终验收清单

### 安全

- Action 日志不包含 Secret、API Key、DB URL。
- Action 日志不包含原始 dispatch payload。
- Action 日志不包含完整训练 snapshot 或健康明细。
- Prompt 全文和用户原文不进入日志。
- file_id、image_key、chat_id、COS key 默认 hash 或截断。

### 可观测性

- 任一同步 run 可从 summary 找到 traceId、queueTaskId、channel、batchId。
- 可看到 AI provider/model/promptVersion/fallback/retry/duration/token。
- 可看到 DB persistenceStatus、row count summary、pending/rollback、slow query。
- 可看到 Markdown export summary。
- 可看到 deploy run id、status、duration、URL。

### 可维护性

- Main/Dev summary 使用同一个脚本生成。
- 日志 domain/level/event 命名统一。
- 新增通道或新增 batch kind 时只扩展 summary formatter，不复制 YAML。

### 效率

- deploy/backup 日志不再输出完整 payload。
- CI 成功日志能区分测试模拟失败和真实失败。
- 维护人员仅通过 Action summary + 少量结构化日志即可判断故障归属。
