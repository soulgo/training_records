# 模块级重构方案：分析

## 当前问题

| 问题 | 证据 | 优先级 | 风险等级 |
| --- | --- | --- | --- |
| 分析链路有两层入口且职责方向仍倒置 | 当前 `src/app/use-cases/training-analysis.use-case.mjs` 只是薄 wrapper，实际 snapshot/AI/审计逻辑仍在 `tools/training-analysis.mjs`；目标才是把核心逻辑迁入 use case 并让 tools 变薄 | P2 | P2 |

## 设计缺陷

- 分析是读模型 + AI 生成 + 通道回复，应该是独立 use case。
- 训练数据源异常时，用户更需要知道“数据源异常”，而不是静默 fallback。
- AI 输出已有本地 `snapshotSource/model/aiAttemptKind` 和 best-effort `ingest.ai_call_log`，但真实 dev/main `/analysis` 端到端仍需验证这些字段能进入 summary/回执判读。

当前行为边界：

- `TRAINING_SNAPSHOT_SOURCE=database` 时，`generateTrainingAnalysisReply()` 会先尝试数据库 snapshot。
- 如果数据库 snapshot 不完整或不可用，当前代码按 `TRAINING_ANALYSIS_SNAPSHOT_POLICY` 决定行为：`strict_db` 返回 `snapshotSource=strict_db_error` 且不 fallback，`allow_markdown_fallback` 才 fallback 到 Markdown 并标记 `fallback_markdown`。
- `TRAINING_SNAPSHOT_STRICT_DATABASE` 当前不参与 `/analysis` fallback 判断；它在导出/构建类路径中被使用，而分析链路通过 `tools/training-analysis.mjs` 的 `resolveAnalysisSnapshotPolicy()` 读取 `TRAINING_ANALYSIS_SNAPSHOT_POLICY`。
- 因此不能把 `TRAINING_SNAPSHOT_STRICT_DATABASE=true` 当作 `/analysis` strict 行为；分析 strict 必须由 `TRAINING_ANALYSIS_SNAPSHOT_POLICY` 或等价分析专用策略显式控制，真实 dev/main 仍需验证 summary/回执可判读。
- `/analysis` question 当前会经 `normalizeAnalysisQuestion()` 处理：空问题使用默认问题，超长问题截断，控制字符移除，Emoji/中文/HTML 字面量保留，并在 prompt 中标记为用户上下文而非系统指令。

## 重构方案

### P1：抽取 TrainingAnalysisUseCase

输入：

| 字段 | 说明 |
| --- | --- |
| `question` | 用户问题 |
| `channel` | 回复通道 |
| `sourceMessageId` | 原始消息 |
| `snapshotSourcePolicy` | strict_db / allow_markdown_fallback |
| `trainingGoal` | 训练目标 |

输出：

| 字段 | 说明 |
| --- | --- |
| `reply` | 回复文本 |
| `snapshotSource` | database / fallback_markdown / strict_db_error |
| `promptVersion` | prompt 版本 |
| `model` | AI 模型 |
| `analysisTaskId` | 审计 ID |

### P1：AI 调度器接入

- analysis 使用独立场景配置：`AI_ANALYSIS_MODEL`、`AI_ANALYSIS_TIMEOUT_MS`、`AI_ANALYSIS_FALLBACK_*`。
- fallback 结果必须在回复尾部或 summary 中标记为 fallback，不伪装成 primary。

### P2：快照源策略

| 场景 | 策略 |
| --- | --- |
| main 线上 `/analysis` | 默认 strict_db；DB 不可用则回复“数据源异常，稍后重试” |
| dev 调试 | 允许 markdown fallback |
| 本地 CLI | 允许显式 `TRAINING_ANALYSIS_ALLOW_MARKDOWN_FALLBACK=true` |

实施前置条件：

- strict_db 切换前，summary 或回复中必须已经能暴露 `snapshotSource=database|fallback_markdown|strict_db_error`。
- main 切换 strict_db 需要可回滚配置，避免短期 DB 抖动导致分析完全不可用。
- dev 与本地 fallback 必须在结果中明确标注，不能伪装成 database 分析。

## 接口变更影响

| 接口 | 影响 | 兼容策略 |
| --- | --- | --- |
| `generateTrainingAnalysisReply()` | 目标状态为内部调用新 use case；当前仍承载实际分析逻辑 | 保持返回 string |
| `/analysis` 命令 | 回复内容可能包含数据源异常提示 | 命令语义不变 |
| `tools/training-analysis.mjs` | 逐步薄化 | 旧导出保留 |

## 风险评估

| 风险 | 等级 | 控制 |
| --- | --- | --- |
| strict_db 导致短期分析失败增多 | P1 | dev 先试，main 可配置 fallback |
| 回复内容变化影响用户体验 | P2 | 保留短回复格式，只在异常时说明 |
| 审计写入失败影响分析回复 | P2 | 审计失败不阻断回复，写 pending log |
| fallback Markdown 掩盖 DB 异常 | P1 | 回复或 summary 必须显示 `fallback_markdown`，并在 main strict_db 阶段禁止静默 fallback |
| 超长/恶意 question 导致 AI 成本和超时上升 | P1 | `normalizeAnalysisQuestion()` 增加最大长度、控制字符过滤和用户文本分隔符；超限时回执提示截断 |

## Bug 修复方案（本轮审计新增）

### P1-13：`TRAINING_SNAPSHOT_STRICT_DATABASE` 不保护 `/analysis`

**问题文件**：`tools/training-analysis.mjs:66-110`

**问题描述**：原始审计发现 `/analysis` 在 `TRAINING_SNAPSHOT_SOURCE=database` 且数据库 snapshot 不可用/不完整时，会 fallback 到 Markdown 并标记 `source=fallback_markdown`。函数没有读取 `TRAINING_SNAPSHOT_STRICT_DATABASE`，所以 workflow 中配置 strict database 不能阻止 `/analysis` 静默 fallback。后续文档不能把“`TRAINING_SNAPSHOT_STRICT_DATABASE` 已保护分析”写成现状。

**实施状态（本地）**：已完成本地合同校准。当前 `/analysis` 通过 `TRAINING_ANALYSIS_SNAPSHOT_POLICY=strict_db|allow_markdown_fallback` 显式控制分析快照策略；DB snapshot 不可用且 policy 为 `strict_db` 时返回 `snapshotSource=strict_db_error` 并不调用 Markdown fallback；允许 fallback 时返回 `snapshotSource=fallback_markdown`；`TRAINING_SNAPSHOT_STRICT_DATABASE=true` 不会被误当作当前分析 strict 开关。真实 dev/main 分析端到端仍需检查 summary/回执中的 snapshot source。

**已落地实现要点**：

1. 新增 `TRAINING_ANALYSIS_SNAPSHOT_POLICY=strict_db|allow_markdown_fallback`，避免复用导出链路的环境变量造成误解。
2. main 默认 `strict_db`；dev/local 可显式 `allow_markdown_fallback`。
3. 即使允许 fallback，也必须在回复或 summary 中暴露 `snapshotSource=fallback_markdown`。

**测试策略 / 当前覆盖**：

- DB snapshot 正常时返回 `snapshotSource=database`。
- DB snapshot 不可用 + `strict_db` 时返回数据源异常，不调用 Markdown fallback。
- DB snapshot 不可用 + `allow_markdown_fallback` 时返回 `fallback_markdown` 且回执可见。

**回滚计划**：

- 如 main strict_db 导致分析不可用，可临时把 `TRAINING_ANALYSIS_SNAPSHOT_POLICY` 改回 `allow_markdown_fallback`，但保留回执标记。

### P1-14：`/analysis` question 无长度和注入边界

**问题文件**：`tools/training-analysis-focus.mjs:4-7`、`tools/training-analysis-request.mjs:20-25`

**问题描述**：原始审计发现用户问题仅做基础裁剪后进入 prompt。超长 Markdown/HTML/控制字符/重复文本会扩大 prompt，增加 timeout 和成本，也可能诱导模型忽略系统提示。

**实施状态（本地）**：已完成本地合同校准。当前 `normalizeAnalysisQuestion()` 会移除控制字符、限制最大长度、为空时使用默认问题，并保留 Emoji/中文/HTML 字面量；`requestTrainingAnalysisResult()` 会用分隔符标明 question 是用户原文上下文，不作为系统指令。已由 `test/training-analysis.test.mjs` 覆盖 prompt-safe question。

**已落地实现要点**：

```js
export function normalizeAnalysisQuestion(question, { maxLength = 1000 } = {}) {
  const normalized = String(question ?? '').trim()
    .replace(/[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]/g, '');
  return normalized.slice(0, maxLength) || defaultQuestion;
}
```

在 `requestTrainingAnalysis()` 中用分隔符标明 `Q` 是用户文本，不是指令覆盖。

**测试策略 / 当前覆盖**：

- 空 question 使用默认问题。
- Emoji/中文保留。
- 控制字符移除。
- 超长问题被截断，且不会导致 prompt 过长。

**回滚计划**：

- 如截断影响正常问题，可提高 `TRAINING_ANALYSIS_MAX_QUESTION_CHARS`；不回滚到无限长。

## 回滚方案

1. 关闭 `TRAINING_ANALYSIS_V2_ENABLED`。
2. 回退到 `tools/training-analysis.mjs` 旧函数。
3. 保留新增审计表，不参与读取。
