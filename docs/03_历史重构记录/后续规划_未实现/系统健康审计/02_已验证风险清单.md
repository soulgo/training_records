## B01：GitHub Action 并发保护绕开全局串行（P0）

**判定：✔ 已验证**

**代码证据**：`.github/workflows/sync.yml:37-39`

```yaml
concurrency:
  group: ${{ (github.event.inputs.queue_task_id || github.event_name == 'repository_dispatch') && format('sync-{0}', github.run_id) || 'sync' }}
  cancel-in-progress: false
```

**解读**（GitHub Actions `A && B || C` 语义）：

| 触发路径 | A 求值 | group | 是否串行 |
|---|---|---|---|
| webhook dispatch（DO 队列带 `queue_task_id`） | 真 | `sync-<run_id>` | 否（每 run 唯一）|
| `repository_dispatch` | 真 | `sync-<run_id>` | 否 |
| 手动 / push | 假 | `sync` | 是 |

webhook 路径确实绕开全局串行组，串行性完全依赖 DO 队列保证。`queue_task_id` 由 `sync-dispatch-queue.mjs:477-480` 的 `buildWorkflowDispatchPayload` 注入，确认 webhook dispatch 一定走 `sync-<run_id>` 分支。

补充约束：`test/github-workflows.test.mjs:691-711` 明确保护当前设计，测试名为 `telegram-sync workflow dispatch runs use unique concurrency groups while the worker queue controls ordering`，并用 `assert.doesNotMatch` 禁止把所有 `repository_dispatch` 放入固定 pending queue。因此把 webhook 改成稳定 concurrency group 不是单纯补漏，而是需要先推翻或改写现有测试保护的设计决策。

> 注：原报告称"第 37 行使用 `sync-${{ github.run_id }}`"——行号与措辞不精确（group 表达式在第 38 行，且为条件三元），但结论实质成立。

## DO 队列串行保证（对不同任务）

**判定：✔ 已验证（对不同任务成立）**

**代码证据**：`cloudflare/sync-dispatch-queue.mjs:67-84`

```js
async alarm() {
  const processing = await this.readProcessing();
  if (processing) {
    await this.continueProcessing(processing);   // 有 processing 就继续，不取新任务
    return;
  }
  const task = await this.dequeueTask();          // 否则只取一条
  if (!task) { return; }
  await this.continueProcessing({ task, phase: 'dispatch', attempts: task.attempts ?? 0 });
}
```

Durable Object 单线程单实例 + `blockConcurrencyWhile`（:26-33）+ processing 标记 + 一次只 dequeue 一条 → 对**互异任务**串行保证成立。

> 注：正常“找不到 run”会进入 `wait_for_run` 并继续查询，不会立刻重复 dispatch；重复窗口集中在 `workflow_dispatch` 已成功发出后，`findDispatchedRunId` 抛错导致 catch 按旧 `phase: 'dispatch'` 重试的路径。详见 `03_误判与修正清单.md`。
