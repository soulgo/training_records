# 误判与修正清单

以下结论**核心机制存在，但声称的代码位置、措辞或触发条件需修正/补充**。修正后可纳入可信风险清单。

## 修正 1：B01 并发保护——行号与措辞不精确

**原声称**：`sync.yml` webhook dispatch 的 concurrency group 使用 `sync-${{ github.run_id }}`，每个 run 都不同（引用 `sync.yml:37`）。

**实际代码**（`.github/workflows/sync.yml:37-39`）：

```yaml
concurrency:
  group: ${{ (github.event.inputs.queue_task_id || github.event_name == 'repository_dispatch') && format('sync-{0}', github.run_id) || 'sync' }}
  cancel-in-progress: false
```

**修正**：
- group 表达式在**第 38 行**而非第 37 行（第 37 行是 `concurrency:` 关键字）。
- 并非"无条件使用 `sync-<run_id>`"，而是**条件三元**：webhook dispatch / repository_dispatch 路径才用 `sync-<run_id>`，手动/push 路径用固定 `sync`（串行）。
- 结论实质成立（webhook 路径不串行），但修复不是直接替换表达式即可；`test/github-workflows.test.mjs:691-711` 明确保护“唯一 concurrency group + worker queue controls ordering”，并禁止固定 pending queue。若要改为稳定 group，必须同步改写该测试和对应设计说明。

## 修正 2：DO 队列串行——补充"同任务重试重复 dispatch"窗口

**原声称**：DO 队列用 DO SQLite/KV 去重、排序、单任务 processing、dispatch workflow，轮询 run 完成后再取下一条。

**实际代码**（`cloudflare/sync-dispatch-queue.mjs`）：

- 对**互异任务**串行成立（`alarm` :67-84，processing 标记 + DO 单线程）。
- 正常“查不到 run”路径已在 `continueProcessing`（:112-118）写入 `phase: 'wait_for_run'` 和 `dispatchStartedAt`，后续 alarm 会继续 `findDispatchedRunId`，不会直接再次 dispatch。
- 但对**同一任务的 run 查询异常重试**存在重复 dispatch 窗口：
  - `continueProcessing`（:86-130）在 `phase: 'dispatch'` 时调用 `dispatchGithubTask`（:98-102）。
  - 若 `dispatchGithubTask` 成功返回，但随后的 `findDispatchedRunId`（:104-110）因 HTTP/网络/响应解析异常抛错 → catch → `retryOrDeadLetter(processing, error)`（:127-128）。
  - `retryOrDeadLetter`（:175-203）在 `attempts < MAX_ATTEMPTS` 时 `storeProcessing({...processing, attempts, lastError}, delay)`（:178-182），传入的是旧 `processing`，**保留原 `phase: 'dispatch'`**，且没有持久化刚生成的 `dispatchStartedAt`。
  - 下次 alarm → `readProcessing` 返回它 → `continueProcessing` → phase 非 wait_for_run/wait_for_completion → **再次 `dispatchGithubTask`**。
  - `dispatchGithubTask`（:369-385）对 GitHub `.../dispatches` API **无幂等键**。

**修正/补充**：若 GitHub 已创建 run，但 DO 在查询 run 阶段遇到网络/HTTP/响应解析异常，重试会再次创建 workflow run。且因该路径 concurrency group 为 `sync-<run_id>`（见 B01），两个 run 互不取消、并行执行同一同步——**重复 dispatch 真实存在**。

建议在审计结论补一句："`dispatchGithubTask` 成功发出后，应先持久化 `phase: 'wait_for_run'` 和 `dispatchStartedAt`；否则 `findDispatchedRunId` 抛错会让重试回到 `phase: 'dispatch'` 并重复触发 workflow。"

## 修正 3：AI fallback 不一致——精确化为"fallback provider 不检查置信度"

**原声称**：AI fallback 是否真的不一致；fallback provider 只在 retryable/timeout/schema 空内容时触发，业务低置信度不会自动换模型。

**实际代码**（`src/app/use-cases/image-recognition.use-case.mjs`）：

- `shouldRetryWithFallbackProvider`（:260-276）触发条件：`AiProviderError` / 可重试状态码（429,500,502,503,504）/ AbortError/TimeoutError / 消息匹配 `timeout|empty content|rate limit|HTTP 429/5xx|network|fetch failed` / 递归 cause。
- **不检查置信度**：`confidence` 只在 `normalizeRecognitionPayload`（:649-651）对 measurement 缺数据时被钳制到 ≤0.5 并加 warning，但不触发 provider 切换。
- format fallback 链（strict→json_object→无格式，:788-822）的输出解析逻辑一致（都走 `parseRecognitionContent` :503-514），输出结构一致。
- `attemptKind` 区分 `normal/strict_json_retry/fallback`（:385, :401, :232），写入审计字段但不改变输出 schema。

**修正**："AI fallback 不一致"措辞需精确化：
- **不是**"fallback 输出格式与主流程不一致"——三者解析逻辑一致。
- **而是**"fallback provider 切换只看错误类型，不看业务置信度"——低置信度结果（confidence<0.75 被系统跳过，见 prompt :137）不会触发换模型重试。
- prompt 中 `confidence<0.75 会被跳过`（:137）与代码 `normalizeRecognitionPayload` 的置信度钳制（:649）是系统侧处理，非 provider 切换。

## 修正 4：隐性丢数据——"无条件 commit"应为"diff 驱动提交"

**原声称**：备份 Action 若提交会扩大损失（隐含"无条件 commit"）。

**实际代码**（`.github/workflows/markdown-backup.yml:97-105`）：

```yaml
if: steps.gate.outputs.run_backup == 'true' && steps.detect.outputs.changed == 'true' && env.MARKDOWN_BACKUP_COMMIT == 'true'
```

- commit 并非无条件，而是三重门控：`run_backup` + `changed`（`git status --porcelain` 检测 :86-95）+ `MARKDOWN_BACKUP_COMMIT`（默认 'true' :22）。
- export step（:82-84 `npm run export:markdown`）若中途失败，`changed` 检测与 commit step 仍会运行（无 `if: success()` 前置）。

**修正**：准确说法是"**diff 驱动提交，无法识别不完整重写**"。
- export 在删除后中断 → "已删除未重写"状态本身会 diff → `changed == 'true'` → 被提交。
- 门控无法区分"完整重写产生的 diff"与"中断导致的净丢失 diff"，两者都会提交。
- "扩大损失"结论成立，但"无条件 commit"措辞不严谨。

## 修正 5：Telegram 通道鉴权——文件归属需精确

**原声称**：通过 `X-Telegram-Bot-Api-Secret-Token` 分流（指向 `sync-dispatch-worker.mjs`）。

**实际代码**：

- **分流**（按 header 存在性路由）在 `sync-dispatch-worker.mjs:54-57` `detectSyncDispatchChannel`。
- **值校验**（401 拒绝）在 `telegram-sync-dispatch-worker.mjs:5,126-130`：
  ```js
  const expectedSecret = env.TELEGRAM_SECRET_TOKEN.trim();
  const providedSecret = request.headers.get(TELEGRAM_SECRET_HEADER) ?? '';
  if (providedSecret !== expectedSecret) {
    return jsonResponse(401, { ok: false, error: 'unauthorized' });
  }
  ```

**修正**：分流在 `sync-dispatch-worker.mjs`，但 secret token **值校验**（真正的鉴权）在 `telegram-sync-dispatch-worker.mjs:126-130`。实质结论成立（Telegram 通道用该 header 既分流又鉴权），文件归属需修正。
