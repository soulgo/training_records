# 中优先级：连接池与读取性能优化

> 优先级：中
> 目标：降低 PostgreSQL 连接峰值、减少快照读取放大、补齐读取链路观测能力。安全边界收敛后再实施本项，避免把连接池和权限迁移混在一起。

## 目标状态

- 所有 PostgreSQL 连接都经过统一 factory 或 pool 管理。
- 读取快照的并发可配置，不能硬编码 6/5 个独立连接。
- 支持 `dateFrom/dateTo` SQL 下推；只查近期数据时不再全表读取再交给 mapper 过滤。
- 读取链路输出与写入链路一致的安全慢查询摘要。
- 连接池配置、statement timeout 和 read parallelism 有明确默认值、配置文档和测试。

## 拟新增配置

这些配置当前尚不存在，落地时必须同步 `docs/01_系统配置/` 和 workflow。

| 配置 | 建议默认 | 用途 |
| --- | --- | --- |
| `TRAINING_DB_POOL_MAX` | `4` 或按 DB 服务商连接上限折算 | 单进程最大连接数。必须小于数据库连接上限，并考虑并发 workflow。 |
| `TRAINING_DB_IDLE_TIMEOUT_MS` | `10000` | Pool idle client 释放时间。 |
| `TRAINING_DB_STATEMENT_TIMEOUT_MS` | `15000` | 防止单条 SQL 长时间卡住。可通过连接参数或 session `set statement_timeout` 实现。 |
| `TRAINING_DB_READ_PARALLELISM` | `2` | 快照读取并发上限。不能超过 `TRAINING_DB_POOL_MAX`。 |
| `TRAINING_DB_READ_SLOW_QUERY_MS` | 复用 `TRAINING_DB_SLOW_QUERY_MS`，或默认 `1000` | 读取链路慢查询摘要阈值。 |

配置解析建议仍放在 `src/db/training/config.mjs` 或新建 `src/db/training/client-config.mjs`，但要保持原有 `resolveTrainingCoreConfig()` 对外兼容。

## 代码改动清单

### 1. 统一连接创建

当前重复创建 `new Client(...)` 的位置包括：

- `src/db/training/read.mjs`
- `src/db/training/write.mjs`
- `tools/sync-training-core.mjs`
- `tools/export-training-markdown.mjs`
- `src/adapters/postgres/archive-repository.pg.mjs`

建议新增一个小模块，例如：

```text
src/db/training/client-factory.mjs
```

职责：

- 解析 DB 配置。
- 创建单个 client 或 pool。
- 可选设置 `application_name`、`connectionTimeoutMillis`、statement timeout。
- 包装 query 观测，不记录 SQL 原文和参数。

### 2. 改造读取并发

当前并行读取逻辑是固定 6 个 client：

```text
training_day / measurement / activity / meal / sleep / body_feedback
```

建议方案：

1. 先用 pool 控制最大连接数，而不是为每个 query 直接创建新 client。
2. 通过 `TRAINING_DB_READ_PARALLELISM` 控制并发 query 数。
3. 如果 pool 不可用或配置为 1，则按现有 fallback 的单连接顺序查询。
4. fallback 日志保留，但只输出错误摘要，不输出连接串。

### 3. SQL 日期范围下推

当前 `dateFrom/dateTo` 会传入 mapper，但 SQL 没有过滤。建议把 `read-queries.mjs` 常量改为 query builder：

```js
buildTrainingDayQuery({ dateFrom, dateTo })
```

每个 `core.*` 主查询都加：

```sql
where ($1::date is null or archived_date >= $1::date)
  and ($2::date is null or archived_date <= $2::date)
```

注意点：

- `BODY_FEEDBACK_QUERY` 当前按 `core.thought.status='active'` 读取全部随想；如果分析只需要 body_feedback 最近窗口，需要先确认业务语义再加过滤。
- `TRAINING_SLEEP_QUERY` 包含 `core.sleep union all archive.training_sleep`，两个分支都要应用同一日期范围，否则 archive fallback 仍会全量扫描。
- `archive.*` 快照读取也要支持日期范围，但历史恢复场景可能需要全量，默认不要改变调用方语义。

### 4. 读取慢查询摘要

写入链路已有 `createObservedClient()` 和 `slowQueries`。读取链路可复用同样字段：

| 字段 | 要求 |
| --- | --- |
| `operation` | 例如 `read.training_day`、`read.core_sleep`、`read.body_feedback`。 |
| `table` | 只允许白名单表名，不记录 SQL 原文。 |
| `durationMs` | 四舍五入毫秒。 |
| `thresholdMs` | 来自 `TRAINING_DB_READ_SLOW_QUERY_MS` 或 `TRAINING_DB_SLOW_QUERY_MS`。 |

输出位置：

- `build:data` / site-build 的 summary。
- `training-analysis` 使用 database snapshot 时的错误或诊断摘要。
- 本地 `maintenance:inspect` 可选显示最近慢查询统计，但不需要第一阶段强制实现。

## 回滚策略

- 保留旧单 client fallback。
- 如果 pool 引发连接泄漏或 too many connections，先把 `TRAINING_DB_POOL_MAX=1`、`TRAINING_DB_READ_PARALLELISM=1`。
- 如果日期下推导致页面数据缺失，先回退 query builder 到全量 SQL，再保留慢查询观测继续排查。
