# 日志事实与瓶颈

## 抽样结论

截图里的 dev/main run 都是成功状态，说明 Telegram、飞书、图片识别入库、随想指令和 deploy dispatch 主链路可用。真正需要优化的是成功 run 的尾部耗时和日志暴露面。

最关键的慢点是同步结束前同步执行的睡眠回填：

```text
dev feishu run 28481129329:
recognition=14100ms, persist=3639ms, sleepBackfill=213372ms, total=231136ms

main feishu run 28483078242:
recognition=13925ms, persist=3907ms, sleepBackfill=80789ms, total=98645ms
```

AI 识别本身在这两次图片 run 中约 10-14s；DB persist 约 3-4s；`sleepBackfill` 才是把成功同步拖到 1.5-4 分钟的主因。

## 已经做好的地方

- `workflow_dispatch` 的 dispatch payload 已改为 runner 临时 event 文件，避免把原始 payload 写入 `$GITHUB_ENV`。
- sync workflow 触发 deploy 时传入 `sync_db_mode=never`、`run_tests=false`，deploy 等待已经不是慢 run 的主因。
- 图片识别已有缓存 key、fallback provider、strict JSON retry、`json_schema -> json_object -> no response_format` 的兼容路径。
- Action summary formatter 已对 summary cell 做 hash/脱敏，问题主要来自绕过 summary 的 raw stdout 和 GitHub env 展示。

## 优先级

| 优先级 | 问题 | 原因 |
| --- | --- | --- |
| 高 | raw Action 日志泄露 chat/source/COS 标识 | 已在 main/dev 成功 run 中复现，且和核心文档的日志安全规则不一致。 |
| 高 | `sleepBackfill` 同步全量扫描 | 单次成功同步可被拖慢 80-213s，影响飞书和 Telegram 图片链路体验。 |
| 高 | 图片 schema 中 `records.sleep` 未必填 | 睡眠字段已经定义但不在 `records.required`，会削弱睡眠图片结构化稳定性。 |
| 中 | 图片字段级校验不足 | 当前可用，但体脂称、睡眠分期、运动字段没有合理性网，容易产生“成功入库但字段错”的隐性问题。 |
| 中 | `TRAINING_DB_READONLY_URL` 在抽样 run 中为空 | 文档和规划已支持只读巡检，但真实 run 未体现只读连接已配置。 |
| 中 | `tools/*` 兼容入口和旧 NDJSON pending 路径 | 不影响当前运行，但会持续放大改代码和测代码的心智成本。 |
| 低 | deploy wait 与耗时观测细化 | deploy 已关闭重复 DB sync/test，不是主瓶颈，可作为后续体验优化。 |
