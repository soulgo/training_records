# 运行速度优化

## 结论

成功同步的主要慢点不是 AI，也不是 deploy，而是同步链路里同步执行的全量睡眠回填。下一轮性能优化应优先处理 `sleepBackfill`，其次再优化 DB 修复入口、deploy wait 和小型 I/O。

## 优先级划分

| 优先级 | 事项 | 代码/日志依据 | 验收重点 |
| --- | --- | --- | --- |
| 高 | `sleepBackfill` 目标日期回填、异步维护或限额保护。 | slow run 中 `sleepBackfill=80789-213372ms`；代码在同步阶段直接执行回填。 | 图片同步不再出现分钟级 `sleepBackfill`。 |
| 中 | 手动 DB 修复阶段拆 timing，并避免默认全量 sleep backfill。 | main 手动 `Sync safe database repairs` 约 2m03s。 | summary 有 phase timing，非显式全量不超过 60s。 |
| 低 | deploy wait 轮询和 summary 细化。 | sync deploy 已传 `sync_db_mode=never`、`run_tests=false`。 | 细分 queue/build/provider deploy，不削弱质量门禁。 |
| 低 | image download/cache read/DB persist 长期观测。 | 单次 run 中这些阶段为秒级，不是主瓶颈。 | 安全输出耗时分布，不暴露 SQL 或图片标识。 |

## 问题 1：`sleepBackfill` 同步全量扫描

当前触发条件：

- 本轮 `storedSleepAny=true` 时默认执行。
- 只有 `TELEGRAM_SYNC_RUN_SLEEP_BACKFILL=false` 才显式关闭。
- 回填函数会查询所有 ready ingest sleep batch，以及 archive 中缺 core sleep 的所有日期，再在一个事务里逐个 `replaceCoreDay()`。

证据：

- `src/app/use-cases/telegram-sync.use-case.mjs:518-525`
- `src/app/use-cases/telegram-sync.use-case.mjs:687-695`
- `src/db/training/write.mjs:481-624`

日志影响：

| run | `recognition` | `persist` | `sleepBackfill` | 结论 |
| --- | ---: | ---: | ---: | --- |
| dev feishu `28481129329` | 14.1s | 3.6s | 213.4s | 回填占同步阶段绝大多数。 |
| main feishu `28483078242` | 13.9s | 3.9s | 80.8s | 同类问题在 main 复现。 |

### 优化方案 A：目标日期回填

让 `backfillCoreSleepFromIngestBatches` 接收 `targetArchivedDates` 或 `targetBatchIds`：

```text
backfillCoreSleepFromIngestBatches({
  targetArchivedDates: [...本轮存入 sleep 的日期],
  sourceChannel: 'telegram_sync' | 'feishu_sync'
})
```

SQL 只查目标日期或目标 batch：

- `ingest.telegram_batch` 加 `archived_date in (...)`。
- `archive.training_sleep` 加 `archived_date in (...)`。
- 没有目标日期时才允许显式维护入口跑全量。

验收目标：

- 图片同步中的 `sleepBackfill` 常态低于 5s。
- 单次飞书睡眠图片成功同步总时长低于 60s。
- 全量 backfill 只由 `maintenance:sync` 或手动 `sync:db` 明确触发。

### 优化方案 B：异步维护化

如果目标日期回填仍可能慢，改为：

1. 同步阶段只把需要回填的日期写入 pending maintenance 表或 result file。
2. 当前聊天回执先返回 `stored` / `pending_backfill`。
3. `sync:db` 或独立 scheduled workflow 消费 pending backfill。

这会牺牲一点“同步后立即可见的睡眠聚合完整度”，但能保证 Telegram/飞书交互延迟稳定。

### 优化方案 C：限额保护

在 A/B 之前也可以先加保护：

- `TRAINING_SLEEP_BACKFILL_MAX_BATCHES`
- `TRAINING_SLEEP_BACKFILL_MAX_MS`
- 超限时返回 `pending_backfill`，不要阻塞主同步。

## 问题 2：手动 DB 修复阶段也需要拆分耗时

截图中 main 手动 run `28482785283` 的 `Sync safe database repairs` 约 2m03s。这个阶段不影响 webhook dispatch，但会影响手动维护体验，也可能掩盖全量扫描问题。

建议：

- `tools/training-maintenance.mjs sync` 每个 phase 输出安全 timing：archive、ingest、markdown、thoughts、sleepBackfill。
- 手动 workflow summary 显示每个 phase 的 rowCounts、durationMs、slowQueries 数量。
- 默认手动 safe repair 不跑全量 sleep backfill，除非显式 `--phase sleep` 或 `--phase all`。

## 问题 3：deploy wait 已优化，但仍可微调

当前 sync 触发 deploy 时已经传：

```text
strict_database_snapshot=true
sync_db_mode=never
run_tests=false
```

这说明 deploy 阶段没有再重复跑 DB sync 和测试。截图中 deploy wait 多在 39-71s，属于次要瓶颈。

可选优化：

- 降低首次轮询等待，让小 deploy 更快完成反馈。
- 在 summary 中区分 queue wait、build duration、provider deploy duration。
- 保持 push/manual deploy 的默认测试，不要为了同步速度削弱主线质量门禁。

## 问题 4：AI 和 DB persist 是次要但可观察

本轮图片 run 中：

- AI schema 识别约 10-14s。
- image download 约 2.5-3.6s。
- cache read 约 1.5s。
- DB persist 约 3.6-3.9s。

建议：

| 阶段 | 优化方向 |
| --- | --- |
| AI | 提高 cache hit 率；评估图片压缩/裁剪是否减少 token 和耗时；保留 fallback。 |
| image download | 避免同一 media group 重复下载；记录安全摘要里的下载耗时分布。 |
| cache read | 给 recognition cache 查询加慢查询摘要，确认是否缺索引。 |
| DB persist | 复用现有 `slowQueries`，把慢 query 计数写入 summary，不输出 SQL。 |

## 性能验收

| 场景 | 目标 |
| --- | --- |
| 飞书睡眠图片同步 | `Sync updates` < 60s，`sleepBackfill` < 5s 或异步 pending。 |
| Telegram 图片同步 | 没有 sleep 全量回填时 < 45s。 |
| 普通文字/随想同步 | `Sync updates` 常态 < 10s。 |
| 手动 safe DB repair | summary 有 phase timing；非显式全量不超过 60s。 |
| deploy wait | 不作为高优先级；保持不重复跑 DB sync/test。 |
