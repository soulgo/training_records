# 第二轮重构优化方案

> 归档说明：本文记录第二轮重构优化方案和阶段状态，不是当前日常维护手册。当前维护入口见 [文档总览](../README.md)。

## 1. 文档目标

本文档用于指导训练记录系统的第二轮重构优化评估与后续实施。读者包括产品经理、架构师、后端工程师、前端工程师、运维维护人员和后续接手项目的开发者。

本轮采用“渐进服务化”路线：不推翻当前 GitHub Actions + Cloudflare Worker + Telegram Bot + PostgreSQL + Hexo 的生产链路，先把代码边界、测试保护和迁移顺序做清楚，再逐步增强 AI、Telegram、数据库和站点展示能力。

本文件的目标不是描述一个理想化大重写，而是给出程序员可以按优先级逐项实现的方案。每个任务都要明确目标、代码范围、禁止事项、验收方式和风险等级，确保后续评估通过后，开发工作可以按文档执行，并尽量做到测试一遍过。

版本记录：

- `1.1.2`：补充 H7 targeted tests 的完成状态，并同步版本到 `1.1.2`。
- `1.1.3`：完成中优先级的 M1/M2/M4/M6，补齐统一 AI provider、prompt/schema 版本化、识别缓存和数据库读取窗口，并同步版本到 `1.1.3`。

本轮文档细化后的核心原则：

- 第一阶段不改生产配置。
- 第一阶段不改 GitHub Actions 工作流触发方式。
- 第一阶段不改 Cloudflare Worker 配置。
- 第一阶段不改 Telegram webhook 协议。
- 第一阶段不改 Telegram 命令语义。
- 第一阶段不改数据库 schema。
- 第一阶段不改现有 npm scripts。
- 所有重构必须可回滚、可测试、可小步合并。

## 2. 现状诊断

### 2.1 当前系统能力

当前仓库已经具备以下能力：

- `训练记录.md` 到 `TrainingSnapshot` 的解析。
- PostgreSQL `core.*` 到 `TrainingSnapshot` 的读取。
- Telegram 图片识别结果优先写 PostgreSQL。
- PostgreSQL 写入失败时，图片 batch 回退写 `训练记录.md`。
- `/thought` 和 `/随想` 支持纯文字、带图、相册、编辑、删除、移动。
- `/analysis` 和 `/分析` 支持基于 `TrainingSnapshot` 生成训练建议并回发 Telegram。
- Cloudflare Worker 校验 Telegram secret，再转发为 GitHub `repository_dispatch`。
- Durable Object `TELEGRAM_ALBUM_BUFFER` 支持相册聚合。
- GitHub Actions 支持测试、站点构建、Telegram 同步、Cloudflare Worker 部署。
- Hexo 站点展示 dashboard、随想、文章和静态页面。
- 测试覆盖 Telegram runner、Cloudflare Worker、数据库 core/archive、dashboard、analysis、parser 等关键路径。

### 2.2 当前代码主要瓶颈

当前系统已经从“静态站点脚本”演变为“小型自动化数据系统”。主要瓶颈不是单点 bug，而是模块边界开始变重：

| 文件 | 当前职责 | 主要问题 |
| --- | --- | --- |
| `tools/telegram-sync.mjs` | Telegram 同步主流程、AI 调用、DB 持久化、fallback、通知 | 应用编排和基础设施混在一起，后续新增命令会继续膨胀 |
| `tools/telegram-sync-lib.mjs` | update 分组、命令解析、识别归一、Markdown 渲染 | 领域逻辑、Telegram 逻辑和 Markdown 输出耦合 |
| `tools/training-analysis.mjs` | summary、意图识别、AI 请求、回复切分 | AI provider 可替换性弱，分析策略难独立测试 |
| `tools/training-db-write.mjs` | ingest、core、thought、transaction、SQL | SQL 与业务合并，repository 边界不清晰 |
| `themes/cactus/layout/dashboard.ejs` | 页面渲染、指标计算、HTML 构造 | EJS 过重，数据 view model 和模板职责未完全分离 |

### 2.3 当前运行速度风险

| 风险 | 影响 | 优先级 |
| --- | --- | --- |
| 图片识别无缓存 | 重跑 workflow 或重复图片会重复消耗 AI 请求 | 中 |
| DB 快照读取全量为主 | 数据增长后 dashboard 构建和分析会变慢 | 中 |
| EJS 内计算较多 | 页面模板维护成本高，测试不够直接 | 低 |
| `source/_data` 每次重写 | 可能产生无意义构建和 diff | 低 |

### 2.4 当前长期维护风险

| 风险 | 影响 | 优先级 |
| --- | --- | --- |
| `tools/` 同时承担 CLI 和业务模块 | 新维护者难判断入口与领域边界 | 高 |
| Telegram 命令解析分散 | 新增 `/summary`、`/plan`、`/补录` 容易影响旧命令 | 高 |
| AI 请求直接拼接 | provider、timeout、schema 校验、错误分类不统一 | 中 |
| pending queue 仍是文件 | GitHub Actions 临时环境下可观测性有限 | 低 |
| Markdown 与 DB 双事实源 | 长期可能出现覆盖和冲突 | 中 |

## 3. 配置冻结清单

### 3.4 Cloudflare `wrangler.toml` 冻结项

第一阶段不得修改 `wrangler.toml` 中的以下内容：

```toml
name = "telegram-sync-dispatch"
main = "cloudflare/telegram-sync-dispatch-worker.mjs"
compatibility_date = "2026-05-14"

[[durable_objects.bindings]]
name = "TELEGRAM_ALBUM_BUFFER"
class_name = "TelegramAlbumBuffer"

[[migrations]]
tag = "v1"
new_sqlite_classes = ["TelegramAlbumBuffer"]
```

冻结原因：

- `name` 影响现有 Worker 部署目标。
- `main` 影响 Worker 入口文件。
- `compatibility_date` 影响 Cloudflare Workers 运行时行为。
- `TELEGRAM_ALBUM_BUFFER` binding 影响相册聚合。
- migration `v1` 影响 Durable Object class 迁移历史。

### 3.5 Cloudflare Worker Settings 冻结项

Cloudflare 控制台中的以下变量和 binding 第一阶段不得要求改名或新增：

- Secret: `GITHUB_TOKEN`
- Secret: `TELEGRAM_SECRET_TOKEN`
- Variable: `GITHUB_OWNER`
- Variable: `GITHUB_REPO`
- Variable: `GITHUB_API_BASE_URL`
- Durable Object binding: `TELEGRAM_ALBUM_BUFFER`

现有默认值保持：

- `GITHUB_OWNER` 未配置时默认 `soulgo`
- `GITHUB_REPO` 未配置时默认 `training_records`
- `GITHUB_API_BASE_URL` 未配置时默认 `https://api.github.com`

- 不修改 `client_payload.telegram_updates` payload 形态。
- 不删除 `tools/`。
- 不删除 `训练记录.md`。
- 不切断 Markdown fallback。
- 不把 `TRAINING_SNAPSHOT_SOURCE` 默认改为 `database`。
- 不新增强制数据库 schema migration。
- 不把 pending store 默认改成 database。
- 不在 build 阶段强依赖 AI API。
- 不迁移到独立后端服务。

这些事项可以作为 Phase 3 或 Phase 4 的独立评审项，但不得和第一阶段代码结构重构混在一起。

## 13. 最终验收标准

完成本轮 v2 优化后，应满足：

- 新维护者能通过 `src/` 目录判断模块职责。
- `tools/*.mjs` 仍然兼容现有 npm scripts。
- GitHub Actions 和 Cloudflare Settings 不需要因为第一阶段重构而调整。
- Telegram 现有命令全部保持兼容。
- 图片识别、随想、分析、pending replay 的测试覆盖稳定。
- AI provider、prompt/schema、错误分类具备扩展点。
- DB repository 边界清晰，SQL 不散落在主编排流程。
- Dashboard 业务计算逐步前移到 view model。
- 每个阶段都有 targeted tests。
- 阶段完成后 `npm test` 和 `npm run build` 通过。
