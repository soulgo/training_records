# 数据库模型

事实来源：`sql/dev-sql/`、`sql/main-sql/` 和 PostgreSQL adapter/read/write 代码。

## Schema 总览

| schema | 作用 | SQL 位置 |
| --- | --- | --- |
| `archive` | Markdown 解析归档、历史快照和历史结构化表 | `sql/<environment>-sql/archive.sql` |
| `ingest` | 外部消息接入、AI 识别、AI 调用日志、pending | `sql/<environment>-sql/ingest.sql` |
| `core` | 当前业务事实源 | `sql/<environment>-sql/core.sql` |
| `monitor` | GitHub Actions run/job/step/failure 与参数健康事实 | `sql/<environment>-sql/monitor.sql`、`src/adapters/postgres/github-action-monitor-repository.pg.mjs` |

## 权限与迁移边界

当前数据库连接统一由 GitHub Settings 中的分支 Secret 注入，不在代码或 SQL 中硬编码环境账号名：

| 角色 / 连接 | 用途 | 边界 |
| --- | --- | --- |
| `training_writer` / `TRAINING_DB_URL` | Telegram / 飞书同步、Action monitor、显式维护和受控 DDL | dev/main 共用同一个写账号；环境隔离由 GitHub Secret 中指向不同数据库的 URL 保证。日常 workflow 只执行自身业务步骤，不运行 schema migration。 |
| `TRAINING_DB_READONLY_URL` 中的环境只读账号 | 站点构建、快照读取、导出、巡检和一致性检查 | 账号名由 dev/main 各自 GitHub Secret 的 URL 决定，源码不假设固定角色名；未配置时读取路径回退 `TRAINING_DB_URL`。 |

运行时代码不包含 schema preflight。结构变更由 `training_writer` 或数据库管理员在目标环境手工执行、验收并重新导出对应 SQL；dev/main 业务数据仍互相独立，当前结构分别以两套环境导出文件为准。

## monitor 表

`monitor` schema 保存 GitHub Actions 自身运行生命周期和系统参数健康检查结果，不保存业务 payload、聊天 ID、图片 key、Prompt、SQL 参数、完整 Action 日志正文、Secret 明文或参数值。Action 监控写入入口是 `tools/report-github-action-status.mjs` 和 `tools/github-action-monitor-server.mjs`；参数健康写入入口是 `tools/check-parameter-health.mjs`。读取入口是站点构建中的 `loadActionMonitorViewFromPostgres()`。

| 表 | 作用 | 写入 / 读取代码 |
| --- | --- | --- |
| `monitor.github_action_runs` | workflow run 主表，每个 `run_id` 一行；保存 workflow、branch、commit、actor、status、conclusion、耗时、URL 和失败摘要。 | `src/adapters/postgres/github-action-monitor-repository.pg.mjs` |
| `monitor.github_action_jobs` | job 明细，每个 GitHub job id 一行；保存 job 状态、结论、runner、labels、耗时和 URL。 | `src/adapters/postgres/github-action-monitor-repository.pg.mjs` |
| `monitor.github_action_steps` | step 明细，每个 `job_id + step_number` 一行；保存 step 名称、状态、结论和耗时。 | `src/adapters/postgres/github-action-monitor-repository.pg.mjs` |
| `monitor.github_action_failures` | 失败摘要表；按 run/job/step 层级记录失败 `failure_key`、结论、摘要和安全上下文。 | `src/adapters/postgres/github-action-monitor-repository.pg.mjs`、`src/app/use-cases/github-action-monitor.use-case.mjs` |
| `monitor.system_config_parameters` | 系统参数健康主表；保存参数名、位置、分类、有效期规则、来源文档和非敏感元数据，不保存参数值。 | `src/adapters/postgres/parameter-health-monitor-repository.pg.mjs` |
| `monitor.system_config_parameter_checks` | 参数健康检查历史；保存 `healthy`、`present`、`invalid`、`missing`、`not_configured`、`unreachable`、`unsupported`、`unknown`、探测类型、耗时、失败分类和可选真实到期日。 | `src/adapters/postgres/parameter-health-monitor-repository.pg.mjs` |

dev 和 main 分别写入自己的 PostgreSQL `monitor.*`；`Action Monitor Report` 同时传入被监控 run 的 branch/environment，读取页面再按当前分支过滤。环境隔离依赖分库和 branch，不要求把业务 payload 写入监控表。

参数健康 registry 位于 `config/parameter-health/dev.json` 和 `config/parameter-health/main.json`。根级 `probes` 定义只读探测，参数通过 `healthProbeKey` 引用；代码不会自动修改生产表。

参数健康相关表的字段边界：

| 表 | 字段边界 |
| --- | --- |
| `monitor.system_config_parameters` | 保存参数身份、`health_probe_key`、`health_check_type`、来源信息和可选到期元数据；probe 的环境变量映射只在 registry 中维护。 |
| `monitor.system_config_parameter_checks` | 保存健康状态、`check_type`、`latency_ms`、`failure_kind`、`observed_expires_at`、证据来源、安全提示和非敏感 details；`last_healthy_at` 在查询时从历史计算。 |

这两张表不保存参数值、value hash、DB URL、token、API key、聊天 ID、COS key 或完整 provider 响应。`source_doc` / `source_code_json` 只用于追溯参数来自哪个文档、workflow 或代码入口。

## 幂等

| 对象 | 幂等依据 |
| --- | --- |
| batch | `persistNormalizedBatch` 对完整 batch JSON 计算 SHA-256 `payloadHash`。 |
| activity | `core-row-writer.pg.mjs` 使用 `sourceChannel + date + time + type + detail` 生成 hash/key。 |
| meal | `core-row-writer.pg.mjs` 使用日期和餐次字段生成 key。 |
| sleep | `core-row-writer.pg.mjs` 使用睡眠字段生成 key。 |
| thought | `core.thought` 有 source identity 唯一索引，定义位于对应环境的 `core.sql`。 |
| trainee profile | `core.trainee_profile.trainee_id`；当前单用户使用 `default`。 |
| action run | `monitor.github_action_runs.run_id`。 |
| action job | `monitor.github_action_jobs.job_id`。 |
| action step | `monitor.github_action_steps` 的唯一约束 `job_id + step_number`。 |
| action failure | `monitor.github_action_failures.failure_key`，写入当前 run 前先删除该 run 的旧 failures 再插入最新失败集合。 |
