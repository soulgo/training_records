# 训练分析逻辑

## 当前流程

`/分析` 不再分别读取多张表后在 Node 中裁剪全量历史。`loadTrainingAnalysisContext()` 使用一个只读 PostgreSQL 连接执行一条带边界的 JSON 聚合 SQL，生成分析上下文后再调用 AI：

```mermaid
flowchart LR
  A[/分析命令] --> B[loadTrainingAnalysisContext]
  B --> C[一个 readonly 连接]
  C --> D[一条近 28 天聚合 SQL]
  D --> E[训练者画像 + 日记录 + 身体反馈]
  E --> F[training-analysis prompt]
  F --> G[训练闭环回复]
```

## 查询边界

- 时间窗口是当前日期向前 27 天，共 28 个自然日，时区按 `Asia/Shanghai` 计算。
- 读取 `core.training_day` 及对应 measurement、activity、meal、sleep 明细，并读取 `body_feedback` 模块随想。
- 使用 `TRAINING_DB_READONLY_URL`；缺少只读数据库配置时直接失败，不回退到写连接执行分析查询。
- Repository 只执行 `SELECT`，不包含 `BEGIN`、`INSERT`、`UPDATE` 或 `DELETE`。

## 训练者画像

分析上下文读取当前 `core.trainee_profile` 中最新的 active 画像：

| 字段 | 用途 |
| --- | --- |
| `timezone`、`birth_date` | 时区与运行时年龄计算；不存冗余 `age`。 |
| `sex_at_birth`、`height_cm` | 仅在确有运动科学计算需要时使用。 |
| `experience_level` | 控制建议难度和术语。 |
| `goal_text` | 作为用户明确目标，不由模型猜测。 |
| `weekly_training_days_target` | 用于训练频率建议。 |
| `profile_json` | 可用器械、长期限制、偏好活动和日程说明等可演进配置。 |

体重、体脂、心率、睡眠、训练量和恢复状态继续来自训练事实表，不复制进画像。

## 输出边界

- 分析以“事实摘要 -> 风险/机会 -> 下一步训练与恢复动作”组织，不把单日波动解释成长期趋势。
- Prompt 不再写死“增肌减腹”；优先使用画像中的 `goalText`，画像为空时才使用运行时默认目标。
- `/分析` 只读并回发，不写入 `core.*`、`ingest.*` 或 Markdown。
