# 常见问题排查

本文按现象给出排查顺序。先看 GitHub Actions 日志，再结合本地命令复现。

## 1. 页面没有更新

排查顺序：

1. 看 GitHub Actions 的 `Deploy GitHub Pages`、`Telegram Sync` 或 `Feishu Sync` 是否运行。
2. 看 workflow 是否生成并上传 `public/`。
3. 本地运行 `npm run build`，确认 `source/_data/training.json` 和 `source/_data/dashboardView.json` 生成。
4. 检查 `TRAINING_SNAPSHOT_SOURCE` 是否切到 `database`，以及数据库是否可读。
5. 如果是 Telegram 或飞书图片同步，查看 Actions summary 中是否有 `ready + stored` 批次；仓库文件无变化时也可能通过 DB-only 内容变化触发站点构建。
6. 检查 `source/CNAME` 和 GitHub Pages 自定义域名设置。

## 2. `npm run build:data` 失败

常见原因：

- `训练记录.md` 不存在或编码异常。
- `TRAINING_SNAPSHOT_SOURCE=database` 但数据库不可用。
- PostgreSQL schema 缺失或账号权限不足。
- archive 写入失败通常只会写入 `runtime/training-db-sync.ndjson`，不应阻断主输出。

处理：

```bash
$env:TRAINING_SNAPSHOT_SOURCE = "markdown"
npm run build:data
```

如果 Markdown 源可正常构建，说明本地兼容输入可用；线上仍应优先修复数据库读取，不要用旧 Markdown 覆盖 `core.*`。

## 3. Telegram 消息没有触发同步

排查顺序：

1. 给 Bot 发送 `/help`，确认 Worker 或同步脚本能回发帮助。
2. 检查 Telegram webhook 是否配置到当前 Worker URL。
3. 检查 Cloudflare Worker 日志是否收到 POST。
4. 检查 Worker 是否返回 `401 unauthorized`。
5. 检查 Worker 是否缺少 `GITHUB_TOKEN`。
6. 检查 GitHub Actions 是否收到 `repository_dispatch: telegram_update`。

如果 Bot 回复“GitHub Action 未能启动”，问题在 Worker 到 GitHub dispatch 之间，优先检查 Cloudflare `GITHUB_TOKEN`、仓库 owner/repo 和 GitHub API 返回码。如果 Bot 回复“GitHub Action 执行失败”，说明 workflow 已启动但某个 Action 阶段失败，直接打开回复里的 run URL 看对应步骤。如果 Bot 回复“部分解析失败”、`pending_replay` 或 `auto_retry`，而 Action 本身是绿色，说明 workflow 执行成功但业务同步存在 partial failure 或待补偿；优先看 Actions summary 中对应 batch 的 `taskStatus`、`failureDisposition` 和 failed message ids。

连续快速发送多批图片时，还要检查相邻 Telegram Sync run 是否有中间一批显示 `cancelled` 且没有 jobs。GitHub Actions 的固定 `concurrency.group` 只保留 1 个 running 和 1 个 pending，同组新 run 会取消旧 pending；Telegram `repository_dispatch` 必须使用包含 `github.run_id` 的唯一并发组，避免第二批图片在进入 runner 前被取消。

相关配置见 [GitHub 与 Cloudflare 配置](../部署维护/GitHub与Cloudflare配置.md)。

## 4. 飞书消息没有触发同步

排查顺序：

1. 检查飞书开放平台事件订阅是否启用 `im.message.receive_v1`，Request URL 是否是已部署的 `feishu-sync-dispatch` Worker URL。
2. 检查飞书开放平台应用是否已开通并发布权限：`im:message`、`im:message.p2p_msg`、`im:message.group_at_msg`、`im:resource`。
3. 检查 Cloudflare Worker 日志是否收到 POST。
4. 如果 Worker 返回 `401 unauthorized`，检查 `FEISHU_ENCRYPT_KEY`、`FEISHU_VERIFICATION_TOKEN` 是否与飞书开放平台事件订阅页一致。
5. 如果 Worker 返回 `missing_github_token` 或 `github_dispatch_failed`，检查飞书 Worker 的 `GITHUB_TOKEN`、`GITHUB_OWNER`、`GITHUB_REPO` 和 GitHub API 返回码。
6. 检查 GitHub Actions 是否收到 `repository_dispatch: feishu_update` 并启动 `Feishu Sync`。
7. 检查 GitHub Secrets/Variables 是否包含 `FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`FEISHU_ALLOWED_CHAT_IDS`。
8. 如果 Feishu Sync 启动后批次为 `ignored unauthorized chat`，把飞书事件里的 `chat_id` 加入 `FEISHU_ALLOWED_CHAT_IDS`。

相关部署步骤见 [飞书通道部署](../部署维护/飞书通道部署.md)。

## 5. Telegram 或飞书图片被跳过

常见原因：

- chat 不在 `TELEGRAM_ALLOWED_CHAT_IDS` 或 `FEISHU_ALLOWED_CHAT_IDS`。
- AI 识别失败或返回为空。
- 识别置信度低于 0.75。
- 同一批次识别出多个不同日期。
- 图片内无日期，Telegram 又没有保留原始文件名。
- 以 `photo` 发送导致 Bot API 拿不到原始文件名。
- 飞书图片当前没有原始文件名日期兜底，截图内需要有可靠日期或可结合消息年份补全的月日。
- 飞书图片下载失败，通常是缺少 `im:resource` 权限、`FEISHU_APP_ID/FEISHU_APP_SECRET` 错误，或应用无法访问该 chat 的消息资源。
- 睡眠截图只有纯时间，没有醒来日期或截图日期，无法按醒来日期减一天归档。

处理：

- 一批只发同一天截图。
- 尽量保证截图画面中有日期。
- 需要依赖文件名日期时，用 Telegram `文件` 发送，不要用 `照片`。
- 飞书图片尽量保证截图画面内有日期。
- 查看 workflow 输出的 batch `reason`、`warnings`、`issues`。
- 如果 Telegram 回复里有 `ai_service` 或“AI 服务失败”，优先查 `AI_API_KEY`、`AI_BASE_URL`、`AI_MODEL`、限流和模型结构化输出支持。
- 如果是 `user_input`，优先检查截图日期、文件名日期、相册是否跨天、chat 是否授权。
- 如果 Actions run 直接 `cancelled` 且没有 jobs，这不是图片识别跳过；按上一节检查 workflow concurrency。

## 6. 睡眠截图识别成功但页面没有数据

排查顺序：

1. 看 Telegram 回复或 workflow JSON 中 `imageType` 是否为 `sleep`。
2. 看 `records.sleep` 是否存在，且是否包含总睡眠、入睡/起床、睡眠阶段或健康指标。
3. 看 `archivedDate` 是否为空；睡眠图需要能从 `wakeTime` 或 `detectedDate` 推出醒来日期。
4. 看 `dateSources.source` 是否为 `sleep_bedtime`；这是睡眠按醒来日期减一天归档的正常信号。
5. 查 `core.sleep` 是否有对应 `archived_date`。
6. 查 `core.training_day` 睡眠汇总字段是否更新。
7. 查 `archive.training_sleep` 是否有对应记录。
8. 如果数据库写入失败，看 `runtime/telegram-sync-pending.ndjson` 是否等待重放。
9. 本地运行 `npm run build:data`，检查 `训练数据解析.md` 是否输出睡眠段落。

如果 `archive.training_sleep` 有数据但 `core.sleep` 缺失，运行 `npm run backfill:core` 后再构建。已有库缺少睡眠健康指标时，先执行 `sql/training_records/sleep_health_metrics.sql`。

如果页面睡眠卡片显示“待比较”，但 action 日志里对应图片已经 `ready + stored`，不要只看 Telegram 回复。继续检查：

1. `core.sleep` 里对应 `archived_date` 的明细是否存在，尤其是 `total_sleep_minutes`、`night_sleep_minutes` 和睡眠阶段字段。
2. `core.training_day` 的睡眠汇总是否存在异常重复值，例如总睡眠等于“总睡眠 + 夜间睡眠”。
3. 构建产物 `source/_data/dashboardView.json` 或 Pages artifact 中睡眠卡片实际读到的分钟数。
4. 图片识别 prompt 是否仍包含 `totalSleepMinutes` 与 `nightSleepMinutes` 不可相加、睡眠阶段必须写入同一个 `records.sleep` 的规则。

当前读模型约定是优先使用 `core.sleep` 明细，只在缺少明细时才回退到 `core.training_day` 睡眠汇总；如果这个约定被破坏，可能出现 action 已入库但页面比较状态异常。

## 7. PostgreSQL 写入失败

表现：

- 图片或随想批次 `persistenceStatus=pending_replay`。
- `runtime/telegram-sync-pending.ndjson` 非空。
- Telegram 或飞书回复中出现 `database` 或“数据库待补偿”。

处理：

1. 检查 `TRAINING_DB_ENABLED=true` 和 `TRAINING_DB_URL`。
2. 检查数据库网络、SSL、账号权限和 schema。
3. 查看 GitHub Actions summary 的 `taskStatus`、`persistenceStatus`、`failureDisposition`、`pending` 和 failed message ids，确认是完全入库、自动重试还是需要人工处理。
4. 数据库恢复后运行 `npm run sync:telegram` 或 `npm run sync:feishu` 重放 pending。
5. 重放成功后 pending 队列会移除对应批次。

## 8. `/分析` 没有回复或回复失败

排查顺序：

1. 确认消息来自白名单 chat。
2. 确认 `AI_API_KEY`、`AI_BASE_URL`、`AI_MODEL` 已配置。
3. 确认 `TRAINING_SNAPSHOT_SOURCE` 对应数据源可读取。
4. 看 Telegram Sync 日志中的 `analysisReplyStatus` 和 `analysisReplyError`。
5. 如果 Bot 已回发“训练分析暂时生成失败”，直接按消息中的原因区分 AI 服务、数据库快照或系统异常。
6. 如果是飞书 `/分析`，看 Feishu Sync 日志中的 reply status，并检查 `FEISHU_APP_ID`、`FEISHU_APP_SECRET` 和应用发送消息权限。

`/分析` 不会写 `训练记录.md`、`source/_posts` 或 PostgreSQL。

## 9. 随想没有出现在页面

排查顺序：

1. 检查 `source/_posts/YYYY-MM-DD-telegram-thought-<id>.md` 或 `source/_posts/YYYY-MM-DD-feishu-thought-<id>.md` 是否生成。
2. 检查 front matter 中 `thought_module` 是否为 `workout`、`misc` 或 `body_feedback`。
3. 检查 tags 是否包含对应模块标签和 `随想`。
4. 运行 `npm run build`。
5. 检查 `themes/cactus/layout/thoughts.ejs` 过滤逻辑是否被修改过。

如果 Telegram 或飞书已回复“随想写入成功，已入库”，但页面没出现，通常是站点构建、Pages 部署或 DB -> Markdown 备份尚未执行。如果回复“已记录，数据库待补偿”，先处理 PostgreSQL pending。

## 10. Markdown 附件随想失败

常见原因：

- 附件不是 `.md` 或 `.markdown`，或 mime type / 文件名无法识别为 Markdown。
- 附件为空，trim 后没有正文。
- 附件声明大小或下载后大小超过 5MB。
- Telegram 文件下载失败，`failureCategory` 通常为 `telegram_api`。
- caption 没有以 `/随想` 或 `/thought` 开头，系统没有进入随想链路。
- 在飞书发送 Markdown 文件；当前 Markdown 文档附件随想只支持 Telegram。

处理：

1. 用 Telegram `文件` 方式发送 Markdown 文档，不要复制为普通消息附件说明。
2. 在文件 caption 写 `/随想`、`/随想 杂七杂八` 或 `/随想 身体反馈`。
3. 确认文件是 UTF-8 编码、非空且不超过 5MB。
4. 看 Telegram 回复或 workflow JSON 里的 `failureReason`，区分超限、空文件和下载失败。
5. 如果入库成功但页面未显示，继续按“随想没有出现在页面”检查 DB -> Markdown 备份和站点构建。

## 11. 消息通道失败分类速查

- `user_input`：输入或发送方式问题，通常改消息、图片日期或 chat 授权即可。
- `ai_service`：AI 平台、模型、网络、限流或 schema 输出问题。
- `telegram_api`：Telegram Bot API、文件下载或消息发送失败。
- `feishu_api` 或飞书相关错误文本：飞书 Open API、图片资源下载或消息发送失败。
- `database`：PostgreSQL 连接、权限、schema 或写入失败。
- `github_action`：GitHub Actions 运行阶段失败，看回复中的 run URL。
- `system_bug`：系统代码未预期异常，需要看 workflow 日志和测试。

## 12. Markdown 备份没有按预期更新

`npm run export:markdown` 严格从数据库导出，不会因为 pending 队列改读旧 Markdown。正常 Telegram/飞书图片 `ready + stored` 成功路径也不会即时改写 `训练记录.md`。

如果数据库里有数据但 Markdown 没更新，这是 DB-only 成功路径的预期；需要看 `.github/workflows/markdown-backup.yml` 是否启用并成功运行。

排查顺序：

- GitHub Variables 中 `MARKDOWN_BACKUP_ENABLED` 是否为 `true`。
- `MARKDOWN_BACKUP_FREQUENCY` 是否符合当天门禁；手动 `workflow_dispatch` 会绕过 enabled/frequency 门禁。
- `MARKDOWN_BACKUP_BRANCH` 是否指向期望分支。
- workflow summary 中是否显示 `Changed: true`，以及是否被 `MARKDOWN_BACKUP_COMMIT=false` 阻止提交。
- 导出失败时优先修复 PostgreSQL 读取或 `core.*` 数据完整性。

## 13. 页面访问异常或 CDN 问题

`soulgo.chat` 通过 Cloudflare 代理（橙云）加速 GitHub Pages。如果页面加载异常，排查顺序：

1. 确认 Cloudflare 代理是否生效：

```bash
curl -sI https://soulgo.chat | grep -E 'server|cf-'
# 期望: server: cloudflare，且有 cf-ray 和 cf-cache-status
```

如果 `server: GitHub.com`，说明代理未生效，检查 Cloudflare Dashboard → DNS 中 CNAME 记录的橙云状态。

2. 确认 SSL/TLS 模式为 **Full (Strict)**。如果设为 Full（非 Strict），可能因为证书校验问题导致间歇性 521/522 错误。

3. 如果部署后页面未更新，可能是 Cloudflare 边缘缓存命中旧内容。手动清缓存：Cloudflare Dashboard → Caching → Purge Everything。

4. 如果出现 522 Connection Timed Out，通常是 Cloudflare 回源 GitHub Pages 超时。检查 GitHub Pages 是否正常（`https://soulgo.github.io` 是否可访问），以及 Cloudflare 是否有区域性故障。

5. 如果 CSS/JS 显示旧样式，是 Cloudflare Cache Rules 中 CSS/JS 的 7 天 Edge TTL 尚未过期。Purge Everything 或 Purge by URL 可立即刷新。

6. Always Online 开启后，即使 GitHub Pages 短暂不可用，Cloudflare 仍会展示上次缓存的页面，访客看到的内容可能略旧但不会白屏。

相关配置见 [GitHub 与 Cloudflare 配置](../部署维护/GitHub与Cloudflare配置.md) 第 8 节。

## 14. 链接或文档失效

文档目录已中文化。新增或移动文档后：

```bash
rg "docs/|docs\\\\" README.md docs
git diff --check
```

优先更新 [文档总览](../README.md) 和项目根 [README](../../README.md)。
