# 常见问题排查

本文按现象给出排查顺序。先看 GitHub Actions 日志，再结合本地命令复现。

## 1. 页面没有更新

排查顺序：

1. 看 GitHub Actions 的 `Deploy GitHub Pages` 或 `Telegram Sync` 是否运行。
2. 看 workflow 是否生成并上传 `public/`。
3. 本地运行 `npm run build`，确认 `source/_data/training.json` 和 `source/_data/dashboardView.json` 生成。
4. 检查 `TRAINING_SNAPSHOT_SOURCE` 是否切到 `database`，以及数据库是否可读。
5. 如果是 Telegram 图片同步，查看 Actions summary 中是否有 `ready + stored` 批次；仓库文件无变化时也可能通过 DB-only 内容变化触发站点构建。
6. 检查 `source/CNAME` 和 GitHub Pages 自定义域名设置。

## 2. `npm run build:data` 失败

常见原因：

- `训练记录.md` 不存在或编码异常。
- `TRAINING_SNAPSHOT_SOURCE=database` 但数据库不可用。
- PostgreSQL schema 缺失或账号权限不足。
- archive 写入失败通常只会写入 `runtime/training-db-sync.ndjson`，不应阻断主输出。

处理：

```bash
$env:TRAINING_SNAPSHOT_SOURCE = "markdown"
npm run build:data
```

如果 Markdown 源可正常构建，再单独排查数据库。

## 3. Telegram 消息没有触发同步

排查顺序：

1. 给 Bot 发送 `/help`，确认 Worker 或同步脚本能回发帮助。
2. 检查 Telegram webhook 是否配置到当前 Worker URL。
3. 检查 Cloudflare Worker 日志是否收到 POST。
4. 检查 Worker 是否返回 `401 unauthorized`。
5. 检查 Worker 是否缺少 `GITHUB_TOKEN`。
6. 检查 GitHub Actions 是否收到 `repository_dispatch: telegram_update`。

如果 Bot 回复“GitHub Action 未能启动”，问题在 Worker 到 GitHub dispatch 之间，优先检查 Cloudflare `GITHUB_TOKEN`、仓库 owner/repo 和 GitHub API 返回码。如果 Bot 回复“GitHub Action 执行失败”，说明 workflow 已启动但某个 Action 阶段失败，直接打开回复里的 run URL 看对应步骤。

相关配置见 [GitHub 与 Cloudflare 配置](../部署维护/GitHub与Cloudflare配置.md)。

## 4. Telegram 图片被跳过

常见原因：

- chat 不在 `TELEGRAM_ALLOWED_CHAT_IDS`。
- AI 识别失败或返回为空。
- 识别置信度低于 0.75。
- 同一批次识别出多个不同日期。
- 图片内无日期，Telegram 又没有保留原始文件名。
- 以 `photo` 发送导致 Bot API 拿不到原始文件名。
- 睡眠截图只有纯时间，没有醒来日期或截图日期，无法按醒来日期减一天归档。

处理：

- 一批只发同一天截图。
- 尽量保证截图画面中有日期。
- 需要依赖文件名日期时，用 Telegram `文件` 发送，不要用 `照片`。
- 查看 workflow 输出的 batch `reason`、`warnings`、`issues`。
- 如果 Telegram 回复里有 `ai_service` 或“AI 服务失败”，优先查 `AI_API_KEY`、`AI_BASE_URL`、`AI_MODEL`、限流和模型结构化输出支持。
- 如果是 `user_input`，优先检查截图日期、文件名日期、相册是否跨天、chat 是否授权。

## 5. 睡眠截图识别成功但页面没有数据

排查顺序：

1. 看 Telegram 回复或 workflow JSON 中 `imageType` 是否为 `sleep`。
2. 看 `records.sleep` 是否存在，且是否包含总睡眠、入睡/起床、睡眠阶段或健康指标。
3. 看 `archivedDate` 是否为空；睡眠图需要能从 `wakeTime` 或 `detectedDate` 推出醒来日期。
4. 看 `dateSources.source` 是否为 `sleep_bedtime`；这是睡眠按醒来日期减一天归档的正常信号。
5. 查 `core.sleep` 是否有对应 `archived_date`。
6. 查 `core.training_day` 睡眠汇总字段是否更新。
7. 查 `archive.training_sleep` 是否有对应记录。
8. 如果数据库写入失败，看 `runtime/telegram-sync-pending.ndjson` 是否等待重放。
9. 本地运行 `npm run build:data`，检查 `训练数据解析.md` 是否输出睡眠段落。

如果 `archive.training_sleep` 有数据但 `core.sleep` 缺失，运行 `npm run backfill:core` 后再构建。已有库缺少睡眠健康指标时，先执行 `sql/training_records/sleep_health_metrics.sql`。

## 6. PostgreSQL 写入失败

表现：

- 图片批次 `persistenceStatus=fallback_markdown`。
- 随想批次 `persistenceStatus=pending_replay`。
- `runtime/telegram-sync-pending.ndjson` 非空。
- Telegram 回复中出现 `database` 或“数据库待补偿”。

处理：

1. 检查 `TRAINING_DB_ENABLED=true` 和 `TRAINING_DB_URL`。
2. 检查数据库网络、SSL、账号权限和 schema。
3. 查看 GitHub Actions summary 的 `persistenceStatus`、`failureDisposition` 和 `pending`，确认是自动重试还是需要人工处理。
4. 数据库恢复后运行 `npm run sync:telegram` 重放 pending。
5. 重放成功后 pending 队列会移除对应批次。

## 7. `/分析` 没有回复或回复失败

排查顺序：

1. 确认消息来自白名单 chat。
2. 确认 `AI_API_KEY`、`AI_BASE_URL`、`AI_MODEL` 已配置。
3. 确认 `TRAINING_SNAPSHOT_SOURCE` 对应数据源可读取。
4. 看 Telegram Sync 日志中的 `analysisReplyStatus` 和 `analysisReplyError`。
5. 如果 Bot 已回发“训练分析暂时生成失败”，直接按消息中的原因区分 AI 服务、数据库快照或系统异常。

`/分析` 不会写 `训练记录.md`、`source/_posts` 或 PostgreSQL。

## 8. `/ai` 没有回复或回答缺数据

排查顺序：

1. 确认消息来自白名单 chat。
2. 检查 AI 配置。
3. 检查 `TELEGRAM_AI_AGENT_ALLOWED_TOOLS` 是否限制了所需工具。
4. 若查询数据库源，确认 `TRAINING_SNAPSHOT_SOURCE` 和数据库配置。
5. 如果回复里提示工具失败，先看 `runtime.get_sync_status`、`training.get_config` 是否被允许。

当前 `/ai` 只调用 MCP 查询和分析类工具，不写训练记录。

## 9. 随想没有出现在页面

排查顺序：

1. 检查 `source/_posts/YYYY-MM-DD-telegram-thought-<id>.md` 是否生成。
2. 检查 front matter 中 `thought_module` 是否为 `workout`、`misc` 或 `body_feedback`。
3. 检查 tags 是否包含对应模块标签和 `随想`。
4. 运行 `npm run build`。
5. 检查 `themes/cactus/layout/thoughts.ejs` 过滤逻辑是否被修改过。

如果 Telegram 已回复“随想写入成功，已入库”，但页面没出现，通常是站点构建或 Pages 部署问题。如果回复“Markdown 已写入，数据库待补偿”，先确认 `source/_posts` 文件存在，再处理 PostgreSQL pending。

## 10. Telegram 失败分类速查

- `user_input`：输入或发送方式问题，通常改消息、图片日期或 chat 授权即可。
- `ai_service`：AI 平台、模型、网络、限流或 schema 输出问题。
- `telegram_api`：Telegram Bot API、文件下载或消息发送失败。
- `database`：PostgreSQL 连接、权限、schema 或写入失败。
- `github_action`：GitHub Actions 运行阶段失败，看回复中的 run URL。
- `system_bug`：系统代码未预期异常，需要看 workflow 日志和测试。

## 11. Markdown 没有按预期更新

`npm run export:markdown` 在检测到 `runtime/telegram-sync-pending.ndjson` 非空时，会优先使用 Markdown 源，避免数据库未补偿时覆盖回退内容。

正常 Telegram 图片 `ready + stored` 成功路径不会默认全量覆盖整份 `训练记录.md`。如果数据库里有数据但 Markdown 没出现整份重导出，这是 V9 以后的预期；需要看目标日期是否做了增量合并，以及页面是否从数据库快照构建。

如果仍怀疑内容被覆盖，先检查：

- pending 队列是否为空。
- 最近一次 `telegram-sync.yml` 是否执行了 export。
- `训练记录.md` 中是否有 `telegram-fingerprint` 注释。

## 12. 链接或文档失效

文档目录已中文化。新增或移动文档后：

```bash
rg "docs/|docs\\\\" README.md docs
git diff --check
```

优先更新 [文档总览](../README.md) 和项目根 [README](../../README.md)。
