# 系统行为手册

本文是用户输入进入系统后的行为事实源。面向开发人员、运维人员、AI Agent 和架构师。

## 行为总则

系统只承认四类用户行为：

| 行为 | 输入 | 主处理结果 |
| --- | --- | --- |
| 图片输入 | Telegram 图片/相册、飞书图片 burst | AI 识别后写入 `core.training_day`、`core.measurement`、`core.activity`、`core.meal`、`core.sleep` |
| 随想输入 | `/随想`、`/thought`、随想编辑、删除、移动、图片附件 | 写入或更新 `core.thought`，图片保存为引用 |
| 分析输入 | `/分析`、`/analysis` | 读取训练快照并回执纯文本分析，不写事实数据 |
| Markdown 输入 | 显式 Markdown 导入命令或维护脚本 | 解析 `训练记录.md` 形态内容并以 `sourceChannel='markdown_import'` 写入 core |

帮助命令、通知、pending replay 和部署任务是运行控制，不是第五类用户业务行为。

## 图片输入

### 输入来源

Telegram 由 `groupTelegramUpdates()` 标准化消息和相册；普通图片成为 `kind: image`，相册按 `media_group_id` 分组。飞书由 `groupFeishuUpdates()` 把 `im.message.receive_v1` 标准化为 Telegram-like update，再复用同一分组逻辑。

证据：

- `src/adapters/telegram/sync-batch-logic.adapter.mjs:133`
- `src/adapters/feishu/sync-batch-logic.adapter.mjs:45`
- `src/app/use-cases/feishu-sync.use-case.mjs:90`

### 识别流程

每张图片逐张调用 AI 识别。`recognizeBatch()` 对 `batch.messages` 做并发 map，每条消息取最后一张 photo，下载为 URL 或 inline data URL，然后调用 `recognizeTelegramImageMessage()`。

识别 Prompt 默认来自 `prompts/telegram-training-image-recognition.md`；结构合同来自 `telegram_training_image` v2 schema。Schema 顶层字段为 `imageType`、`detectedApp`、`detectedDate`、`dateEvidence`、`records`、`confidence`、`warnings`。

证据：

- `src/app/use-cases/telegram-sync/image-processing.mjs:32`
- `src/core/ai/telegram-recognition-schema.mjs:1`
- `prompts/telegram-training-image-recognition.md:1`

### 图片类型

`imageType` 只允许：

- `measurement`
- `workout`
- `nutrition`
- `sleep`
- `unknown`

`unknown` 不写 core。低于 `0.75` 置信度的识别结果会被跳过。

证据：

- `src/core/ai/telegram-recognition-schema.mjs:10`
- `src/adapters/telegram/sync-batch-logic.adapter.mjs:271`
- `prompts/telegram-training-image-recognition.md:134`

### 时间归因

当前实现的图片归档日期规则如下：

1. AI 只能输出截图画面内可靠日期；截图只有月日时，可用消息年份补全年份。
2. 程序会解析 `detectedDate`、体脂测量时间、`dateEvidence`、带图片证据的 warnings。
3. 睡眠图片按醒来时间或 `detectedDate` 前推一天归档。
4. 同一 batch 内识别出的图片归档日期必须一致；多日期会跳过该 batch。
5. 如果图片内没有可靠日期，Telegram document 文件名可作为程序兜底；普通 photo 通常没有原始文件名。
6. 当前未看到“系统接收时间”作为图片归档日期兜底；缺少可靠图片日期和文件名日期时会跳过。

因此，理想优先级“图片内时间 -> 消息时间 -> 系统接收时间”与当前代码不完全一致：消息时间主要用于补全年份，不直接作为归档日期；系统接收时间没有作为图片归档兜底。

### 入库

图片 batch 通过日期、置信度和业务字段校验后，写入 ingest 审计和 core 主数据。核心表包括：

- `core.training_day`
- `core.measurement`
- `core.activity`
- `core.meal`
- `core.sleep`

识别审计写入 `ingest.telegram_batch`、`ingest.telegram_message`、`ingest.telegram_recognition`，AI 调用可 best-effort 写入 `ingest.ai_call_log`。这些表名保留 `telegram` 历史命名，但通过 `source_channel` 区分 Telegram 和飞书。

## 随想输入

### 新增

随想命令由 `groupTelegramUpdates()` 的 command resolver 识别。Telegram 和飞书共享命令语义；飞书先转为 Telegram-like update 再附加 `sourceChannel='feishu'`。

新增随想写入 `core.thought`。主身份是 `(source_channel, source_chat_id, source_message_id)`；`telegram_message_id` 是 legacy 兼容字段。

### 图片附件

随想图片会先经过图片存储边界，再把最终引用保存到 `core.thought.image_refs_json`。没有图片时走 database-only，不强行生成 Markdown 文章。

当前支持两种 provider：

- `github_local`：默认路径，图片写入 `source/images/thoughts/YYYY/MM/`，数据库保存 `/images/thoughts/...`。
- `tencent_cos`：`COS_ENABLED=true` 且 `COS_PROVIDER=tencent_cos` 时启用，图片上传腾讯云 COS，数据库保存完整 `https://{COS_BUCKET}.cos.{COS_REGION}.myqcloud.com/{COS_PATH_PREFIX}/thoughts/...` 公有读 URL。

上传失败时不会写入错误 URL，也不会调用随想持久化；本批次应失败或进入既有补偿语义。上传成功但后续数据库写入失败时，可能产生短期孤儿 COS 对象，pending replay 会使用稳定 key 重试并写入同一 URL。

编辑随想并替换图片时，新图片全部写入成功后才更新 `image_refs_json`。删除或移动随想只更新数据库状态或模块，不硬删除 COS 对象。历史 `/images/thoughts/...` 引用不会迁移，可与新 COS URL 共存。

## 分析输入

分析命令由共享 command resolver 识别，进入 `kind: analysis`。处理流程调用训练分析用例，读取已有结构化快照，生成一段纯文本回复并发回原通道。

分析 Prompt 要求：

- 只输出纯文本。
- 不输出 Markdown 表格或 JSON。
- 1200 字以内。
- 基于结构化证据回答；数据不足时说明暂无足够数据。
- 默认围绕长期目标“增肌减腹”，但必须服从用户问题的时间窗和意图。

分析不写 `core.*` 事实表。

## Markdown 输入

Markdown 导入是显式维护入口，不是普通图片同步成功路径。`importTrainingMarkdownToDatabase()` 调用 `parseTrainingRecord()` 解析 Markdown，然后以 `sourceChannel='markdown_import'` 持久化到 core。

解析规则来自 Markdown 结构：

- 日期段由 `splitDateSections()` 拆分。
- `体脂秤` 块解析 measurement。
- `运动截图记录` 块解析 workout 和 daily summary。
- `饮食截图记录` 块解析 nutrition。
- `睡眠截图记录` 或 `睡眠记录` 块解析 sleep。

## Telegram / 飞书一致性结论

结论：部分一致。

一致部分：

- 飞书通过 adapter 复用 `runTelegramSync()` 主链路。
- 图片识别使用同一套 prompt、schema 和 `recognizeBatch()`。
- batch 分析、置信度、日期校验、core 写入规则共享。
- 随想、分析、帮助命令复用共享命令语义。

平台差异：

- Telegram 用 Bot API 和 secret token；飞书用飞书事件、token/sign/envelope。
- Telegram 相册靠 `media_group_id`；飞书图片 burst 按同 chat 3 秒窗口聚合。
- Telegram 图片可用 document 文件名做程序日期兜底；飞书图片当前没有同等文件名兜底。
- Telegram 支持 `.md` / `.markdown` 文档附件随想；飞书当前不支持。
- 回执和图片下载 API 不同。

证据：

- `src/app/use-cases/feishu-sync.use-case.mjs:90`
- `src/adapters/feishu/sync-batch-logic.adapter.mjs:147`
- `src/app/use-cases/telegram-sync/image-processing.mjs:32`

## AI 风险边界

### 幻觉风险

Prompt 已明确禁止 AI 补数据、猜日期、用历史记录补字段。代码还会用 schema、置信度、日期和业务规则二次拦截。残余风险在于：AI 仍可能把不可见内容写成结构化字段，因此所有新增字段必须先进入 prompt fixture、schema 和写库测试。

### 结构漂移

当前存在两个需要优先修正的结构漂移点：

1. fallback prompt 只列出 `measurement`、`workout`、`nutrition`、`unknown`，漏掉 `sleep`。
2. schema 定义了 `records.sleep`，但 `records.required` 未包含 `sleep`；这让“睡眠截图必须输出 records.sleep 全字段”的 prompt 约束与 schema 必填集合不完全一致。

### Prompt 超能力

当前最明显的超能力风险是时间规则：文档或目标中若声称系统会使用“系统接收时间”作为图片归档日期兜底，会超过当前实现。代码实际在无可靠图片日期和无文件名日期时跳过 batch。

## 维护规则

1. 行为变化先改代码和测试，再更新本文。
2. Prompt 字段变化必须同步 schema、写库映射和数据模型文档。
3. 文档只描述当前事实，不把规划或历史讨论写入主结构。
4. 同一个事实只允许一个主文档；其它文档链接到本文。
