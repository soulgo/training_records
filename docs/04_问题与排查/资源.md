# CPU、内存与资源

## 现象

- AI 识别耗时过长。
- 图片下载失败或超时。
- Node 进程在 Actions 中异常退出。
- 同步处理大量图片时不稳定。

## 原因

- `AI_CONCURRENCY` 设置过高。
- `AI_TIMEOUT_MS` 或识别 fallback timeout 不合适。
- 单图下载大小超过 `MAX_IMAGE_DOWNLOAD_BYTES`。
- Actions runner 资源有限。

## 日志特征

- `timeout`
- `ETIMEDOUT`
- `fetch failed`
- `AI recognition request failed`
- `maxDownloadBytes`

## 排查步骤

1. 查并发归一：`src/app/use-cases/message-sync-env.mjs`（`normalizeAiConcurrency`）。
2. 查 AI timeout：`src/adapters/ai/openai-compatible.adapter.mjs:7`。
3. 查图片下载大小：`src/app/use-cases/message-sync.use-case.mjs`（`MAX_IMAGE_DOWNLOAD_BYTES`）、`src/app/use-cases/feishu-sync.use-case.mjs`。
4. 查 Actions summary 中 `timingsMs`。

## 主备 AI 切换链路（识别失败定位）

图片识别配置了主 AI + 备 AI 兜底，逻辑在 `src/app/use-cases/image-recognition-provider.mjs`（`requestRecognitionWithProviderFallback`）：

- 主 AI（`AI_MODEL`，超时 `AI_TIMEOUT_MS`）先按 `openai-compatible.adapter.mjs` 的 `fetchWithRetry` 最多重试 3 次（429/5xx 与网络错误可重试）。
- 主 AI 重试耗尽后，自动切到备 AI（`TELEGRAM_RECOGNITION_FALLBACK_*`，超时 `TELEGRAM_RECOGNITION_FALLBACK_TIMEOUT_MS`），同样最多 3 次。
- **只有主备都失败**才向用户返回 `解析失败：AI 服务失败：AI recognition request failed`（文案见 `message-sync/status.mjs`）。

区分报错文案定位失败段：

- `AI recognition failed with HTTP 500: upstream error ...` —— 服务商上游故障（快速失败），提高超时无效，靠重发或备 AI 兜底。
- `AI request timed out after Nms` —— 模型生成超时，提高对应超时有效。睡眠截图字段密集（schema 26 个必填字段），生成较慢，最易超时。
- 用户只看到 `AI recognition request failed`、workflow 仍为绿色 —— 识别失败是软失败（图片标记 skipped/入重试队列，进程 exit 0），业务失败只体现在通知文案，不影响 Action conclusion。

已识别成功的图有缓存（`TELEGRAM_RECOGNITION_CACHE_ENABLED`），后续同步命中缓存 `recognition` 耗时约 1ms；只有首次真调用 AI 才会撞上服务商故障，「重发一次」通常即可恢复。

### 案例（2026-07-15）

飞书睡眠图同步失败：主 AI `gpt-5.4-mini` 连续 3 次 HTTP 500 上游故障 → 切备 AI `kimi-k2.6` 又连续 3 次 30s 超时耗尽，单图识别耗时约 102s 后返回失败。根因是服务商偶发 500（重发已恢复）叠加备 AI 超时（30s）比主 AI（45s）还短。修复：`AI_TIMEOUT_MS` 45s→60s、`TELEGRAM_RECOGNITION_FALLBACK_TIMEOUT_MS` 30s→90s。

## 解决方案

- 降低 `AI_CONCURRENCY`。
- 增加或修正 `AI_TIMEOUT_MS`、`TELEGRAM_RECOGNITION_FALLBACK_TIMEOUT_MS`（当前 dev/main 共用值：主 60000ms、备 90000ms）。备 AI 是最后一道防线，其超时应不小于主 AI。
- 对超大图片改用更小文件或配置 `MAX_IMAGE_DOWNLOAD_BYTES`。
- 服务商上游 HTTP 500 属临时故障，先重发一次验证；若某模型频繁 500 再考虑更换主模型。

## 预防措施

- 默认并发保持小值。
- 大批量导入前先在 dev 环境验证。
- 不在 Worker 中做重型 AI 或图片上传，重活放在 GitHub Actions Node 进程。
