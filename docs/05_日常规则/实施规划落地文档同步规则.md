# 实施规划落地文档同步规则

本规则定义一次性分析、目标、方案、Checklist 和 TDD 过程完成后，如何把仍然有效的事实同步进长期文档。目标是只维护当前事实，不让已完成规划形成第二套系统说明。

## 1. 长期文档分工

| 内容 | 目录 |
| --- | --- |
| 当前环境配置 | `docs/01_系统配置/` |
| 当前业务和运行逻辑 | `docs/02_系统核心逻辑/` |
| 当前问题排查 | `docs/04_问题与排查/` |
| 长期开发和维护规则 | `docs/05_日常规则/` |
| 版本变更摘要 | `CHANGELOG.md` |
| 实施过程与历史背景 | Git 提交、PR、任务记录和代码 diff |

仓库不长期保留已完成规划的重复副本。规划完成后，读者应只依赖当前 docs 操作系统。

## 2. 完成后的必做动作

1. 从实际代码、workflow、SQL、配置和运行结果确认最终实现，而不是从原方案反推。
2. 将仍有效的配置事实写入 `01_系统配置`。
3. 将当前业务流程、数据流、数据库读写和不变量写入 `02_系统核心逻辑`。
4. 将新增或改变的故障场景写入 `04_问题与排查`。
5. 将可重复执行的新约束写入 `05_日常规则`。
6. 更新 `docs/README.md`、所属目录 README 和根 README 的必要导航。
7. 在 CHANGELOG 记录显著的 Added / Changed / Removed / Fixed。
8. 删除已完成的一次性规划、过程报告、TDD 记录和验收副本；需要追溯时使用 Git 历史。

## 3. 不能直接复制的内容

- 被实现否定的备选方案和临时猜测。
- “计划将要”“建议未来”“可以考虑”等未落地描述。
- 只适用于实施过程的命令、Checklist 和分阶段状态。
- 旧路径、旧变量、旧 workflow、旧表名和旧兼容层。
- 没有源码、SQL、配置或运行证据支撑的结论。
- Secret、连接串、聊天 ID、图片 key、payload 或完整日志正文。

## 4. 完成标准

```text
[ ] 实际改动面已经从代码、workflow、SQL 和配置确认。
[ ] 当前配置事实已进入 01_系统配置。
[ ] 当前核心逻辑已进入 02_系统核心逻辑。
[ ] 当前排查方式已进入 04_问题与排查。
[ ] 长期规则已进入 05_日常规则。
[ ] README 导航和 CHANGELOG 已更新。
[ ] 已完成的一次性过程文档已删除。
[ ] 没有 Secret 明文，也没有混写 dev/main 业务数据。
[ ] git diff --check、相关测试和站点构建通过。
```
