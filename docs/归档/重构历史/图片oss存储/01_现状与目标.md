# 01 现状与目标

> 状态：已实现。v1.3.1 已完成腾讯云 COS 随想图片存储扩展；本文件保留实施前现状、目标和设计依据。当前系统事实以 `docs/` 顶层正式文档和 `04_实施结果与验收报告.md` 为准。

## 目标方案（已定）

随想图片从「写 Git 仓库」迁移到「腾讯云 COS」：

- 桶权限：**私有写 / 公有读**（不可变约束，见 02）。
- 上传：在 GitHub Action 内用腾讯云 COS SDK 上传。
- 引用：数据库 `core.thought.image_refs_json` 保存**完整公有读 URL**。第一阶段因自有域名未备案，`COS_DOMAIN` 使用腾讯云 COS 默认公网域名，不使用自定义域名。
- 展示：Markdown `photos` 与站点页面直接使用该 URL，浏览器公网访问。

不选私有桶 + 预签名 URL 的原因：`image_refs_json` 与 Markdown `photos` 都是**静态永久字符串**，COS 预签名 URL 强制带 `Expires`，无法生成永久有效签名；私有桶会导致已落库 URL 整批失效且无刷新层。因此唯一标准是**公有读**。

## 实施前现状

实施前，随想图片存储在 GitHub 仓库的 `source/images/thoughts/YYYY/MM/` 下，页面访问路径是 `/images/thoughts/YYYY/MM/...`。数据库事实源是 `core.thought.image_refs_json`，Markdown 备份中的 `photos` 来自数据库快照的 `thought.imageRefs`。

当时代码还没有腾讯云 COS、OSS 或对象存储实现。v1.3.1 已新增 `cos-nodejs-sdk-v5` 和图片存储 adapter；实施结果见 `04_实施结果与验收报告.md`。

## 当前图片保存位置

随想图片写入位置由 `tools/telegram-thoughts.mjs` 决定：

- 本地仓库路径：`source/images/thoughts/{year}/{month}/`
- 文件名：`{date}-{channelSlug}-thought-{sourceMessageId}-{index}{extension}`
- 公开路径：`/images/thoughts/{year}/{month}/{imageFileName}`

关键实现：

- `writeThoughtImageArtifacts()` 调用 `writeThoughtImageFiles()` 写图片。
- `writeThoughtImageFiles()`（`telegram-thoughts.mjs:424-468`）下载外部平台图片后执行 `writeFile(outputPath, file.data)`。
- `channelSlug` 根据 `message.sourceChannel` 区分 `telegram` 和 `feishu`。

## 当前数据库记录方式

随想事实记录保存在 `core.thought`。与图片相关字段：

| 字段 | 类型 | 当前用途 |
| --- | --- | --- |
| `markdown_path` | `text` | Markdown 兼容层路径 |
| `image_refs_json` | `jsonb NOT NULL DEFAULT '[]'` | 有序图片引用清单 |
| `status` | `text NOT NULL DEFAULT 'active'` | `active` 或 `deleted` |
| `deleted_at` | `timestamptz` | 删除时间 |

SQL 注释已明确：`image_refs_json`「当前为 /images/thoughts/...，**后续可切换为 OSS object key 或 URL**」。该字段已为完整 URL 留出语义空间。

实际写入路径：

```text
handleThoughtSyncBatch()
-> writeThoughtArtifact()
-> attachThoughtStorageMetadata()
-> PostgresThoughtRepository.persistMirror()
-> persistThoughtToCore()
-> core.thought.image_refs_json
```

`thought-repository.pg.mjs` 关键契约：

- 新增随想：`imageRefs: batch.thought?.storage?.photoPaths ?? []`
- 编辑 / 移动：`imageRefs: ... ?? null`
- SQL（`persistThoughtToCore`，line 273-276）：`image_refs_json = case when $11::jsonb is null then core.thought.image_refs_json else excluded.image_refs_json end` → **传 null 保留旧值，传数组（含 `[]`）整体覆盖**。

## 当前 Markdown 引用方式

Markdown 备份由数据库导出。`tools/export-training-markdown.mjs`：

1. `buildTrainingSnapshot()` 读数据库快照。
2. `renderThoughtPost()`（line 236-240）将 `thought.imageRefs` 原样写入 front matter `photos`：

```js
for (const photoPath of thought.imageRefs) {
  lines.push(`  - ${photoPath}`);
}
```

读取侧：`read-queries.mjs:193` 查 `image_refs_json` → `read-mapper.mjs:365` 映射 `imageRefs` → 导出层原样透传。**不拼域名、不解析 provider**。

因此无论 `image_refs_json` 存的是 `/images/...` 还是 `https://...`，导出层都能原样输出。这就是「不改 schema、不改导出层」的代码基础。

## 当前同步链路

```text
Telegram / 飞书
-> Cloudflare Worker（仅 webhook 接入 / 缓冲 / 队列 / dispatch）
-> GitHub Actions sync.yml / sync-dev.yml
-> npm run sync:telegram | npm run sync:feishu
-> runMessageSync()
-> 图片下载 / AI 识别 / 随想处理
-> PostgreSQL core.* / ingest.*
-> Markdown backup / Pages deploy
```

飞书通道注入 `sourceChannel: 'feishu'` 后复用 Telegram 主同步管线，因此两通道最终都进入同一个 `writeThoughtImageArtifacts()` 与 `core.thought.image_refs_json`。

## 当前约束

- **域名约束**：当前自有域名未备案，腾讯云 COS 不能绑定自定义源站域名或 CDN 加速域名作为 `COS_DOMAIN`。第一阶段必须使用默认 COS 域名，格式为 `https://{COS_BUCKET}.cos.{COS_REGION}.myqcloud.com`。
- **部署与传输约束**：系统同步和部署运行在 GitHub Actions / GitHub Pages，图片存储在腾讯云 COS。上传链路是 GitHub Actions runner 公网访问腾讯云 COS；浏览链路是用户浏览器直接访问 COS 公有读 URL，GitHub Pages 不代理图片流量。
- **性能边界**：第一阶段目标是减少 Git 仓库图片膨胀和 Pages 构建负担，不保证图片访问延迟优于 GitHub Pages 本地图片。若后续实际访问延迟不可接受，再评估已备案域名 + CDN 或 COS 全球加速。

## 当前问题

当前图片存储职责落在 Git 仓库：

- 同步时图片写入 `source/images/thoughts`。
- Actions 需要提交图片文件。
- Markdown backup 也检测 `source/images`。
- Pages 构建依赖仓库中的图片文件。

长期运行后：Git 仓库膨胀；clone/checkout 变慢；Actions diff/commit/push 成本变高；Pages 构建变慢；图片生命周期无法对象存储级精细管理。

## 可保留的设计资产

- PostgreSQL 已是事实源。
- Markdown 已是派生备份。
- 双通道已共享消息同步主编排。
- `core.thought.image_refs_json` 已是图片引用的唯一事实字段。
- SQL 注释已为完整 URL 留出语义空间。
- dev/main 已通过 workflow、数据库 secret、Worker vars/ref 做环境隔离。

这些资产决定了 COS 改造只需替换「图片 artifact 存储边界」，不重写 Telegram、飞书、AI 或 Markdown 导出链路。
