# 03 配置安全与容灾

> 状态：已实现。v1.3.1 已接入 `COS_*` / `DEV_COS_*` workflow 配置、默认域名校验、dev/main 隔离校验和上传统计；当前正式运维入口见 `docs/部署运维/部署运维.md#腾讯云-cos-图片存储`。

## 配置总则

COS 上传发生在 GitHub Actions 内，因此 COS 凭据和环境参数配置在 **GitHub Settings**，不进 Cloudflare Worker、不进代码、不进 `repository_dispatch` payload。

dev / main 必须完全独立：

- 独立 SecretId / SecretKey（独立 CAM 子账号）。
- 独立 Bucket。
- 独立路径前缀。
- 独立访问域名。第一阶段使用两个 bucket 各自的 COS 默认公网域名；不要配置自定义域名。

延续项目现有隔离方式（`TRAINING_DB_URL` / `DEV_TRAINING_DB_URL`、`TELEGRAM_BOT_TOKEN` / `DEV_TELEGRAM_BOT_TOKEN` 等）。

## 域名策略（当前未备案域名）

当前自有域名未备案，腾讯云 COS 无法配置自定义源站域名或 CDN 加速域名。因此第一阶段的标准做法是：

- `COS_DOMAIN` 使用 main bucket 默认公网访问域名：`https://{COS_BUCKET}.cos.{COS_REGION}.myqcloud.com`。
- `DEV_COS_DOMAIN` 使用 dev bucket 默认公网访问域名：`https://{DEV_COS_BUCKET}.cos.{DEV_COS_REGION}.myqcloud.com`。
- 不配置 `img.soulgo.chat`、`img-dev.soulgo.chat` 这类自定义域名。
- 不接腾讯云 CDN；CDN 域名同样会涉及域名备案和证书配置，不属于第一阶段。
- 数据库保存完整默认域名 URL。未来域名备案后，如要切到自定义域名，需要做一次 URL 迁移或兼容映射，不能只改环境变量，因为历史 `image_refs_json` 已保存旧完整 URL。

默认域名拼接规则：

```text
COS_DOMAIN = https://{COS_BUCKET}.cos.{COS_REGION}.myqcloud.com
public_url = {COS_DOMAIN}/{COS_PATH_PREFIX}/thoughts/{yyyy}/{MM}/{filename}
```

示例：

```text
https://training-images-prod-1250000000.cos.ap-shanghai.myqcloud.com/main/thoughts/2026/06/2026-06-25-telegram-thought-700-1.jpg
```

备案完成后的后续选项：

1. 给 `img.soulgo.chat` / `img-dev.soulgo.chat` 配置 COS 自定义源站域名或 CDN 加速域名。
2. 新 URL 先切环境变量，新图片写新域名。
3. 历史 URL 是否迁移需单独评估：直接 SQL 批量替换可行，但必须先确认新域名访问、HTTPS 证书、缓存策略和回滚方案。

## 参数获取指南（腾讯云 COS 准备顺序）

按以下顺序在腾讯云准备资源，拿到上述参数：

1. **确认 APPID**：登录腾讯云 → 右上角账号 → **账号信息** → APPID（10 位数字）。每个 bucket 名为 `自定义名-{APPID}`。
2. **创建存储桶**：COS 控制台 → **存储桶列表 → 创建存储桶**。
   - 名称：如 `training-images-prod-{APPID}`（main）、`training-images-dev-{APPID}`（dev）。
   - 所属地域：记下 region（如 `ap-shanghai`），即 `COS_REGION`。
   - 访问权限：选 **公有读私有写**（对应本方案桶 ACL）。
   - 创建后桶名（含 APPID）即 `COS_BUCKET`。
3. **创建 CAM 子账号并授权**：访问管理 CAM 控制台 → **用户 → 用户列表 → 新建用户**（main/dev 各一个，类型选「可访问资源并接收消息」）。
   - 为子账号按「最小权限（CAM）」段授予策略（限定到对应 bucket + prefix）。
   - 进入子账号详情 → **API 密钥 → 新建密钥**，得到 `SecretId` 和 `SecretKey`（SecretKey 仅显示一次，立即复制）。
4. **确定默认访问域名**：不要配置自定义域名。按 `https://{COS_BUCKET}.cos.{COS_REGION}.myqcloud.com` 拼出 main 的 `COS_DOMAIN`，按 `https://{DEV_COS_BUCKET}.cos.{DEV_COS_REGION}.myqcloud.com` 拼出 dev 的 `DEV_COS_DOMAIN`。
5. **配置 CORS（建议）**：COS 控制台 → 桶 → **安全管理 → 跨域访问 CORS 设置**。见下方「CORS 建议配置」。
6. **录入 GitHub**：main 参数录入 `COS_*` Secret/Variable，dev 参数录入 `DEV_COS_*`（位置见上两节表头）。

> APPID 本身不是 GitHub 参数，但它决定 bucket 名格式；不要把 APPID 单独存为 Secret。

## CORS 建议配置

如果图片只是 `<img src="...">` 展示，浏览器通常不要求 CORS；但后续若前端需要 canvas、图片尺寸探测、懒加载库读取响应头，缺 CORS 会带来排障成本。建议第一阶段就配置只读 CORS：

| 配置项 | main 建议值 | dev 建议值 | 说明 |
| --- | --- | --- | --- |
| 来源 Origin | `https://soulgo.chat` | dev 站点域名，如 Cloudflare Pages dev 域名 | 不用 `*`，避免无意义放宽 |
| Methods | `GET`, `HEAD` | `GET`, `HEAD` | 页面只读图片 |
| Allowed-Headers | `*` 或空 | `*` 或空 | 若控制台要求填写，用 `*` |
| Expose-Headers | `ETag`, `Content-Length`, `Content-Type` | 同 main | 便于调试和后续校验 |
| Max-Age | `3600` | `3600` | 缓存预检结果 |

不要在 CORS 中开放 `PUT`、`POST`、`DELETE`。上传发生在 GitHub Actions 的 Node SDK，不依赖浏览器 CORS。

## 其他 workflow 是否需要 COS 配置

- **markdown-backup.yml**：第一阶段不需要。它只从数据库读 `image_refs_json` 原样写 Markdown，不上传图片，不需要 COS Secret。
- **deploy-pages.yml**：第一阶段不需要。Pages 构建只消费 Markdown 和数据库快照，图片由浏览器直接访问 COS URL，站点不拼 URL。
- **Cloudflare Worker**：第一阶段不需要。对象存储上传不在 Worker 发生，COS 凭据不进 `wrangler.toml` 或 Worker Secrets。

## 配置校验规则（fail fast）

启用 COS 时（`COS_ENABLED=true`）启动必须校验，任一不满足直接失败：

- `COS_SECRET_ID` 非空。
- `COS_SECRET_KEY` 非空。
- `COS_BUCKET` 非空。
- `COS_REGION` 非空。
- `COS_DOMAIN` 非空且以 `https://` 开头。
- 当前未备案域名阶段，`COS_DOMAIN` 应匹配默认域名格式：`https://{COS_BUCKET}.cos.{COS_REGION}.myqcloud.com`。若填入自定义域名，必须显式确认域名已备案并已完成 HTTPS 配置。
- `COS_PATH_PREFIX` 非空，且不含 `..`、反斜杠、前导斜杠。

dev 还应校验：

- `DEV_COS_BUCKET` 不等于 `COS_BUCKET`。
- `DEV_COS_DOMAIN` 不等于 `COS_DOMAIN`。
- `DEV_COS_DOMAIN` 应匹配 `DEV_COS_BUCKET` 与 `DEV_COS_REGION` 拼出的默认域名。

## COS SDK 使用要点

依赖包：`cos-nodejs-sdk-v5`（腾讯云官方 Node.js SDK，npm 安装 `npm i cos-nodejs-sdk-v5`）。

### 客户端构造

`SecretId` / `SecretKey` 是构造参数；`Bucket` / `Region` 是**每请求参数**（不在构造时传入）：

```js
import COS from 'cos-nodejs-sdk-v5';

const cos = new COS({
  SecretId: env.COS_SECRET_ID,
  SecretKey: env.COS_SECRET_KEY,
});
```

### API 风格：回调式，需 promisify

SDK 为回调式 `function(err, data)`，**不返回 Promise**。adapter 内建议统一用 `util.promisify` 或手写 Promise 包装，避免回调地狱：

```js
import { promisify } from 'node:util';
const putObject = promisify(cos.putObject.bind(cos));
const headObject = promisify(cos.headObject.bind(cos));
```

### PutObject（上传）

```js
await putObject({
  Bucket: env.COS_BUCKET,        // 含 APPID，如 training-images-prod-1250000000
  Region: env.COS_REGION,        // 如 ap-shanghai
  Key,                           // 稳定 key，见 02「推荐对象路径」
  Body: imageItem.data,          // Buffer / Uint8Array
  ContentType: inferContentType(imageItem.extension),  // image/jpeg 等
});
// 成功无 err；返回 data 含 ETag，可记录用于一致性校验
```

### HeadObject（幂等校验 / 超时判定）

```js
try {
  const data = await headObject({ Bucket, Region, Key });
  // 对象存在 → 视为已上传成功，跳过 PutObject
  // 可选：用 data.headers['content-length'] / data.headers['content-type'] 校验一致性
} catch (err) {
  if (err.statusCode === 404) {
    // 对象不存在 → 需要上传
  } else if (err.statusCode === 403) {
    // 权限问题 → fail，不应静默重试
  } else {
    throw err;  // 其他错误（网络等）→ 交给上层重试
  }
}
```

> 注意 404 在 `err.statusCode`，不在 `data`。这是 SDK 回调式 API 的特性：存在则 `data` 有值，不存在则 `err.statusCode===404`。

### 不使用的 SDK 能力

- 不用 `cos.sliceUploadFile`（分片上传）：随想图片是小文件，`putObject` 足够。
- 不用 `cos.deleteObject`：第一阶段不删对象，CAM 也不授权 `cos:DeleteObject`。
- 不用 `getAuthorization` 临时密钥模式：直接用长期 SecretId/SecretKey（已通过 CAM 限权到单桶 + 三权限）。

## 最小权限（CAM）

main 和 dev 使用不同 CAM 子账号。

### main 权限

限定在 main bucket 和 main prefix，仅授：

```text
cos:PutObject
cos:HeadObject
cos:GetObject
```

第一阶段不做删除，**不授予 `cos:DeleteObject`**。

### dev 权限

限定在 dev bucket 和 dev prefix，同样三权限。dev 不应拥有 main bucket 写权限。

## 桶权限与运维红线（不可变）

- **桶 ACL = 私有写 / 公有读**（bucket 公有读权限作用于对象读取）。
- 运维红线：**禁止将桶改为私有读**。一旦改私有读，所有已落库 `image_refs_json` URL 会整批失效，且无预签名刷新层可恢复。
- 建议在腾讯云 COS 控制台为该桶设置「禁止修改 ACL」的告警或 CAM 限制，防止误操作。
- 第一阶段 `COS_DOMAIN` 使用 COS 默认 HTTPS 域名，不配置自定义域名。
- 自定义域名只有在域名备案完成后才允许作为后续变更；切换前必须先验证 HTTPS 证书、访问、CORS、缓存和历史 URL 迁移策略。

## 密钥轮换流程

GitHub Secrets 支持更新值，但需规范流程避免「换了密钥但 COS 端旧密钥仍有效」的窗口：

```text
1. 在腾讯云 CAM 新建一对子账号 SecretId/SecretKey。
2. 更新 GitHub Secrets（COS_SECRET_ID / COS_SECRET_KEY，dev 同理 DEV_*）。
3. 在 dev 发送一条图片随想，验证上传成功、URL 可公有读访问。
4. 验证通过后，在腾讯云 CAM 禁用并删除旧 SecretKey。
5. 观察 dev/main 各一次同步无 403/401。
```

轮换期间不修改代码、不修改 workflow。

## 开关策略

显式开关 `COS_ENABLED=true|false`：

- `false`：沿用当前本地 `source/images` 写入（provider = github_local）。
- `true`：上传 COS，数据库保存 COS URL。

回滚时只需关闭开关并重新运行同步；**已写入数据库的 COS URL 继续可访问**（桶保持公有读）。

## 风险总览与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| COS 上传失败（4xx/5xx） | 新随想图片不能生成 URL | 重试有限次；失败则不写 DB，batch 失败或 pending，通道通知 |
| GitHub Actions 到 COS 网络慢 | 同步耗时变长，可能误判为同步卡死 | adapter 记录上传耗时；小批量有限并发；设置单对象超时；summary 输出上传数量和耗时 |
| 网络超时（客户端超时但服务端已写） | 上传状态不确定 | 稳定 key + HeadObject 校验；存在视为成功，不存在则重试 |
| 用户浏览器访问 COS 默认域名慢 | 页面图片加载慢，但 HTML 不受影响 | 首阶段接受；验收记录图片加载 P95；必要时备案后引入自定义域名/CDN/全球加速 |
| 默认 COS 域名被误换成未备案自定义域名 | URL 无法访问或 COS 配置失败 | fail fast 校验域名格式；文档明确未备案阶段只用默认域名 |
| Secret 失效 / CAM 权限收窄 | 全部 COS 上传失败 | fail fast，workflow fail，通知通道，保留 `COS_ENABLED=false` 旧链路 |
| DB 写入失败 | COS 已有对象但事实未落库 | 进入现有 pending replay，接受短期孤儿对象 |
| Markdown 生成失败 | 备份和页面可能未更新 | 不回滚 DB 的 COS URL；修复后重新 export |
| GitHub Action 失败 | 同步链路中断 | 依赖现有 Action summary 和失败通知 |
| 主/备 AI 并发或 replay | 重复处理同一 batch | COS key 只由稳定业务身份决定，重复写同一对象，幂等 |
| 图片重复上传 | COS 重复对象 | 稳定 key，PutObject 覆盖或 HeadObject 跳过 |
| dev/main 配错 | 污染生产/开发图片 | 独立 bucket + 独立 secret + 启动校验 |

## 关键失败模式

### COS 上传失败

```text
上传失败
-> 不写 core.thought.image_refs_json
-> thought batch 标记失败 / pending
-> workflow failure
-> 通道通知失败
```

不推荐：保存本地 `/images/...` 作为静默 fallback、写入不可访问的 COS URL、写 Markdown 但不写数据库。原因：静默 fallback 会让迁移状态不可判断，并继续向 Git 仓库写新图片。

### 网络超时

```text
1. 对目标 key 执行 HeadObject。
2. 对象存在且大小、content-type 可接受 -> 视为上传成功。
3. 对象不存在 -> 重试上传。
4. 重试超过阈值 -> 失败。
```

### GitHub Actions 与 COS 跨网耗时

当前链路是：

```text
GitHub Actions runner
-> 下载 Telegram / 飞书图片
-> 上传腾讯云 COS（公网）
-> 写 PostgreSQL
-> 触发 Pages / Cloudflare Pages 部署
```

需要明确三点：

- COS 上传耗时只影响同步 workflow，不影响后续站点构建时长；构建阶段不会再上传图片，也不会把 COS 图片下载到仓库。
- 新图片不再进入 Git diff，长期会减少 checkout、commit、push、Pages artifact 体积，这是本改造的主要性能收益。
- 单次同步中的图片数量较少，建议先顺序上传或 `2-3` 并发上限；不要无上限并发，以免 GitHub runner 到 COS 公网抖动时放大失败。

实现建议：

```text
每张图片:
  start timer
  HeadObject
  PutObject（需要时）
  HeadObject 校验（超时后或可选）
  record duration/status

每个 batch:
  uploadedCount
  skippedExistingCount
  failedUploadCount
  totalUploadMs
  maxSingleUploadMs
```

建议默认阈值：

- 单对象上传软告警：`> 10s`。
- 单对象上传硬超时：`30s` 到 `60s`，按 SDK 可配置能力落地。
- 单 batch COS 上传总耗时软告警：`> 60s`。

这些阈值不是业务正确性标准，只用于排障定位。只要 URL 可访问、DB 正确写入，网络慢不应触发数据回滚。

### 浏览器访问 COS 图片耗时

当前页面托管在 `https://soulgo.chat`，图片第一阶段来自 `https://*.myqcloud.com` 默认域名：

```text
用户浏览器
-> GitHub Pages / Cloudflare Pages 拉 HTML
-> 腾讯云 COS 默认域名拉图片
```

这意味着：

- 图片请求不会占用 GitHub Pages 带宽。
- 浏览器不能复用 `soulgo.chat` 的 HTTP 连接，需要连接 COS 默认域名。
- 若用户主要在中国大陆访问，选择 `ap-shanghai` 通常合理；若主要在海外访问，需要用实测决定 region 或 CDN，而不是凭感觉切 region。
- 因没有备案域名，第一阶段不能通过 `img.soulgo.chat` 做同品牌域名或 CDN 加速。

上线前抽检：

```bash
curl -I "https://training-images-dev-1250000000.cos.ap-shanghai.myqcloud.com/dev/thoughts/2026/06/example.jpg"
curl -w "dns:%{time_namelookup} connect:%{time_connect} ttfb:%{time_starttransfer} total:%{time_total}\n" -o /dev/null -s "https://..."
```

验收时至少在 GitHub Actions Ubuntu runner 或本地类 Unix shell 中记录一次 dev 图片 URL 的 `TTFB` 和 `total`，作为后续判断是否需要 CDN 的基线。

### DB 写入失败（孤儿对象）

```text
COS upload succeeded -> DB write failed -> pending replay -> replay 用同一 key -> DB write succeeded 后引用该 URL
```

当前代码依据：`handleThoughtSyncBatch()` 在图片 artifact 写入后调用 `persistBatch()`；DB 写失败会调用 `appendPendingPersistenceBatch()` 返回 `persistenceStatus: 'pending_replay'`。注意：**现有 pending replay 只兜底 DB 写失败，不兜底 COS 上传失败**——COS 重试/HeadObject 须在 adapter 内实现。

### 权限失效

启动时 fail fast：`COS_ENABLED=true` 但缺必填项 / Domain 非 https / dev=main bucket 或 domain → 直接失败。运行时权限失败：workflow fail，通知通道，不写 DB。

## 一致性保障

- **Telegram vs 飞书**：两通道汇于同一 `writeThoughtImageFiles` + 同一 DB 字段 + 同一导出层，结构上保证一致。
- **dev vs main**：独立 bucket / secret / domain / prefix；`sync-dev.yml` 只读 `DEV_COS_*`，`sync.yml` 只读 `COS_*`；启动校验 dev≠main。
- **Markdown vs DB**：Markdown 永远从 DB 派生，`image_refs_json` 是唯一事实源；禁止手写 Markdown 图片引用。
- **COS URL 唯一真实来源 = `core.thought.image_refs_json`**。

## 容灾与恢复优先级

1. 保证数据库事实不写错。
2. 保证历史图片继续可访问。
3. 保证新图片 URL 可访问。
4. 保证 Markdown 可从数据库重建。
5. 最后治理孤儿对象和仓库图片清理。

## 可接受 / 不可接受失败模式

**可接受**：COS 上传成功但 DB 失败产生孤儿对象；Markdown backup 暂时失败但 DB 正确；历史和新图片混合 URL。

**不可接受**：数据库写入不可访问的图片 URL；Markdown 有图片但数据库没有；dev 图片写入 main bucket；引入 COS 后历史 `/images/...` 失效。

## 回滚方案

### 快速回滚（配置级）

```text
COS_ENABLED=false
DEV_COS_ENABLED=false
```

效果：新同步恢复本地 `source/images` 写入；已写入 DB 的 COS URL 继续可访问（桶保持公有读）；历史 `/images/...` 不受影响。

### 单条数据回滚

```text
更新 core.thought.image_refs_json 为旧 /images/thoughts/... 或正确 URL
-> npm run export:markdown
-> deploy
```

前提：旧 GitHub 图片仍保留。

### 全量回滚

1. 关闭 `COS_ENABLED`。
2. 停止历史迁移。
3. 保留 COS 对象不删除。
4. 将最近一批迁移的 DB 引用改回旧路径。
5. 重新导出 Markdown。
6. 重新部署站点。

## 验收标准

### 功能

- Telegram / 飞书新图片随想可入库。
- 图片 URL 可从浏览器公网访问（公有读）。
- `core.thought.image_refs_json` 保存最终 COS URL。
- Markdown backup `photos` 与数据库一致。
- 历史 `/images/thoughts/...` 仍可访问。
- 无图片随想仍走 database-only。
- 随想编辑、删除、移动语义不变。

### 环境

- dev 新图进 dev bucket；main 新图进 main bucket。
- dev DB 不出现 main COS domain；main DB 不出现 dev COS domain。
- 关闭 COS 开关后可回到本地图片路径。

### 运维

- workflow summary 不泄露 Secret。
- workflow summary 能看到 COS provider、上传数量、跳过数量、失败数量、上传耗时、图片 URL host。
- COS 上传失败时 workflow 不写错误 URL。
- DB 失败时 batch 进入 pending 或明确失败。
- Markdown backup 失败不影响数据库事实。
- dev 至少抽检 1 条图片 URL 的 `curl -I` 返回 200，`Content-Type` 为图片类型，`time_starttransfer/time_total` 有记录。
- 页面 HTML 由 GitHub Pages / Cloudflare Pages 返回，图片请求直接来自 COS 默认域名；不要求 GitHub Pages 代理图片。

### 回滚触发条件

满足任一即回滚或暂停：main DB 出现 dev COS URL；dev DB 出现 main COS URL；未备案阶段写入了 `img.soulgo.chat` / `img-dev.soulgo.chat` 等不可用自定义域名；COS 上传成功率持续异常；任何新写入 `image_refs_json` URL 无法访问；Markdown 与 DB 图片引用不一致；历史 `/images/...` 链接失效；关闭 COS 开关后本地 fallback 不可用。
