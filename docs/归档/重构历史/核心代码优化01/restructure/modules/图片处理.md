# 模块级重构方案：图片处理

## 当前问题

| 问题 | 证据 | 优先级 | 风险等级 |
| --- | --- | --- | --- |
| 图片处理与 Telegram 命名强绑定 | `recognizeTelegramImageMessage`、`TELEGRAM_RECOGNITION_*` | P1 | P2 |
| 识别失败与 DB 写入失败共用 pending 语义 | `ingest.telegram_pending_batch` 同时承载 AI 与 database failure | P1 | P1 |
| AI 缓存与审计粒度不足 | `ingest.telegram_recognition` 以 message_id 为主键 | P1 | P2 |

| npm `form-data` CRLF 漏洞影响图片上传 | AI provider 和飞书 API 的 multipart 请求均使用 `form-data` | P1 | P1 |
| 日期归档置信度缺失，绿色 Action 仍可能掩盖业务歧义 | `Sync (Dev) #56` 为 `manual_intervention`；`Sync (Main)` / `27726311686`、`27723440758` 出现 `6月18日` warning、`sleep_bedtime`、`no_date`、`archivedDate=2026-06-17` 等混合证据 | P1 | P1 |

实施状态校准（2026-06-21，本地合同）：

- 图片下载大小限制、inline 下载错误保留、日期置信度字段、无效 `archivedDate` 防护、DB 层无效日期人工介入、measurement 多图合并、`detectedDate` 保留均已完成本地合同测试，并记录到 `实施checklist.md`。
- 上表保留的是原始风险来源；真实 dev/main 图片端到端、飞书开放平台真实 403/404、生产图片灰度仍按阶段 6 条目单独验收，未在本文档中视为完成。

## 设计缺陷

- 图片业务是跨渠道能力，但变量、表和函数名仍以 Telegram 为中心。
- 识别结果缓存没有显式绑定 prompt version、model、image fingerprint。
- 局部失败可以继续处理，但失败重试、缓存命中和人工排障缺少统一 task trace。
- 飞书图片不是 Telegram file_id：适配层把 `image_key` 伪装成 `photo.file_id` 复用 Telegram 分析管线，下载时仍必须传飞书 `sourceMessageId` 和 tenant access token。
- 历史上日期归档只输出 `archivedDate/dateSources/warnings`，没有可被 summary/gate 直接消费的 `dateConfidence`。本地合同已补 `dateConfidence/dateStages`，但 dev/main 端到端仍需检查它们是否进入真实 Action summary。
- `AI_CONCURRENCY` 未配置时当前代码默认 3，不是单并发；后续设置为 2 属于飞书图片限流策略，不能当作修复默认并发的事实依据。

## 重构方案

### P0：统一图片任务状态

新增 `ImageRecognitionTask`：

| 字段 | 说明 |
| --- | --- |
| `taskId` | 来自 MessageSyncTask |
| `imageId` | `channel:sourceMessageId:fileUniqueId/imageKey` |
| `imageFingerprint` | 文件 bytes hash；无法下载时为空 |
| `promptVersion` | prompt metadata |
| `model` | 实际识别模型 |
| `status` | pending / recognized / partial_failed / failed |
| `retryable` | 是否允许自动重试 |

图片任务结果必须额外保留日期判定字段：

| 字段 | 说明 |
| --- | --- |
| `archivedDate` | 最终用于入库/归档的业务日期，可为空 |
| `dateSources` | 每张图的日期来源、证据和 `source`，原样保留 |
| `dateWarnings` | 从识别 warning 中筛出的日期相关 warning |
| `dateConfidence` | `exact` / `derived` / `uncertain` / `missing` |

建议判定：

- `exact`：图片内有完整日期或明确 header，且同批无冲突。
- `derived`：由文件名、消息年份补全或睡眠跨日规则推导，例如 `source=sleep_bedtime`。
- `uncertain`：出现“缺少年份”“无法可靠生成 YYYY-MM-DD”“混合日期证据”等 warning。
- `missing`：`source=no_date` 或 `failureReason=no reliable image or filename date`，进入 `manual_intervention`。

### P1：拆出 ImageRecognitionUseCase

职责：

1. 从 adapter 下载或生成 image input。
2. 调用 AiScheduler。
3. 校验 schema。
4. 写入识别缓存和 AI 日志。
5. 输出标准 recognition result。

### P1：缓存 key 升级

缓存 key 从 `message_id` 升级为：

```text
sha256(channel + imageFingerprint + promptVersion + model)
```

旧 `ingest.telegram_recognition` 保留读取 fallback。

### P2：失败分类统一

| 分类 | 示例 | 自动重试 |
| --- | --- | --- |
| `image_download` | Telegram file 404 / 飞书资源过期 | 是，短期 |
| `ai_timeout` | provider timeout | 是 |
| `ai_rate_limit` | 429 | 是，退避 |
| `ai_invalid_schema` | JSON/schema 不合格 | 先在同一 provider 上严格 JSON 重试；只有 provider/network/timeout/429/5xx/empty content 等可恢复错误才切 fallback |
| `user_input` | 非训练截图 | 否 |
| `database` | 写入失败 | 是 |

### P1：飞书图片真实运行风险

最近 dev 日志显示，飞书图片处理至少要独立记录这些阶段：

| 阶段 | 日志现象 | 文档/设计要求 |
| --- | --- | --- |
| 识别缓存 | `recognition cache read failed ... timeout expired` | cache timeout 不应阻断 AI，但要进入 metrics |
| AI schema | `telegram_training_image expected object at $` | 记录 provider/model/content snippet；不要默认认为所有 schema error 都已经尝试 fallback |
| DB 写入 | `queued database replay ... timeout expired` | 明确 `pending_replay` 是自动重试，不是已完成 |
| Action 结论 | Action success | 文档必须强调业务状态看 summary，不看 run conclusion |

### P1：日期归档与业务状态 gate

最近日志显示，图片识别成功不代表日期归档可靠：

| 运行 | 日志现象 | 设计要求 |
| --- | --- | --- |
| `Sync (Dev) #56` / `27726387902` | `taskStatus=skipped`、`failureReason=no reliable image or filename date`、`failureDisposition=manual_intervention` | `dateConfidence=missing`，不触发 deploy，不算业务通过 |
| `Sync (Main)` / `27726311686` | 消息时间 `2026-06-18 07:28:01 Asia/Shanghai`，warning 为截图只显示 `6月18日`，但 `source=sleep_bedtime` 后 `archivedDate=2026-06-17` | `dateConfidence=derived/uncertain`，summary 必须说明由睡眠跨日推导 |
| `Sync (Main)` / `27723440758` | 同批存在 `image header: 2026-06-17`、`sleep_bedtime`、`no_date` 和 `6月18日` warning | 混合证据必须保留到 summary，必要时进入人工复核 |

实现上不应丢弃现有 `dateSources`；新增 `dateConfidence` 只是给 summary/gate 一个稳定入口。下次重构如果拆 `ImageRecognitionUseCase`，日期解析、睡眠跨日、文件名 fallback 和业务 gate 要在同一批测试里覆盖。

## Bug 修复方案（本轮审计新发现）

### P1-1：图片下载大小限制需保留端到端验收

**代码级修复**

- **文件**：
  - `src/adapters/telegram/telegram-api.mjs:57-68`
  - `src/adapters/feishu/feishu-api.mjs:104-122`
- **问题**：两条图片下载链路都用 `new Uint8Array(await response.arrayBuffer())` 将整个文件加载进内存，没有 `content-length` 检查和累计读取上限，超大文件会导致 Action/Worker 进程内存峰值失控。
- **实施状态（本地）**：已补 `MAX_IMAGE_DOWNLOAD_BYTES` 路径和 Telegram/飞书 `content-length` / 无 `content-length` 流式累计测试；真实 dev/main 上传 5MB/15MB/30MB 图片仍按阶段 6 单独验收。
- **修复步骤**：
  1. 在发起下载前读取 `response.headers.get('content-length')`。
  2. 若 `content-length` 存在且大于 `20 * 1024 * 1024`（20MB），立即抛错拒绝下载。
  3. 若 `content-length` 缺失或文件超大，改用流式下载（`response.body` 配合 `ReadableStream`），边读取边校验累计大小，超过阈值时中断并清理资源。
  4. Telegram 和飞书共用同一 `downloadBinaryWithLimit()` helper，避免一条通道修了另一条遗漏。
  5. 记录超限事件到日志和 metrics，便于后续分析。

**测试策略**

- 单元测试：Telegram/飞书各 Mock 一个 `content-length = 25MB` 的响应，验证函数在下载前抛错。
- 单元测试：Telegram/飞书各 Mock 无 `content-length` 的响应，使用流式读取并在累计超过 20MB 时中断，验证资源不泄漏。
- 集成测试：在 dev 环境上传一张 5MB、15MB、30MB 的训练截图，确认 30MB 的任务被拒绝且不会导致服务 OOM。
- 回归测试：确认正常大小图片（<20MB）的下载、识别、入库链路不受影响。

**回滚计划**

- 若发现大小限制误杀正常图片，调整阈值配置为环境变量 `MAX_IMAGE_DOWNLOAD_BYTES`（默认 20MB），无需回滚代码即可恢复。
- 若流式下载引入兼容性 bug，可切回原来的 `arrayBuffer()` 全量读取，并在网关层增加大小限制兜底。

### P2-1：`normalizeDateKey` 真实日期校验需保留回归保护

**代码级修复**

- **文件**：`src/adapters/postgres/incremental-write.pg.mjs`
- **问题**：原始审计发现为正则只验证格式，无法识别 `2023-02-30` 这类无效日期。
- **实施状态（本地）**：已在图片增量写入归一化日期时校验真实日历日期；共享同步管线已把 DB 层无效日期失败归为 `manual_intervention`，不进入 `pending_replay`。
- **已落地实现**：
  1. 在正则匹配通过后，通过 UTC 日期构造并回读年/月/日校验真实日期：
     ```js
     const date = new Date(`${yyyy}-${mm}-${dd}T00:00:00.000Z`);
     date.getUTCFullYear() === Number(yyyy);
     ```
  2. 若校验失败，抛出 `invalid archivedDate: <value>`。
  3. 共享同步管线把该错误归类为 `user_input`，ready 图片批次进入 `manual_intervention`，不写入 `pending_replay`。

**测试策略**

- 单元测试：输入 `2023-02-30`、`2023-04-31`、`2023-13-01`，验证校验失败并抛出异常。
- 单元测试：输入 `2023-02-28`、`2023-12-31`，验证校验通过。
- 集成测试：在 dev 环境构造一批包含非法日期的训练截图，确认同步任务进入 `manual_intervention` 或在应用层报出日期错误，不等到 PostgreSQL `date` 类型报错后才回滚整批。
- 回归测试：确认历史正常日期数据的写入性能无退化。

**回滚计划**

- 若日期库引入导致时区或性能问题，可注释掉新增校验逻辑，保留原有正则校验作为降级方案。
- 若误判率过高（如某些合法日期被错误拦截），可放宽校验策略或切换为仅记录 warning 而不阻断。

**回滚计划**

- 若合并逻辑复杂导致性能问题，可简化合并策略为“同日期同类型取最新”，并记录 warning 供人工确认。

### P1-7：measurement `detectedDate` 保留需保留端到端核对

**代码级修复**

- **问题**：原始审计发现为 `detectedDate` 被解构后未返回，导致下游 `measuredAt` 回填时丢失原始日期上下文。
- **实施状态（本地）**：已保留 `detectedDate`，并在 `measuredAt` 只有 `HH:mm` 时用于回填完整日期。
- **修复步骤**：
  1. 在 `normalizeMeasurementForArchive` 的返回对象中，显式保留 `detectedDate` 字段。
  2. 确认下游消费方（如 `persistTelegramImageBatchIncremental` 或归档逻辑）能够读取到该字段并正确回填 `measuredAt`。
  3. 若 `detectedDate` 与 `archivedDate` 不一致，在 `dateSources` 中补充记录差异原因（如 `source=detectedDate_override`）。

**测试策略**

- 单元测试：调用 `normalizeMeasurementForArchive` 时传入包含 `detectedDate` 的对象，验证返回值中包含 `detectedDate`。
- 集成测试：在 dev 环境触发一次完整同步，确认归档后的训练记录中 `measuredAt` 被正确回填为 `detectedDate`。
- 回归测试：确认不携带 `detectedDate` 的旧数据仍能正常通过该函数，不会引入 undefined 污染。

**回滚计划**

- 若保留 `detectedDate` 导致下游序列化或存储失败（如数据库 schema 不允许该字段），可临时从返回对象中移除，改为仅写入日志供人工追溯。
- 若 `measuredAt` 回填后产生业务逻辑冲突，可切换为仅记录不回填，由后续流程统一处理。
