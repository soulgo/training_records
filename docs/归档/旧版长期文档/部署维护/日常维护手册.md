# 日常维护手册

本文面向接手项目的维护人员，整理最常用的本地、数据库、Telegram、飞书、部署和检查操作。

## 1. 本地开发

```bash
npm ci
npm test
npm run build
npm run server
```

线上以 PostgreSQL 为唯一事实源。需要本地验证线上口径时，设置 `TRAINING_SNAPSHOT_SOURCE=database`、`TRAINING_DB_ENABLED=true` 和 `TRAINING_DB_URL` 后再构建。

## 2. 手工维护训练记录

日常不再通过修改 `训练记录.md` 维护数据。训练、体脂秤、饮食、睡眠、随想和身体反馈都应通过 Telegram、飞书或数据库维护入口写入 PostgreSQL。

`训练记录.md` 是数据库派生备份。如果确实需要用 Markdown 修复数据库，必须把它当作人工迁移动作：

1. 确认 Markdown 是比数据库更可信的完整快照。
2. 先备份当前数据库或导出现有快照。
3. 先运行 `npm run reconcile:markdown -- --dry-run`，审核输出的 `affectedDays`。
4. 显式运行 `npm run import:markdown` 或 `npm run reconcile:markdown`。
5. 运行数据库读写测试和页面构建验证。

注意：不要手工维护 `训练数据解析.md`，它是生成文件。

## 3. 数据库维护

新库初始化使用：

```bash
psql "$TRAINING_DB_URL" -f sql/pgsql17.sql
```

常用命令：

```bash
npm run maintenance:inspect
npm run import:markdown
npm run export:markdown
npm run sync:db
npm run reconcile:markdown
npm run backfill:core
npm run backfill:thoughts
```

`maintenance:inspect` 是只读巡检命令。输出里的 `pendingDatabaseCount`、`pendingDatabaseOldestAgeMinutes`、`pendingDatabaseMaxAttemptCount` 和 `pendingDatabaseAlertLevel` 用于判断 pending 是否堆积：`pendingDatabaseAlertLevel=P2` 表示 pending 已超过 30 分钟，`P1` 表示数量超过 10、最老 pending 超过 24 小时或最大 attempt_count 达到 25。`pendingDatabaseAlertReasons` 会列出触发原因。

同一输出里的 `aiMonitoringFallbackRate`、`aiMonitoringSchemaFailureCount`、`aiMonitoringAvgRecognitionLatencyMs`、`aiMonitoringMaxRecognitionLatencyMs`、`aiMonitoringTotalTokens` 和 `aiMonitoringTotalCostUsd` 来自 `ingest.ai_call_log` 与 `ingest.telegram_recognition`，用于巡检最近 60 分钟的 AI fallback、schema failure、识别耗时和 token/cost 趋势。`aiMonitoringAlertReasons` 出现 `ai_fallback_rate_gt_30pct` 或 `ai_schema_failure_gte_2_per_hour` 时，应检查主 provider 状态、余额、限流和 prompt/response_format。

排查 AI 识别错写时，先按批次只读审计：

```bash
npm run maintenance:inspect -- --batch-id <batchId>
```

输出里的 `data.batchAudit.recognitions[].recognitionJson` 是原始识别结果，`coreTargets` 和 `recoveryTargetDays` 用于确认需要人工恢复的目标日期。确认后再选择受控 SQL、`reconcile:markdown` 或 `backfill:core`，不要直接用旧 Markdown 覆盖数据库。

维护原则：

- `TRAINING_DB_ENABLED=false` 时，数据库读写会跳过或返回空快照。
- `TRAINING_DB_ENABLED=true` 且配置了 `TRAINING_DB_URL` 后，Telegram 同步会优先写 PostgreSQL。
- `sync:db` 默认只执行安全同步：archive 回填、ingest 睡眠修复和 thoughts 同步，不执行 Markdown 对账入库。
- `import:markdown` / `reconcile:markdown` 会按 Markdown 快照写数据库，只能作为显式人工维护命令使用。
- `export:markdown` 严格从数据库导出 Markdown，数据库不可用时失败，不回退旧 Markdown。

## 4. Telegram 同步维护

手动运行同步：

```bash
npm run sync:telegram
```

必要环境变量：

- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_ALLOWED_CHAT_IDS`
- `AI_API_KEY`
- `AI_BASE_URL`
- `AI_MODEL`
- `TRAINING_DB_ENABLED`
- `TRAINING_DB_URL`

即使只处理随想，当前同步入口也会统一校验 AI 和数据库相关变量。

当前图片同步稳定支持：

- 锻炼截图：活动总览、活动明细、热量、时长、距离、心率。
- 体脂秤截图：体重、BMI、体脂率、骨骼肌、基础代谢等身体成分。
- 饮食截图：餐次、总摄入和餐次明细。
- 睡眠截图：入睡/起床、睡眠阶段、睡眠评分、心率、HRV、血氧、呼吸率、解读和建议。

睡眠图按醒来日期减一天归档。维护时如果看到截图显示 6 月 5 日早上醒来，而数据归到 6 月 4 日，这是预期行为。

Telegram 图片正常成功路径是增量入库：先写 `ingest.*`，再 upsert 本批次 `core.measurement`、`core.activity`、`core.meal`、`core.sleep`，最后刷新目标 `core.training_day` 汇总。成功批次不会覆盖 `训练记录.md`；PostgreSQL 失败时写 pending 队列等待后续重放。

默认 pending 队列是 PostgreSQL `ingest.telegram_pending_batch`。历史 `runtime/telegram-sync-pending.ndjson` 只作为 legacy 队列保留，不会被普通 `sync:telegram` / `sync:feishu` 自动消费。接手或清理前先只读检查：

```bash
node tools/telegram-sync-fallback.mjs inspect
```

只有确认需要恢复旧队列时，才显式开启 legacy replay：

```bash
TELEGRAM_SYNC_REPLAY_LEGACY_NDJSON_PENDING=true npm run sync:telegram
```

legacy replay 成功清理或改写 `runtime/telegram-sync-pending.ndjson` 前，会在同目录生成 `telegram-sync-pending.ndjson.backup-<UTC timestamp>`。如果需要回滚旧队列，先使用 backup 文件还原，不要凭空重建 NDJSON。

图片识别规则变更后，至少运行：

```bash
node tools/prompt-generator.mjs
node --test test/prompt-generator.test.mjs test/telegram-sync.test.mjs test/telegram-sync-runner.test.mjs
```

如果涉及睡眠表结构或数据库读写，再补充：

```bash
node --test test/training-db-core.test.mjs test/training-db-archive.test.mjs test/training-snapshot.test.mjs
```

真实 dev Bot / dev workflow 验收直接按当前链路执行：向 dev Bot 发送一批带可靠日期的测试图片，确认 `sync-dev.yml` 的 GitHub Actions summary、Telegram 回复、dev 数据库目标日期、pending 状态和 dev Pages 预览部署结果。旧 runbook 已归并到本手册和问题排查文档，不再作为当前操作入口。

## 5. Webhook 与 Cloudflare

生产 Telegram / 飞书共用统一 Worker。部署生产 Worker：

```bash
npx wrangler deploy --config wrangler.toml
```

部署 dev Worker：

```bash
npx wrangler deploy --config wrangler.dev.toml
```

刷新 Telegram webhook：

```bash
npm run telegram:webhook
```

GitHub Actions 中：

- `Deploy Cloudflare Worker` 部署生产统一 Worker，并刷新生产 Telegram webhook。
- `Deploy Cloudflare Worker (Dev)` 部署 dev 统一 Worker，并刷新 dev Telegram webhook。
- `refresh-telegram-webhook.yml` 支持生产 webhook 手动和每 6 小时定时刷新。

统一 Worker 至少需要：

- `TELEGRAM_SECRET_TOKEN`
- `GITHUB_TOKEN`，普通同步 dispatch 必需
- `TELEGRAM_BOT_TOKEN`，Worker 直接回复帮助消息必需
- `FEISHU_ENCRYPT_KEY`，飞书事件校验必需
- `FEISHU_VERIFICATION_TOKEN`，飞书事件 token 校验必需
- 可选 `GITHUB_OWNER`，默认 `soulgo`
- 可选 `GITHUB_REPO`，默认 `training_records`
- Durable Object binding `TELEGRAM_ALBUM_BUFFER`
- Durable Object binding `FEISHU_IMAGE_BUFFER`

## 7. 部署站点

普通部署由 `.github/workflows/deploy-pages.yml` 处理。它调用 `.github/actions/site-build/action.yml`，完成：

1. Setup Node.js 22。
2. 缓存 Hexo 实际生成的 `db.json`。
3. `npm ci`。
4. 可选 `npm run sync:db`，执行安全数据库修复，不做 Markdown 对账。
5. 可选测试。
6. `npm run build`。
7. 上传并部署 `public/`。

Telegram 或飞书同步产生文件变化或 DB-only 内容变化后，对应 sync workflow 会异步 dispatch `deploy-pages.yml`，并传入严格数据库快照模式。DB-only 内容变化包括图片入库、随想新增、随想编辑、随想删除和随想移动的 `ready + stored` 批次。成功通知会先回发原消息通道，站点构建结果需要到对应 deploy workflow 查看。

dispatch 场景会写 GitHub Actions summary，维护时优先看 `batchId`、`taskStatus`、`persistenceStatus`、`archivedDate`、图片计数、pending 状态、`failureDisposition` 和 failed message ids。

GitHub Actions 排队、失败、超时和重跑的处理口径：

- Worker 返回 5xx 时先查 Cloudflare tail 里的 `[sync-dispatch-worker]`，`outcome=worker_5xx` 会给出 `channel`、`status` 和安全错误码；不要在日志里期待看到原始消息正文或 secret。
- `SyncDispatchQueue` 通过 `workflow_dispatch` 传入 `queue_task_id`，workflow run 名称会显示 `Sync queue task <queue_task_id>`；排队时先看对应 run 是否仍是 `queued` / `in_progress`。
- 队列会按 `queue_task_id` 查找 workflow run；如果出现 workflow run 查找超时 / run lookup timeout，任务会按队列重试策略继续重试，超过上限后进入 `dead-letter`，需要人工介入。Cloudflare tail 里的 `[sync-dispatch-queue] outcome=dead_letter` 是死信告警入口，DO storage 的 `deadLetters` 是事后审计入口。
- Action 阶段失败时看 Telegram/飞书回执里的 run URL 和 summary；`pending_replay`、`manual_intervention`、`partial_failed` 即使 run 是绿色也不是完整业务成功。Deploy wait 失败会在 workflow 中输出 `Deploy workflow failed` error annotation。
- 如果 summary 同时出现 `Telegram sync business incomplete` 或 `Feishu sync business incomplete` warning，说明原消息通道已尝试回执业务不完整状态，但仍要按 `batchId`、`persistenceStatus` 和 `failureDisposition` 判断是等待自动重放还是人工介入。
- 对同一批次执行重跑 / rerun 前后，预期 DB 层依靠 `payload_hash` 幂等返回 `unchanged` 或执行 upsert；同一个 `batch_id + payload_hash` 不应重复写 core。
- 如果重跑后发现重复写 core，先暂停继续重跑，按 `batchId` 用 `npm run maintenance:inspect -- --batch-id <batchId>` 审计 `ingest.telegram_batch`、`payload_hash` 和目标 `core.*` 行，再决定恢复动作。

Dev 分支在线预览由 `.github/workflows/deploy-cloudflare-pages-dev.yml` 处理。它在 `dev` 分支站点相关文件变化或手动触发时运行，使用 Dev 数据库变量构建，删除 `public/CNAME` 后通过 Wrangler Direct Upload 发布到 Cloudflare Pages。默认项目名为 `training-records-dev`，默认访问地址为 `https://training-records-dev.pages.dev`；如需改名，设置 GitHub Variable `CLOUDFLARE_PAGES_DEV_PROJECT_NAME`。

生产 Pages 部署成功后会自动尝试清理 Cloudflare 缓存；需要 GitHub Secrets 同时配置 `CLOUDFLARE_ZONE_ID` 和具备 `Zone -> Cache Purge -> Purge` 权限的 `CLOUDFLARE_API_TOKEN`。如果 secret 缺失或 token 权限不足，workflow 会输出 warning 但不会把 Pages deploy 标红，页面仍可能命中旧 HTML；可在 Cloudflare Dashboard -> Caching -> Purge Everything 手动刷新。

验证 CDN 代理是否正常工作：

```bash
curl -sI https://soulgo.chat | grep -E 'server|cf-cache-status|cf-ray'
# 期望: server: cloudflare, cf-cache-status: HIT 或 MISS
```

如果 `server` 仍为 `GitHub.com`，说明 Cloudflare 代理未生效，检查 DNS 记录的橙云状态。

## 8. Markdown 定时备份

`.github/workflows/markdown-backup.yml` 负责从数据库导出 Markdown 备份。workflow 使用固定 cron 唤醒，再读取 GitHub Settings Variables 判断是否执行。

| Variable | 建议值 | 说明 |
| --- | --- | --- |
| `MARKDOWN_BACKUP_ENABLED` | `false`，确认后改 `true` | 是否启用定时备份 |
| `MARKDOWN_BACKUP_FREQUENCY` | `weekly` | `weekly` 或 `daily` |
| `MARKDOWN_BACKUP_BRANCH` | `main` | 备份提交目标分支，dev 验证可设为 `dev` |
| `MARKDOWN_BACKUP_COMMIT` | `true` | 是否自动提交导出的 Markdown |

手动触发 `Markdown Backup` workflow 会绕过 enabled/frequency 门禁，适合临时验证 DB -> Markdown 导出。导出失败时应先修复数据库读取，不要用旧 Markdown 兜底覆盖备份。

每次运行都应查看 workflow summary 里的 `Conclusion` 和 `Alert`：

- `Alert: changed_without_commit` 表示数据库导出的 Markdown 文件已有变化，但 `MARKDOWN_BACKUP_COMMIT` 不是 `true`，workflow 只会发出 warning，不会自动提交；确认导出内容后，将 `MARKDOWN_BACKUP_COMMIT=true` 或人工审核并提交备份分支。
- `Alert: workflow_failed_before_alert_evaluation` 表示 workflow 在告警评估前失败，先看失败 step 和日志，重点检查数据库 schema、权限、`TRAINING_DB_URL`、Node 依赖安装和导出命令。
- 导出失败或告警未评估时，只能修复 DB/schema/权限后重新导出；不要回退到旧 Markdown 作为“成功备份”。

## 10. 接手检查清单

- 确认本地 `npm ci`、`npm test`、`npm run build` 可运行。
- 确认 `TRAINING_SNAPSHOT_SOURCE` 当前线上取值。
- 确认 GitHub Secrets/Variables 是否齐全。
- 确认统一 Cloudflare Worker 变量和 Durable Object binding 是否齐全。
- 确认飞书事件订阅 URL、`FEISHU_IMAGE_BUFFER` 和飞书校验参数是否齐全。
- 确认 Telegram webhook 是否指向当前 Worker URL。
- 确认 GitHub `FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`FEISHU_ALLOWED_CHAT_IDS` 是否齐全。
- 确认 PostgreSQL schema 已包含 `archive.*`、`ingest.*`、`core.*`。
- 确认 PostgreSQL schema 已包含 `core.sleep` 以及睡眠健康指标字段；`archive.training_sleep` 仅用于历史归档/回填维护。
- 确认 `runtime/telegram-sync-pending.ndjson` 是否为空；若非空，先运行 `node tools/telegram-sync-fallback.mjs inspect`，再决定是否显式 legacy replay。
- 确认 `CHANGELOG.md` 最新版本条目和 `package.json` 版本是否符合预期。

### 10.1 接手演练题卡

以下题卡用于人工验收新接手人员是否真正理解系统，不可用阅读记录或本地测试替代。

1. 画链路图：画出 `Telegram/飞书 -> Worker -> Queue -> Action -> AI -> DB -> Pages`，并标明 Telegram 和飞书哪些入口差异只属于鉴权、下载或回执格式，哪些业务阶段必须统一。
2. 解释成功口径：说明 `Action success` 只代表 workflow 跑完；`业务 stored` 才代表结构化事实已经写入 `core.*` 并刷新 `core.training_day`。如果 summary 出现 `pending_replay`、`manual_intervention` 或 `partial_failed`，即使 GitHub run 是绿色也不能算完整业务成功。
3. 判读 summary：给出一个 sync summary，让接手人员用 `taskStatus`、`persistenceStatus`、`failureDisposition`、`recognitionPendingStatus`、`dateConfidence` 和 failed message ids 判断 `auto_retry`、`manual_intervention`、`skipped` 分别该等待重放、人工介入还是接受跳过。
4. 说明恢复优先级：按 `core.* -> ingest.* -> archive.* -> 训练记录.md` 说明恢复优先级。`core.*` 是线上事实源；`ingest.*` 是消息、AI 和 pending 审计来源；`archive.*` 是历史归档/回填来源；`训练记录.md` 是数据库派生备份，只有在确认它比数据库更可信且先 dry-run 审核 affected days 后，才能作为显式人工迁移输入。
