# 重构收益评估（供决策：值不值得做）

本文件回答一个问题：执行 `03_计划实施` 下的重构方案，相比当前系统能带来哪些实际优势，以及要付出的成本和风险。结论供你评估，不代表已决定执行。

前提认知：**当前系统功能是正常的**。本轮所有重构都以"外部行为不变"为硬约束，即不修 bug、不加功能，只改内部结构。因此收益全部是"可维护性 / 可扩展性 / 长期成本"层面的，不会带来任何用户可见的新能力。这一点决定了它是"技术投资"而非"功能交付"。

## 一、当前系统的真实痛点（已用代码核对）

| 痛点 | 证据 | 现在的实际影响 |
| --- | --- | --- |
| 持久化层双向耦合 | `db/training` ↔ `adapters/postgres` 互相 import（4 处正向 + 2 处反向） | 改动一处持久化逻辑要同时读两个目录，容易漏改；新人难以判断"数据库代码到底住在哪" |
| 分层方向倒置 | `core` → `domain` 单向依赖，与 `系统总览.md` 定义相反 | 文档与代码不一致，按文档理解会走错方向 |
| 渠道无关主链路以 telegram 命名 | `runMessageSync` 定义在 `telegram-sync.use-case.mjs:95`，飞书 import 它 | 新增第三个渠道时，要 import 一个叫 telegram 的文件，认知负担明确存在 |
| 超大文件 | `sync-batch-logic.adapter.mjs` 1857 行 64 个函数等 10 个大文件 | 单文件职责过多，改动风险大、评审困难、测试定位慢 |
| 遗留 shim 与遗留表 | 多个纯转发文件 + 4 张无引用的 telegram_* 表 | 冗余；读代码/读 SQL 时被无用对象干扰 |

这些痛点都是"慢性"的：不影响当前运行，但每次改动同步链路时都会重复付出理解成本。

## 二、执行后能带来的优势（分项）

### 低风险项（R5 + R2-B）——投入小、收益确定
- 删掉纯转发 shim 文件，读代码时少一层跳转；`import` 直达真实实现。
- 修正 `系统总览.md` 分层描述，让文档和 `core→domain` 实际方向一致，避免误导。
- **优势性质**：即时净瘦身，几乎零风险。适合"先做了再说"。

### 中风险项（R4 拆分超大文件）——收益最直接
- 把 1857 / 1344 / 1168 行的三个巨型文件按职责拆开。
- 未来改"命令解析"只打开命令解析文件，改"图片识别缓存"只看缓存文件。
- 评审 diff 时范围更聚焦；测试失败时定位更快。
- **优势性质**：日常改动同步链路的体验会明显改善，是本轮"可维护性"收益的主体。

### 高风险项（R1 + R3 + R6）——收益最大但成本也最高
- R1 合并持久化双层：数据库代码只有一个落点，依赖单向，心智模型清晰。
- R3 去 telegram 化命名：新增渠道时不再 import telegram 文件，`系统总览.md` 里"来源无关"这个设计目标才算在代码里兑现。
- R6 清理 4 张遗留表 + 序列：SQL 导出更干净，`数据库模型.md` 描述与实际一致。
- **优势性质**：真正解决"跨层耦合"和"命名误导"两个根因，但改动面覆盖 use-cases / adapters / db 多目录。

## 三、成本与风险（诚实评估）

| 维度 | 说明 |
| --- | --- |
| 无用户可见收益 | 全程行为不变，用户/页面/命令无任何新能力，收益纯内部 |
| 回归风险 | R1、R3 改动面大，虽有 62 个测试文件兜底，但重构引入 bug 的概率始终 > 0 |
| 时间成本 | R4 逐文件拆分 + R1/R3 全量改名需要分多次小步提交与验证，非一蹴而就 |
| R6 不可逆 | DROP 表不可回退，须先确认历史数据无需保留，且由你手动执行 |
| 机会成本 | 这段时间不能用于做新功能或修实际 bug |

## 四、建议的决策分层

不必"全做或全不做"。按投入产出比，建议这样评估：

1. **强烈建议做**：R5 + R2-B（低风险档）。投入极小，即时瘦身，几乎无风险。
2. **建议做**：R4（拆分超大文件）。可维护性收益最实在，风险中等且逐文件可回退。
3. **可选、想清楚再做**：R1 + R3（高风险档）。收益大但改动面大，适合在一段没有紧急功能需求的窗口期集中做。
4. **单独决策**：R6（删表）。与上面解耦，任何时候你确认历史数据无需保留即可单独执行，SQL 已备好在 `sql/dev-sql/update-dev-sql/20260714_drop_legacy_telegram_tables.sql`。

## 五、一句话结论

如果近期系统稳定、你希望降低后续每次改同步链路的理解成本和出错概率，这套重构值得做——但要按风险分层推进，优先低/中风险项拿确定收益，高风险项在空窗期再上。如果近期要密集加功能或系统即将有大调整，则可以只做低风险项，其余暂缓。
