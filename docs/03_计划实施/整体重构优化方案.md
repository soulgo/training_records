# 整体重构优化方案（评估用，未实施）

本文件是一次性规划，供用户评估是否执行。评估通过并落地后，按 `docs/05_日常规则/实施规划落地文档同步规则.md` 把当前事实写回长期文档、变更摘要写入 CHANGELOG，然后删除本文件。

## 1. 前提与约束

本方案严格服从用户提出的四条前提，任何单项重构若违反其一即不纳入：

1. 系统功能不能变：对外行为（命令、识别结果、入库结果、页面产物、workflow 触发链路）保持一致。
2. 不产生冗余文件和代码，最终瘦身：净删除行数与文件数应为正，不允许只搬家不减量。
3. 可维护性加强：降低跨层耦合、消除误导性命名、缩小超大文件职责。
4. 更稳健、可扩展：明确分层依赖方向，让新增来源渠道（已有 Telegram / 飞书）不再依赖以 `telegram` 命名的主链路。

附加流程约束（来自 `CLAUDE.md`）：仅在 `dev` / `main` 分支操作；commit message 使用中文；不擅自新建分支。

## 2. 现状证据

以下为本轮只读排查得到的事实（行数为排查时快照）：

### 2.1 分层依赖存在双向耦合

`src/db/training/` 与 `src/adapters/postgres/` 互相 import：

- `src/db/training/write.mjs` → `adapters/postgres/index.mjs`、`adapters/postgres/incremental-write.pg.mjs`
- `src/db/training/read.mjs` → `adapters/postgres/source-batch-repository.pg.mjs`
- `src/db/training/archive.mjs` → `adapters/postgres/archive-repository.pg.mjs`
- 反向：`adapters/postgres/core-day-repository.pg.mjs` → `db/training/read.mjs`
- 反向：`adapters/postgres/training-analysis-repository.pg.mjs` → `db/training/config.mjs`

`src/db/training` 与 `src/adapters/postgres` 事实上是同一个 PostgreSQL 持久化层的两半，互相回指，边界不清。

### 2.2 分层方向倒置：core 依赖 domain

- `src/core/entities/training-record.mjs` → `domain/training/training-domain.mjs`
- `src/core/services/training-merge-service.mjs` → `domain/training/training-domain.mjs`
- 反向不存在（`domain` 不 import `core`）。

按 `系统总览.md` 的分层定义，Core 是"稳定业务契约"、Domain 是"来源无关规则"，当前 Core 反向依赖 Domain，两层职责边界与实际依赖方向不一致。

### 2.3 共享编排器命名与位置误导

- 渠道无关的编排入口 `runMessageSync` 定义在 `src/app/use-cases/telegram-sync.use-case.mjs:95`。
- `src/app/use-cases/feishu-sync.use-case.mjs` 反过来 import 这个位于 `telegram-sync` 文件里的共享函数，并复用 `telegram-sync/image-processing.mjs` 的 `recognizeBatch`。
- 大量源码神经中枢仍以 `telegram` 命名，却是飞书也走的公共主链路：`groupTelegramUpdates`、`processTelegramBatch`、`persistTelegramImageBatchIncremental`、`adapters/telegram/sync-batch-logic.adapter.mjs`。

对新维护者而言，"飞书为什么要 import telegram 用例"是明显的认知负担。

## 3. 重构项（按主题分组）

每项标注：问题 / 方案 / 影响面 / 是否改变外部行为 / 验证方式。所有项均要求"行为不变、净瘦身"。

### R1 合并 PostgreSQL 持久化双层（对应 2.1）

- 问题：`db/training` 与 `adapters/postgres` 双向耦合，同一持久化层被拆成互指两半。
- 方案：以 `adapters/postgres` 为唯一 PostgreSQL 适配层落点，将 `db/training` 中属于纯适配职责的读写（read/write/archive/config 的连接与查询实现）迁入或明确单向依赖，消除反向 import；删除 `db/training/archive.mjs` 等纯转发文件，调用方直接引用适配层。
- 影响面：`src/db/training/*`、`src/adapters/postgres/*` 及其所有 import 方（含 `telegram-sync`、`feishu-sync`、tools、site 读取）。
- 外部行为：不变（仅移动实现与调整 import 路径）。
- 验证：全量测试（62 个测试文件）+ `npm run build` + `git diff --check`；重点跑入库、读取、分析、站点构建相关测试。

### R2 校正 core / domain 依赖方向（对应 2.2）

- 问题：Core 反向依赖 Domain，分层定义与实际依赖冲突。
- 方案：二选一，评估时确认取向——
  - 方案 A（推荐）：把 `training-domain.mjs` 中被 Core 依赖的稳定契约类工具（如 `buildTrainingDay`、`emptyNutrition`、`emptySleep`、类型规范化）下沉到 `core`，Domain 的 Markdown 解析类逻辑保留在 `domain` 并单向依赖 Core；
  - 方案 B：若判定当前 Domain 即为稳定契约层，则在 `系统总览.md` 中修正分层描述，使文档与依赖方向一致（纯文档修正，零代码风险）。
- 影响面：方案 A 涉及 `src/core/entities/*`、`src/core/services/*`、`src/domain/training/*` 及 import 方；方案 B 仅文档。
- 外部行为：不变。
- 验证：解析、合并、快照构建相关测试 + 站点构建。

### R3 共享编排器去 telegram 化命名（对应 2.3）

- 问题：渠道无关主链路以 `telegram` 命名，飞书 import telegram 用例，语义误导。
- 方案：将 `runMessageSync` 及其真正渠道无关的编排逻辑抽到中性模块（如 `src/app/use-cases/message-sync.use-case.mjs`），`telegram-sync` / `feishu-sync` 各自只保留渠道特有装配；对确属公共的 `groupTelegramUpdates`、`processTelegramBatch`、`persistTelegramImageBatchIncremental` 等做重命名（如 `groupSourceMessages` 已存在，可统一到 source 语义）。为控制风险，重命名一次性完成并更新全部引用，不保留旧名 re-export 兼容层（符合前提 2）。
- 影响面：`app/use-cases/*`、`adapters/telegram|feishu/*`、相关测试与文档源码入口表。
- 外部行为：不变（命令、识别、入库结果一致）。
- 验证：Telegram 与飞书同步全链路测试；文档 `源码事实入口` 表同步更新。

### R4 拆分超大文件（对应 2.4）

- 问题：单文件职责过多，阅读与改动风险高。
- 方案：按已有职责边界做纯物理拆分（不改逻辑），优先处理耦合中枢：
  1. `sync-batch-logic.adapter.mjs`（1857）→ 命令解析 / 消息分组 / 批次分析 / Markdown 应用 / 并发工具 分文件；
  2. `telegram-sync.use-case.mjs`（1344）→ env 装配 / 批次路由 / 随想处理 / provider 装配 分文件；
  3. `image-recognition.use-case.mjs`（1168）→ 缓存 / provider 与 fallback / schema 请求 / 解析校验 分文件。
  拆分以"移动 + 精确 import"为主，禁止顺手改行为；每拆一个文件立即跑相关测试。
- 影响面：上述文件及 import 方。
- 外部行为：不变。
- 验证：逐文件拆分后即时测试，最终全量测试 + 构建。

### R5 清理 re-export shim（对应 2.5）

- 问题：纯转发文件增加间接跳转，不利维护，且属冗余。
- 方案：逐个内联——将调用方 import 直接指向真实实现文件，删除 shim。对确有"分层入口"价值的 barrel（如需要对外稳定聚合点）保留并在首行注释说明其存在理由；其余删除。
- 影响面：`src/db/training/archive.mjs`、`src/adapters/telegram/sync-batch.adapter.mjs`、`src/telegram/*` 转发文件及各 `index.mjs`。
- 外部行为：不变。
- 验证：全量测试 + 构建；确认净删除文件数为正。

### R6 处置数据库遗留表（对应 2.6，需用户单独确认）

- 问题：`ingest.telegram_batch/message/recognition/pending_batch` 四张表及序列 `telegram_pending_batch_pending_id_seq` 仍在 dev SQL 导出中，代码已不引用（此前方案漏列 `telegram_recognition`）。`telegram_pending_batch` 序列 `setval=17`，历史上有过数据，需先核对。
- 方案：这是数据库结构变更，按 `数据库模型.md` 的边界必须由 `training_writer` 或 DBA 在目标环境手工执行、验收、再重新导出 SQL，日常 workflow 不做 DDL。因此本项只产出一份"待人工执行的清理清单"（DROP 顺序：先检查历史/依赖，再删表、后删序列），不由重构代码自动执行。dev/main 需分别独立操作，不混写业务数据。
- 影响面：仅数据库结构与 `sql/dev-sql`、`sql/main-sql` 导出文件。
- 外部行为：不变（表本就无生产引用）。
- 验证：删除前确认无外部对象依赖；删除后重新导出并 `check:data-consistency`。
- 风险提示：属不可逆的 DROP 操作，需用户明确批准后再由人工执行。

## 4. 分阶段实施建议

按"先低风险、后高风险；先文档/删除、后移动/重命名"排序，每阶段独立可验证、可回退：

| 阶段 | 内容 | 风险 | 前置 |
| --- | --- | --- | --- |
| P0 | R5 清理 shim（纯删除 + 内联 import） | 低 | 无 |
| P1 | R2 方案 B 文档修正，或确认走方案 A | 低 | 用户选定 R2 取向 |
| P2 | R4 拆分超大文件（逐个、纯物理） | 中 | P0 |
| P3 | R1 合并 PostgreSQL 双层 | 中高 | P0、P2 |
| P4 | R3 去 telegram 化命名（一次性全量改名） | 中高 | P2、P3 |
| P5 | R6 数据库遗留表清理清单（人工执行） | 高（不可逆） | 用户单独批准 |

每阶段结束：跑相关测试 → `git diff --check` → 中文 commit（当前 `dev` 分支）。P3、P4 变动面大，建议阶段内再细分小步提交。

## 5. 明确不做（防止范围蔓延，服从前提 1）

- 不改识别 schema（保持 `RECOGNITION_SCHEMA_VERSION = v4`）与语义校验行为。
- 不改命令别名、帮助文本、页面路由与主题模板产物。
- 不改 workflow 触发链路、队列 DO 命名、pending 消费策略。
- 不引入新框架、新依赖、新抽象层；不为"未来可能"预留配置。
- 不在同步链路中新增任何运行时 DDL 或全量扫描。
