# 重构方案 · 高风险（评估用，未实施）

本文件是《整体重构优化方案.md》按风险拆分出的一份，只包含高风险项。落地后按 `docs/05_日常规则/实施规划落地文档同步规则.md` 写回长期文档并删除本文件。

风险定义：改动面大且触及依赖方向、跨渠道命名或不可逆 DDL；回退成本高；需分小步提交，R6 需用户单独明确批准并由人工执行。

## 前提与约束

服从四条前提：功能不变、净瘦身、可维护性加强、更稳健可扩展。仅在 `dev` / `main` 分支操作；commit message 使用中文；不擅自新建分支（见 `CLAUDE.md`）。R6 涉及数据库 DDL，按 `数据库模型.md` 权限边界必须由人工在目标环境执行。

## R1 合并 PostgreSQL 持久化双层（中高）

- 问题：`db/training` 与 `adapters/postgres` 双向耦合，同一持久化层被拆成互指两半。已核对的双向 import：
  - `db/training/write.mjs` → `adapters/postgres/index.mjs`、`adapters/postgres/incremental-write.pg.mjs`
  - `db/training/read.mjs` → `adapters/postgres/source-batch-repository.pg.mjs`
  - `db/training/archive.mjs` → `adapters/postgres/archive-repository.pg.mjs`
  - 反向：`adapters/postgres/core-day-repository.pg.mjs` → `db/training/read.mjs`
  - 反向：`adapters/postgres/training-analysis-repository.pg.mjs` → `db/training/config.mjs`
- 方案：以 `adapters/postgres` 为唯一 PostgreSQL 适配层落点，将 `db/training` 中属纯适配职责的读写实现迁入或明确单向依赖，消除反向 import；删除 `db/training/archive.mjs` 等纯转发文件，调用方直接引用适配层。
- 影响面：`src/db/training/*`、`src/adapters/postgres/*` 及其所有 import 方（含 `telegram-sync`、`feishu-sync`、tools、site 读取）。
- 外部行为：不变（仅移动实现与调整 import 路径）。
- 验证：全量测试（62 个测试文件）+ `npm run build` + `git diff --check`；重点跑入库、读取、分析、站点构建相关测试。
- 前置：低风险档 R5、中风险档 R4 先完成。建议阶段内细分小步提交。

## R3 共享编排器去 telegram 化命名（中高）

- 问题：渠道无关主链路以 `telegram` 命名，飞书 import telegram 用例，语义误导。已核对：
  - `runMessageSync` 定义在 `src/app/use-cases/telegram-sync.use-case.mjs:95`。
  - `feishu-sync.use-case.mjs` import `runMessageSync` 及 `telegram-sync/image-processing.mjs` 的 `recognizeBatch`、`telegram-sync/status.mjs`。
  - `adapters/feishu/sync-batch-logic.adapter.mjs` import `adapters/telegram/sync-batch-logic.adapter.mjs` 的 `groupSourceMessages`。
- 方案：将 `runMessageSync` 及真正渠道无关的编排逻辑抽到中性模块（如 `src/app/use-cases/message-sync.use-case.mjs`），`telegram-sync` / `feishu-sync` 各自只保留渠道特有装配；对确属公共的 `groupTelegramUpdates`、`processTelegramBatch`、`persistTelegramImageBatchIncremental` 等统一到 source 语义。一次性完成改名并更新全部引用，不保留旧名 re-export 兼容层（符合前提 2）。
- 影响面：`app/use-cases/*`、`adapters/telegram|feishu/*`、相关测试与文档源码入口表。
- 外部行为：不变（命令、识别、入库结果一致）。
- 验证：Telegram 与飞书同步全链路测试；`源码事实入口` 表同步更新。
- 前置：R4（缩小改名面）、R1（持久化层稳定后再改编排命名）先完成。

## R6 处置数据库遗留表（高，不可逆，需用户单独批准）

- 问题：遗留 telegram 表仍在 dev/main SQL 导出中，代码已不引用。**已核对修正**：实际为 **4 张表** + 1 序列，原方案漏写 `telegram_recognition`：
  - `ingest.telegram_batch`
  - `ingest.telegram_message`
  - `ingest.telegram_pending_batch`
  - `ingest.telegram_recognition`
  - 序列 `ingest.telegram_pending_batch_pending_id_seq`（dev 导出中 `setval=17`，提示表内可能有历史数据）
- 已核对的外键依赖（决定 DROP 顺序）：
  - `telegram_message.batch_id` → `telegram_batch`
  - `telegram_recognition.batch_id` → `telegram_batch`、`telegram_recognition.message_id` → `telegram_message`
- 代码引用核对：四张表名在 `src/` 中作为表引用零命中（此前 grep 命中的 `telegram_message_id` 是其他表的列名，非这些表本身）。新主链路使用来源无关表 `source_batch`、`source_message`、`recognition_run`、`pending_task`（均被代码引用）。
- 方案：本项只产出"待人工执行的清理清单"，不由重构代码自动执行。按 `数据库模型.md` 权限边界，由 `training_writer` 或 DBA 在目标环境手工执行、验收、再重新导出 SQL；日常 workflow 不做 DDL。dev/main 分别独立操作，不混写业务数据。
- **表结构变更约束（见 `CLAUDE.md`）**：任何表结构改动必须在 `sql/dev-sql/update-dev-sql/` 目录提供一份可直接执行的 SQL 文件，由用户手动在 dev 数据库执行；AI 不直接连库执行 DDL。文件命名沿用现有 `YYYYMMDD_简述.sql` 约定（参照 `20260713_remove_system_parameter_monitoring.sql`），内部按"先删子表/检查历史，后删主表与序列"组织，并在文件头注释说明用途与执行顺序。
- 建议 DROP 顺序（先核对历史与依赖，再执行）：
  1. 确认无外部对象依赖、确认历史数据无需保留。
  2. `DROP TABLE ingest.telegram_recognition;`（先删依赖 message/batch 的子表）
  3. `DROP TABLE ingest.telegram_message;`
  4. `DROP TABLE ingest.telegram_batch;`
  5. `DROP TABLE ingest.telegram_pending_batch;`
  6. `DROP SEQUENCE IF EXISTS ingest.telegram_pending_batch_pending_id_seq;`
  7. 重新导出 `sql/dev-sql`（或 `sql/main-sql`）并运行 `check:data-consistency`。
- 影响面：仅数据库结构与 `sql/dev-sql`、`sql/main-sql` 导出文件。
- 外部行为：不变（表本就无生产引用）。
- 风险提示：不可逆 DROP，需用户明确批准后再由人工执行；参照既有脚本 `sql/dev-sql/update-dev-sql/20260713_remove_system_parameter_monitoring.sql` 的"先删子表/检查历史，后删主表与序列"模式。

## 实施顺序

1. R1 合并 PG 双层（前置：R5、R4）。
2. R3 去 telegram 化改名（前置：R4、R1）。
3. R6 遗留表清理清单（用户单独批准 → 人工执行，dev/main 分别操作）。

每阶段结束：相关测试 → `git diff --check` → 中文 commit（当前 `dev` 分支）。R1、R3 变动面大，阶段内再细分小步提交。

## 明确不做

- 不改命令别名、帮助文本、页面路由与主题模板产物。
- 不改 workflow 触发链路、队列 DO 命名、pending 消费策略。
- 不保留旧名 re-export 兼容层。
- 不在同步链路中新增任何运行时 DDL 或全量扫描。
