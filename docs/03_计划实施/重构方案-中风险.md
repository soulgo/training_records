本文件是《整体重构优化方案.md》按风险拆分出的一份，只包含中风险项。落地后按 `docs/05_日常规则/实施规划落地文档同步规则.md` 写回长期文档并删除本文件。

## R4 拆分超大文件（中风险）

- 问题：单文件职责过多，阅读与改动风险高。当前行数已核对准确：

  | 文件 | 行数 | 顶层函数数 |
  | --- | --- | --- |
  | `src/adapters/telegram/sync-batch-logic.adapter.mjs` | 1857 | 64 |
  | `src/app/use-cases/telegram-sync.use-case.mjs` | 1344 | 39 |
  | `src/app/use-cases/image-recognition.use-case.mjs` | 1168 | 43 |
  | `src/db/training/write.mjs` | 1079 | — |
  | `src/app/use-cases/telegram-sync/thought-artifacts.mjs` | 940 | — |
  | `src/adapters/postgres/archive-repository.pg.mjs` | 875 | — |
  | `src/app/use-cases/telegram-sync/image-processing.mjs` | 862 | — |
  | `src/app/use-cases/telegram-sync/status.mjs` | 818 | — |
  | `src/site/monitor-view.mjs` | 738 | — |
  | `src/adapters/postgres/core-row-writer.pg.mjs` | 687 | — |

- 方案：按已有职责边界纯物理拆分（不改逻辑），优先耦合中枢：
  1. `sync-batch-logic.adapter.mjs`（1857）→ 命令解析 / 消息分组 / 批次分析 / Markdown 应用 / 并发工具 分文件。
  2. `telegram-sync.use-case.mjs`（1344）→ env 装配 / 批次路由 / 随想处理 / provider 装配 分文件。
  3. `image-recognition.use-case.mjs`（1168）→ 缓存 / provider 与 fallback / schema 请求 / 解析校验 分文件。
- 拆分以"移动 + 精确 import"为主，禁止顺手改行为；每拆一个文件立即跑相关测试。
- 影响面：上述文件及其 import 方。
- 外部行为：不变。
- 验证：逐文件拆分后即时测试 → 最终全量测试（62 个测试文件）+ `npm run build` + `git diff --check`。
- 顺序建议：先做 `sync-batch-logic.adapter.mjs`（飞书也复用其 `groupSourceMessages`，改动前先固定测试基线），再做两个 use-case。
- 与 R3 的关系：R4 只搬不改名；跨渠道函数改名属 R3（高风险档）。R4 应先于 R3，缩小 R3 的改名面。

## R2-A（可选）core/domain 下沉稳定契约（中风险）

仅当 R2 取向选 A 时纳入本档，否则见《重构方案-低风险.md》R2-B。

- 方案：把 `training-domain.mjs` 中被 Core 依赖的稳定契约类工具（如 `buildTrainingDay`、`emptyNutrition`、`emptySleep`、类型规范化）下沉到 `core`；Domain 的 Markdown 解析类逻辑保留在 `domain` 并单向依赖 Core。
- 影响面：`src/core/entities/*`、`src/core/services/*`、`src/domain/training/*` 及 import 方。
- 外部行为：不变。
- 验证：解析、合并、快照构建相关测试 + 站点构建。
