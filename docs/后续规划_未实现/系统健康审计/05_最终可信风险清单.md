# 最终可信风险清单

本清单是经代码逐条回溯验证后，**可以信任**的系统风险清单。每条均附代码证据位置，修正后的措辞以本目录验证文档为准。

---

## P0（立即关注）

### P0-1：webhook 路径 Action 并发不串行，串行完全依赖 DO

**可信度**：✔ 已验证

**代码证据**：
- `.github/workflows/sync.yml:37-39` concurrency group 在 webhook dispatch / repository_dispatch 路径为 `sync-<run_id>`（每 run 唯一，不串行）；仅手动/push 路径用固定 `sync`。
- `queue_task_id` 由 `cloudflare/sync-dispatch-queue.mjs:477-480` 注入，确认 webhook 一定走不串行分支。
- `test/github-workflows.test.mjs:691-711` 明确保护当前设计：webhook dispatch run 使用唯一 concurrency group，排序由 worker queue 控制，并禁止把所有 `repository_dispatch` 放进固定 pending queue。

**真实影响**：Action 层不阻止并发写 DB / 推送，串行性完全押在 DO 队列。若 DO 在 `workflow_dispatch` 已发出后查询 run 异常，可能重复 dispatch（见 P0-2）。同时，现有测试说明这是被保护过的设计选择，不能当成无争议补丁直接修改。

**修复方向**：先做设计决策：继续接受“DO 负责排序、Actions 使用唯一 group”，或改为 webhook sync 使用稳定 group（如 `sync-main-webhook`）让 Action 层也兜底串行。若选择后者，必须同步改写 `test/github-workflows.test.mjs` 中与之相反的断言。

### P0-2：DO 重试路径无幂等键，存在重复 dispatch 窗口

**可信度**：✔ 已验证（原报告未明确，验证补充）

**代码证据**：
- `cloudflare/sync-dispatch-queue.mjs:97-118` 中，`dispatchGithubTask` 成功后才调用 `findDispatchedRunId`；正常“未找到 run”会写入 `phase: 'wait_for_run'` 和 `dispatchStartedAt`。
- 如果 `findDispatchedRunId`（:104-110）抛错，catch 会调用 `retryOrDeadLetter(processing, error)`（:127-128），传入的仍是旧 `phase: 'dispatch'`。
- `retryOrDeadLetter`（:175-203）重试时 `storeProcessing({...processing, attempts, lastError}, delay)`，没有持久化 `dispatchStartedAt` 或 `wait_for_run`。
- 下次 alarm `continueProcessing`（:86-130）会再次 `dispatchGithubTask`（:98-102）。
- `dispatchGithubTask`（:369-385）对 GitHub `.../dispatches` API 无幂等键。
- 配合 P0-1 的 `sync-<run_id>` concurrency group，重复创建的两个 run 互不取消、并行执行同一同步。

**真实影响**：GitHub 已创建 run 后，如果 DO 在查询 run 阶段遇到网络/HTTP/响应解析异常，同一任务可能被 dispatch 两次，并发写库。

**修复方向**：`dispatchGithubTask` 成功返回后先持久化 `phase: 'wait_for_run'` 和 `dispatchStartedAt`，再查 run；重试时如果已有 dispatch identity / `dispatchStartedAt`，必须先查已有 run，不能直接再次 dispatch。

### P0-3：同日 core 汇总来源被后到批次覆盖

**可信度**：✔ 已验证

**代码证据**：
- `src/adapters/postgres/incremental-write.pg.mjs:48-51`（`ensureCoreTrainingDayStub`）和 `:226-228`（`refreshCoreTrainingDaySummary`）对 `archived_date` ON CONFLICT 覆盖 `source_batch_id/source_channel`。
- `core.training_day` 主键仅 `archived_date`（`sql/training_records/core.sql:304`），单日一行。

**真实影响**：同日先 Telegram 后飞书批次，日汇总来源变成最后批次，无法反查所有贡献批次。

**修复方向**：`training_day` 增加 `source_batch_ids_json` 或明细表按行追踪；日汇总不承担审计职责。

### P0-4：随想 Markdown 备份先删后写，非原子

**可信度**：✔ 已验证

**代码证据**：`tools/export-training-markdown.mjs:143`（删除）→ `:162`（写入），无原子替换/暂存/回滚；`rm({force:true})` 静默吞错。

**真实影响**：进程中断/DB 异常/磁盘错误时工作区"已删除未重写"；diff 驱动提交会扩大损失（`markdown-backup.yml:97-105`）。

**修复方向**：先写临时目录 + 校验数量/关键 ID + 原子替换；提交前删除数量异常阈值。

## P1（中期修复）

### P1-1：双通道字段不一致——飞书 source id 哈希成数字塞进 telegram 字段

**可信度**：✔ 已验证（最大技术债）

**代码证据**：
- 哈希：`src/adapters/feishu/sync-batch-logic.adapter.mjs:18, 92-97`
- 写入 telegram_message_id/message_id：`telegram-batch-repository.pg.mjs:103,152`；`thought-repository.pg.mjs:243,317`
- 随想 edit/delete/move 回退 `findByTelegramMessageId`：`thought-repository.pg.mjs:93/139/182`；`getMissingTargetResult`（:224-230）纯 message_id
- 导出/文件名/去重绑定 telegramMessageId：`tools/export-training-markdown.mjs:160, 193-207`

**真实影响**：飞书随想文件名、编辑/删除定位依赖哈希数字 id，跨通道碰撞有覆盖/漏导风险。

**修复方向**：导出、随想文件名、编辑/删除、缓存 join 全部迁到 `(source_channel, source_chat_id, source_message_id)`；旧 telegram 字段仅作兼容别名。

### P1-2：识别缓存 join 未用 source identity

**可信度**：✔ 已验证

**代码证据**：`src/app/use-cases/image-recognition.use-case.mjs:296-307` join `m.message_id = r.message_id`，无 source 维度。

**真实影响**：跨通道 fileUniqueId 碰撞（实际概率低，因飞书 imageKey 与 Telegram file_unique_id 字符串空间不同）理论可能读错缓存。

**修复方向**：缓存查询改为 source identity join。

---

### P1-3：飞书复用 telegram 命名链路

**可信度**：✔ 已验证

**代码证据**：`feishu-sync.use-case.mjs:90` 复用 `runTelegramSync`；`pending-recognition.mjs:160` 表名 `telegram_pending_batch`；`feishu-sync.use-case.mjs:143-145` 前缀替换。

**真实影响**：排障口径混乱，按通道清理 pending/统计 AI 失败易误删/漏查。

**修复方向**：pending payload 强制写 sourceChannel；中期改通用 `message_pending_batch`。

---

### P1-4：Pages cache purge 失败使整条链路报失败

**可信度**：✔ 已验证

**代码证据**：`deploy-pages.yml:121-125, 130-131` 硬 `exit 1` → `sync.yml:537-538` 判定失败 → `:548-561` 通知 Telegram 失败。

**真实影响**：数据已入库并部署到 Pages，但 cache purge 失败/缺凭证时用户收到"同步失败"通知。

**修复方向**：cache purge 失败降级为 warning（`continue-on-error`），不阻断链路。

---

### P1-5：AI 单批多图无全局预算

**可信度**：✔ 已验证

**代码证据**：单图超时 `openai-compatible.adapter.mjs:90-94`；批并发上限 `telegram-sync.use-case.mjs:836-838`（默认3最大5）；全文无 batch/action 级 deadline。

**真实影响**：多图相册 + strict JSON 重试 + fallback 叠加时 Action 耗时不可控，超时进 pending，用户只见延迟/部分成功。

**修复方向**：单批设总 deadline，超预算直接 queue pending 并通知"已排队重试"。

---

### P1-6：AI fallback provider 不检查置信度

**可信度**：✔ 已验证（原"fallback 不一致"修正为此）

**代码证据**：`image-recognition.use-case.mjs:260-276` `shouldRetryWithFallbackProvider` 只看错误类型，不看 confidence；`normalizeRecognitionPayload:649-651` 仅钳制置信度加 warning，不触发换模型。

**真实影响**：低置信度结果不会自动换模型重试。

**修复方向**：低置信度策略纳入 fallback 触发条件。

## P2（结构优化）

### P2-1：运行时 schema preflight 直接 ALTER 生产表

**可信度**：✔ 已验证

**代码证据**：`schema-preflight.pg.mjs:8-112` ALTER TABLE ADD COLUMN + backfill UPDATE + set not null；运行时调用 `write.mjs:73`。

**真实影响**：迁移边界不清，权限不足时表现为业务链路故障；索引/约束/语义变更无法有序审计。

**修复方向**：preflight 降级为只读校验；正式迁移走 SQL migration + CI。

---

### P2-2：ai_call_log 主事务外 best-effort 写入

**可信度**：✔ 已验证

**代码证据**：`write.mjs:105-115` COMMIT 后写 ai_call_log，失败仅 stderr。

**真实影响**：业务成功不代表审计日志完整。

**修复方向**：关键 AI 调用日志纳入主事务或独立可靠写入。

---

### P2-3：随想编辑/删除/移动 DB-only，Markdown 不即时同步

**可信度**：✔ 已验证

**代码证据**：`telegram-sync.use-case.mjs:1264, 1267-1269` thought_edit(非替换图片)/delete/move 走 `buildDatabaseOnlyThoughtWriteResult`（:1274-1292）不动 Markdown。

**真实影响**：备份未及时跑时仓库 Markdown 与 DB 短期不一致。

**修复方向**：Markdown 备份定义为异步派生并明确告知；关键变更触发一次导出或站点构建前强制 DB 快照。

---

### P2-4：主 Worker 手动部署，代码与线上可能滞后

**可信度**：✔ 已验证

**代码证据**：`deploy-cloudflare-worker.yml:3-4` 仅 `workflow_dispatch`；dev `deploy-cloudflare-worker-dev.yml:3-12` push 自动。

**真实影响**：改 Worker 代码忘手动跑则线上跑旧版。

**修复方向**：主 Worker 部署接入 push 触发或定期巡检线上版本。

---

### P2-5：wrangler.toml 命名误导

**可信度**：✔ 已验证

**代码证据**：`wrangler.toml:1` `name = "feishu-sync-dispatch"` 实为双通道（入口 :1-13 双 handler，DO 绑定 :22-32 双通道）。

**真实影响**：认知负担，维护时易误判单通道。

**修复方向**：改名为 `sync-dispatch` 或 `multi-channel-sync`。
