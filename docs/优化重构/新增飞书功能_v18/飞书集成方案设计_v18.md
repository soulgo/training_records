# 飞书消息通道集成方案 v18

## 结论

新增飞书通道不复制 Telegram 同步主流程。飞书只新增通道适配层：事件接收、签名验证、消息标准化、飞书图片下载、飞书消息发送和 GitHub Actions 入口。图片识别、批次分析、随想写入、数据库 core 写入、Markdown 兼容层继续复用现有 Telegram 同步管线。

本轮目标：

- 飞书发送训练图片后，进入现有 AI 识别与 PostgreSQL 入库流程，core 数据写 `source_channel = 'feishu'`。
- 飞书发送 `/随想` 文本后，进入现有随想 DB 镜像流程；如随想包含图片附件，则复用现有图片 artifact 写入。
- 飞书 `/帮助`、`/分析` 可复用现有命令解析与回复逻辑。
- Telegram 行为保持不变。

本轮不做：

- 不重构核心域模型。
- 不把 `ingest.telegram_*` 泛化为统一多通道表。
- 不迁移 `core.thought` 主键。飞书随想使用稳定数字代理 ID 兼容现有 `telegram_message_id` bigint 主键，同时保留 `source_channel/source_message_id/source_chat_id` 作为真实来源标识。
- 不复制一份完整 Telegram use case。

## 文档审计修正

原方案中“新增 `src/app/use-cases/feishu-sync/image-processing.mjs`、复制通知系统、复制 tools 入口、独立飞书 pending queue、独立飞书 ingest 表”会产生大量重复代码，且与当前代码结构不一致。当前真实代码已经把同步调度集中在 `src/app/use-cases/telegram-sync.use-case.mjs`，图片识别在 `src/app/use-cases/telegram-sync/image-processing.mjs`，批次分析在 `src/adapters/telegram/sync-batch-logic.adapter.mjs`。飞书应通过依赖注入复用这些边界，而不是复制主流程。

## 目标链路

```text
飞书事件
  -> cloudflare/feishu-sync-dispatch-worker.mjs 验签与缓冲
  -> repository_dispatch: feishu_update
  -> .github/workflows/feishu-sync.yml
  -> npm run sync:feishu
  -> runFeishuSync
  -> resolveDispatchFeishuUpdates
  -> groupFeishuUpdates
  -> runTelegramSync 共享编排器
  -> recognizeBatch / analyzeTelegramBatch / persistNormalizedBatch
  -> 飞书通知
```

## 通道适配设计

### 1. 飞书消息标准化

新增 `src/adapters/feishu/sync-batch-logic.adapter.mjs`：

- `normalizeFeishuMessage(event)` 解析 `im.message.receive_v1`。
- 飞书原始 `message_id` 是字符串，不能直接写入当前 `core.thought.telegram_message_id`。适配层生成稳定数字代理 `messageId`，并保留：
  - `sourceChannel: 'feishu'`
  - `sourceMessageId: <飞书 message_id>`
  - `sourceChatId: <飞书 chat_id>`
  - `eventId: <飞书 event_id>`
- 图片消息转换为 Telegram-compatible message，`photos[].fileId` 使用飞书 `image_key`。
- 多图按同一 `chat_id` 的时间窗口分组，默认 3 秒。
- 分组后调用现有 `groupTelegramUpdates`，复用 `/随想`、`/帮助`、`/分析` 等命令解析。

### 2. 飞书图片识别

现有 `recognizeBatch` 增加通道无关的图片文件下载入口：

- Telegram 默认仍走 `resolveTelegramFileUrl` 或 Telegram inline 下载。
- 飞书强制使用 inline 模式：`fetchFeishuImageResource(message.sourceMessageId, imageKey)` 下载图片字节，再转成 `data:image/*;base64,...` 交给 AI Provider。
- 识别结果保留 `sourceMessageId`，便于飞书 ingest/审计关联。

### 3. 数据库写入

`persistNormalizedBatch` 增加 `sourceChannel` 参数：

- 默认仍为 `telegram`，Telegram 调用不变。
- 飞书图片批次传入 `sourceChannel: 'feishu'`。
- `persistTelegramImageBatchIncremental` 接收 `sourceChannel`，写入 core 子表和 `core.training_day`。
- 本轮不新增独立 `ingest.feishu_*` 表，仍用现有 ingest 审计表保存批次 payload。原因是飞书消息已经带 `sourceChannel/sourceMessageId`，复制一组表会增加维护面；后续若需要更强审计隔离，再做统一多通道 ingest 设计。

### 4. 飞书随想兼容

当前随想链路历史上使用 `telegram_message_id bigint` 作为稳定主键。为了不在本轮迁移表结构：

- 飞书 `message_id` 通过稳定 hash 生成安全整数代理 ID。
- 文本随想保持现有 DB-first 行为，不新增正文 Markdown 帖；Telegram 当前也是这个行为。
- 如果后续导出或历史兼容层生成飞书 Markdown，文件名使用 `YYYY-MM-DD-feishu-thought-<代理ID>.md`。
- 如果生成飞书 Markdown，front matter 额外写入：
  - `source_channel: feishu`
  - `source_message_id: <飞书 message_id>`
  - `source_chat_id: <飞书 chat_id>`
- 标签中的通道标签写 `飞书`，Telegram 继续写 `Telegram`。
- 编辑、删除、移动随想仍依赖现有 Telegram 数字定位习惯；飞书侧本轮只保证新建 `/随想`。

### 5. 飞书 API

新增 `src/adapters/feishu/feishu-api.mjs`：

- `getFeishuTenantAccessToken`：获取 tenant access token，支持内存缓存。
- `sendFeishuMessage`：发送文本消息。
- `fetchFeishuImageResource`：下载图片资源，返回 `{ data, contentType, filePath }`。

### 6. Cloudflare Worker

新增 `cloudflare/feishu-sync-dispatch-worker.mjs`：

- 支持 `url_verification` challenge。
- 使用 Web Crypto API 验证 `X-Lark-Signature`。
- 校验 `FEISHU_VERIFICATION_TOKEN`。
- 图片事件进入 Durable Object 缓冲，默认 3 秒。
- 调用 GitHub `repository_dispatch`，`event_type` 默认为 `feishu_update`；单条事件 payload 使用 `feishu_update`，缓冲批量事件使用 `feishu_updates`。

### 7. CI/CD

新增：

- `wrangler.feishu.toml`
- `.github/workflows/feishu-sync.yml`
- `.github/workflows/feishu-sync-dev.yml`

`package.json` 新增：

```json
{
  "sync:feishu": "node tools/feishu-sync.mjs",
  "feishu:sync": "npm run sync:feishu"
}
```

## 环境变量

| 变量名 | 用途 |
| --- | --- |
| `FEISHU_APP_ID` | 飞书应用 App ID |
| `FEISHU_APP_SECRET` | 飞书应用 App Secret |
| `FEISHU_ENCRYPT_KEY` | Worker 验签密钥 |
| `FEISHU_VERIFICATION_TOKEN` | 飞书事件 token 校验 |
| `FEISHU_ALLOWED_CHAT_IDS` | 允许接入的飞书 chat_id，逗号分隔 |
| `FEISHU_SYNC_TRANSPORT` | 固定 `webhook` |
| `FEISHU_SYNC_NOTIFY` | 是否发送飞书通知 |
| `FEISHU_SYNC_NOTIFY_STAGE` | `inline` 或 `after_action` |
| `FEISHU_SYNC_RESULT_PATH` | 同步结果 JSON 路径 |
| `FEISHU_RECOGNITION_IMAGE_INPUT_MODE` | 飞书图片输入模式，本轮使用 `inline` |

AI、数据库和训练分析变量继续复用现有 `AI_*`、`TRAINING_DB_*`、`TRAINING_ANALYSIS_GOAL`。
