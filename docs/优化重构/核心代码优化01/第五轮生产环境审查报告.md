# 第五轮生产环境审查报告

## 审查结论

本轮审查结论为：**有条件通过**。

当前 `docs/优化重构/核心代码优化01/` 已经能作为开发重构入口，并在本轮补充后具备生产运维 runbook 雏形；但若目标是“未来运维人员仅依靠文档处理线上问题”，仍必须把故障恢复、监控告警、数据恢复和上线演练纳入验收。系统已有部分自动重试、pending、dead-letter、Markdown 备份和 GitHub summary 能力，但这些能力分散在 Worker、GitHub Actions、AI 调度、数据库和历史维护文档中，不能只用 workflow conclusion 或单一日志判断生产成功。

生产运行必须按四层判断成功：

| 层级 | 成功含义 | 不能误判为成功的状态 |
| --- | --- | --- |
| Worker 接收 | Telegram/飞书 webhook 鉴权通过并成功进入队列或 dispatch | HTTP 200/202 后队列 dead-letter、前置 buffer dispatch 失败 |
| GitHub Action 执行 | `sync.yml` / `sync-dev.yml` 完成并产生 summary | Action success 但 `pending_replay`、`manual_intervention`、`partial_failed` |
| 业务入库 | batch 已 `stored/unchanged`，必要投影已刷新 | 仅完成 AI 识别、DB 写入 pending、日期不可信 |
| 用户可见 | 来源通道回执、页面或查询侧可见最新数据 | 通知失败被忽略、deploy/cache 未完成 |

## 告警建议

必须告警的异常：

| 告警 | 建议阈值 | 人工介入要求 |
| --- | --- | --- |
| Worker 5xx | 任意生产 webhook 5xx | 立即查 Cloudflare tail 和 Worker secret |
| buffered 后无 Action | 2 分钟内没有 queued/run | 查 DO alarm、GitHub token、repo dispatch 权限 |
| queue dead-letter | 任意出现 | 手工确认 taskId、payload、用户是否已通知 |
| Action failure 或 deploy failure | 任意 main 失败 | 判断数据是否已入库但页面未更新 |
| Action success 但业务失败 | `failureDisposition != none` 或 `persistenceStatus=pending_replay` | 区分自动重放和人工介入 |
| AI fallback 升高 | 10 分钟 fallback 使用率 > 30% | 查主 provider 状态、余额、限流 |
| AI schema failure | 每小时 >= 2 次 | 查模型输出、prompt、response_format |
| pending 堆积 | 最老 pending > 24 小时或 attempt_count 持续增长 | 判断 abandoned、手工恢复或暂停相关入口 |
| Markdown backup 失败 | 最近一次失败或连续 changed 未 commit | 修复 DB/schema/Git 权限后重新导出 |
| AI/Actions 成本异常 | 超出日预算或单 run 耗时异常 | 降低并发、暂停批量图片、检查异常重放 |

## 数据恢复建议

恢复原则：

1. 先冻结高风险写入入口，再保留事故证据。
2. 恢复前导出当前数据库快照，至少导出目标日期相关 `core.*`、`ingest.*` 行。
3. 优先使用 ingest/pending 中的原始 payload 和 recognition 作为图片链路恢复来源。
4. `训练记录.md` 是可写回数据库的维护输入，不是无风险只读备份；导入前必须审核 affected days。
5. 恢复后必须验证 `core.*` 明细、`core.training_day` 投影、`npm run build:data` 和用户可见结果。

恢复来源优先级：

| 场景 | 优先来源 | 注意事项 |
| --- | --- | --- |
| AI 已识别但 DB 写入失败 | `ingest.telegram_batch/message/recognition`、pending batch | 保留 `source_channel` 和 batchId，避免来源覆盖 |
| pending 长期未恢复 | `ingest.telegram_pending_batch` | 超过阈值应标记 abandoned 或人工处理 |
| AI 错误写入 | batchId 对应 recognition JSON、目标日期 core 行 | 先冻结 sync，再按日期回滚/修正 |
| 数据误删 | DB 快照、`archive.*`、Git 历史、Markdown 备份 | Markdown 导入是 whole-day replacement，必须先 dry-run |
| 随想页面丢失 | `core.thought`、Git 历史中的 posts/images | 页面 artifact 不是事实源，需同步回 DB |

`实施checklist.md` 已新增“阶段 7：生产上线验收”。该阶段应作为生产上线硬门槛，重点覆盖：

- 数据恢复验证：`maintenance:inspect`、`check:data-consistency`、pending resolved/abandoned、archive/Markdown 恢复。
- 监控告警验收：Worker、queue、Action 业务状态、pending、AI、Markdown backup。
- 运维接手验收：新接手人员必须能画出 Telegram/飞书 -> Worker -> Queue -> Action -> AI -> DB -> Pages 链路，并能解释 Action success 与业务 stored 的区别。

在阶段 7 完成前，`实施checklist.md` 只能视为开发实施清单，不能视为完整生产上线验收标准。

## 最终判断

当前重构文档经过本轮补充后，已经从“指导开发”推进到“可以指导生产运维准备”。但生产级长期稳定运行还依赖以下条件全部完成：

1. 阶段 7 生产上线验收全部通过。
2. 核心告警能覆盖 workflow success 但业务失败的状态。
3. pending、dead-letter、Markdown backup 和 AI fallback 都有可观测指标和人工处理入口。
4. 数据恢复至少完成一次演练，证明误删、AI 错写和 Markdown 导入都可控。
5. 新接手人员能只依靠核心文档完成一次故障定位和一次恢复演练。

因此本轮结论是：**文档已达到生产审查可用状态，但系统上线前仍需按阶段 7 完成故障、容灾、数据恢复和告警验收。**
