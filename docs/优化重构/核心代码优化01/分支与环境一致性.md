# 分支与环境一致性设计

## dev / main 环境一致性设计

| 项 | main | dev | 一致性规则 |
| --- | --- | --- | --- |
| Worker 配置 | `wrangler.toml` | `wrangler.dev.toml` | 入口同为 `cloudflare/sync-dispatch-worker.mjs` |
| Dispatch type | `telegram_update` / `feishu_update` | `telegram_update_dev` / `feishu_update_dev` | 后缀只允许 dev 差异 |
| Sync workflow | `.github/workflows/sync.yml` | `.github/workflows/sync-dev.yml` | 步骤结构应保持同构 |
| DB URL | `secrets.TRAINING_DB_URL` | `secrets.DEV_TRAINING_DB_URL` | dev 严格使用独立 DB，无 fallback |
| Telegram token | `secrets.TELEGRAM_BOT_TOKEN` | `secrets.DEV_TELEGRAM_BOT_TOKEN` | dev 严格使用 dev token，无 fallback |
| Feishu app | `secrets.FEISHU_*` | `secrets.DEV_FEISHU_*` fallback `secrets.FEISHU_*` | 飞书允许 dev→main fallback，需显式记录 |
| 页面校验 URL | `vars.CLOUDFLARE_PAGES_BASE_URL=https://soulgo.chat` | `vars.CLOUDFLARE_PAGES_DEV_BASE_URL=https://training-records-dev.pages.dev` | dev/main 校验 base URL 分离 |
| Telegram webhook URL | `vars.TELEGRAM_WEBHOOK_URL=https://feishu.soulgo.chat/telegram` | `vars.DEV_TELEGRAM_WEBHOOK_URL=https://feishu-dev.soulgo.chat/telegram` | 复用飞书域名下 `/telegram` 路由 |
| Node.js 版本 | `node-version: 22`（`actions/setup-node@v4`） | 同 main | dev/main 应使用同一 Node 版本 |
| GitHub Actions runtime | Node.js 24（runner 实际），`actions/checkout@v4` 和 `actions/setup-node@v4` 内部 target Node.js 20 | 同 main | Action 版本弃用警告需关注 |
| npm 依赖安全 | `npm audit --omit=dev` 报告 4 个 vulnerable packages（`dompurify`、`form-data`、`js-yaml`、`ws`） | 同 main | dev/main 共享 package-lock.json |
| 测试文件数 | 38 个 `.test.mjs` 文件 | 同 main | 测试覆盖应保持一致 |
| Workflow 文件数 | 9 个 `.yml` 文件 | 同 main | 包括 ci-tests、markdown-backup、refresh-telegram-webhook 等辅助 workflow |

## 配置隔离策略

### P0：机器可读配置契约

建议新增 `docs/优化重构/核心代码优化01/env-contract.json` 或测试 fixture：

```json
{
  "main": {
    "worker": "feishu-sync-dispatch",
    "dispatchTypes": ["telegram_update", "feishu_update"],
    "branch": "main"
  },
  "dev": {
    "worker": "sync-dispatch-dev",
    "dispatchTypes": ["telegram_update_dev", "feishu_update_dev"],
    "branch": "dev"
  }
}
```

### P1：启动前 preflight

同步命令启动前检查：

- channel 需要的 token/secret 是否存在。
- DB URL 是否和分支匹配。
- AI provider 是否完整。
- result path 是否可写。
- GitHub event payload 是否和 channel 匹配。
- dev 飞书是否实际使用 `DEV_FEISHU_APP_ID` / `DEV_FEISHU_APP_SECRET`；若 fallback 到生产 `FEISHU_*`，至少输出 warning。

| 变量 | 代码/配置状态 | 建议 |
| --- | --- | --- |

| `AI_TIMEOUT_MS` | 未配置，飞书识别已观察到 37.7s | **建议立即配置 45000**，防止 Action 卡死 |
| `AI_CONCURRENCY` | 未配置，代码默认 3 | **建议配置 2 作为飞书图片限流策略**；这不是修复单并发默认值 |
| `TELEGRAM_RECOGNITION_MODEL` | 未配置 | 为空时使用主 `AI_MODEL` |
| `FEISHU_API_BASE_URL` | 未配置 | 默认 `https://open.feishu.cn` |
| `TRAINING_ANALYSIS_SNAPSHOT_POLICY` | 代码已支持；仓库级 Variable 未在本快照确认 | `/analysis` 专用：`strict_db` 或 `allow_markdown_fallback`；不要误用 `TRAINING_SNAPSHOT_STRICT_DATABASE` 当作当前分析 strict 开关 |
| `FEISHU_SIGNATURE_MAX_SKEW_SECONDS` | Worker 已支持；未配置时默认 300 秒；仓库级 Variable 未在本快照确认 | 飞书 webhook 签名 timestamp 新鲜度窗口，建议 300 秒；真实飞书 replay 演练仍需端到端验收 |
| `MAX_IMAGE_DOWNLOAD_BYTES` | Telegram/飞书图片下载入口已支持；未配置时默认 20MB | Telegram/飞书图片下载统一大小上限；真实平台 5MB/15MB/30MB 图片仍需端到端验收 |
| `AI_CONCURRENCY_MAX` | 代码已支持；未配置时 clamp 上限默认 5；仓库级 Variable 未在本快照确认 | 防止 `AI_CONCURRENCY` 被误设过高，建议 5；真实 dev/main 连续图片峰值仍需观测 |

> 状态口径：上表的“未确认仓库级配置”只说明本轮 GitHub Variables 快照未证明已经配置，不等同于本地代码缺少支持。代码支持项仍需通过 dev/main workflow 实跑、summary 和真实平台日志完成最终验收。

### GitHub Environment

- 当前只有 `github-pages` environment。
- environment-level variables/secrets 为空。
- 因此环境隔离不能依赖 GitHub Environment secrets，必须靠 repo-level secrets/vars + workflow 条件 + preflight。

## 功能一致性保障

| 功能 | main/dev 一致性规则 | 验证 |
| --- | --- | --- |
| Telegram 图片 | dev 与 main 使用同一识别 prompt 和 schema | recognition 测试 |
| 飞书图片 | inline input 默认一致 | feishu sync 测试 |

| Pages 部署 | DB-only 内容变更都能触发部署 | workflow 测试 |

## 防止环境漂移方案

### P1：合同测试

扩展现有：

```bash
node --test test/cloudflare-config.test.mjs test/github-workflows.test.mjs
```

覆盖：

- Worker main 文件一致。
- DO binding 名称一致。
- dispatch type 符合环境。
- workflow channel choice 一致。
- dev workflow 不引用 main DB secret。
- main workflow 不引用 dev DB secret。
- dev Feishu fallback 到 main Feishu secrets 时必须被测试或 preflight 标注。
- workflow 中所有 `run:` shell 脚本应能通过解析后的 `bash -n`。
- `TRAINING_SNAPSHOT_STRICT_DATABASE` 与 `/analysis` strict 策略必须分开测试；分析 strict 只认分析专用策略或等价代码开关。
- `AI_CONCURRENCY` 必须测试默认值、飞书建议值和最大值 clamp。
- `MAX_IMAGE_DOWNLOAD_BYTES` 必须同时覆盖 Telegram 与飞书下载入口。
- 飞书 webhook 必须测试 timestamp skew 与 nonce replay，不只测试 HMAC 正确性。

### P1：运行时 summary

每次 sync summary 输出：

- channel
- branch
- db app name
- snapshot source
- dispatch type
- task id
- AI model
- AI timeout/concurrency clamp 后的实际值
- snapshot source / analysis snapshot policy
- `dateSources` / `warnings` / `dateConfidence`（图片任务）

不得输出 secret。

## 生产监控与告警建议

当前仓库没有独立监控平台配置，生产监控应先从 GitHub Actions、Cloudflare Worker tail/metrics、PostgreSQL 查询和 AI provider 账单/状态页建立最低闭环。

### 必须监控的指标

| 层级 | 指标 | 来源 | 建议阈值 |
| --- | --- | --- | --- |
| Worker | 请求 4xx/5xx、异常数、DO alarm 触发、buffered 后是否 flushed | Cloudflare Workers metrics / tail | 5xx 任意出现告警；buffered 后 2 分钟无 queued 告警 |
| Queue | `SyncDispatchQueue` queue age、attempts、deadLetters、run lookup timeout | Durable Object 日志/存储 | dead-letter 任意出现 P1；queue age > 10 分钟 P2 |
| GitHub Actions | sync/deploy conclusion、queued time、run duration、deploy wait timeout | GitHub Actions | sync failure P1；deploy failure P1；queued > 10 分钟 P2 |
| 业务状态 | `taskStatus`、`persistenceStatus`、`failureDisposition`、failed messageIds | GitHub step summary / result JSON | `pending_replay`、`manual_intervention`、`partial_failed` 任意出现进入人工看板 |
| AI | primary timeout、fallback 使用率、schema parse failure、单 run recognition 耗时、并发值 | stderr summary / provider dashboard | primary timeout >=3/15min；fallback 使用率 >30%/10min；schema failure >=2/h |
| DB | 连接失败、pending 数量、pending 最老时间、core/archive 行数差异、查询耗时 | `maintenance:inspect` / SQL / `check:data-consistency` | pending > 0 超 30 分钟 P2；pending > 10 或 oldest > 24h P1 |
| Markdown 备份 | backup run 失败、changed 但未 commit、导出可解析性 | `markdown-backup.yml` summary | 连续 2 次失败 P1；手动导出失败 P2 |
| 成本/容量 | AI token/费用、Action 分钟、日志量、DB 表大小 | Provider/GitHub/Postgres | 90 天趋势异常增长需复盘 |

### 必须告警的异常

- Worker 返回 `github_dispatch_failed`、`missing_github_token`、`telegram_help_failed`、`invalid_encrypted_payload` 激增。
- `SyncDispatchQueue` dead-letter 或 workflow run 查找超时。
- `Sync (Main)` / `Deploy GitHub Pages` 失败，或 deploy 等待超过 15 分钟。
- Action success 但 summary 中出现 `persistenceStatus=pending_replay`、`failureDisposition=auto_retry/manual_intervention`。
- `ingest.telegram_pending_batch` pending 超过阈值，或同一 batch attempt_count 持续增长。
- 主备 AI 同时失败、AI schema parse failure 连续出现、AI 单张识别耗时接近或超过 timeout。
- `Markdown Backup` 连续失败，或导出后 `训练记录.md` 不能被解析。

### 需要人工介入的问题

| 问题 | 人工动作 |
| --- | --- |
| `manual_intervention` / 日期缺失 / 日期冲突 | 要求用户重发可靠日期截图，或人工确认后用维护入口修正 |
| pending 超过 24 小时 | 判断是否继续重放、标记 abandoned，或手工恢复 |
| Cloudflare/GitHub 平台故障 | 暂停批量发送图片，保留 webhook/队列证据，平台恢复后重放 |
| AI 错误写入 core | 冻结相关 sync，按 batchId 定位 ingest/core，执行受控恢复 |
| Markdown 导入前 | 审核 affected days，确认 Markdown 比 DB 更可信 |

## 回滚方案

- 合同测试失败不影响生产，先修配置。
- preflight 可用 `SYNC_PREFLIGHT_STRICT=false` 临时关闭。
- dev/main 配置文件不做自动覆盖，所有改动走 PR。
