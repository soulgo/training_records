## 审计结论

- **结论**：有条件通过。
- **汇总**：P0:2，P1:13，P2:7，P3:0。
- **关键纠偏**：
  - `caption/text/question` 由 `JSON.stringify` 包装进请求体，普通引号、反斜杠、Emoji 不会直接破坏 JSON；真实风险是无长度上限、控制字符和 prompt 注入边界。
  - `AI_CONCURRENCY` 未配置时默认 3，`mapWithConcurrency()` 有 worker 上限；真实风险是 env 可被误设过高。
  - 严格 JSON 重试成功后会回到 recognition 结果路径并随 `upsertRecognitions()` 写库，不能写成“确定不更新缓存”；真实缺口是缺少三路径缓存验收。
  - `groupTelegramUpdates()` 的 thought key 顺序问题不能写成已确认 bug；真实缺口是同批 create/reply/edit/move fixture 不足。

## 最终建议

1. **先修 P0/P1 行为边界，不先抽大架构**：AI timeout、payloadHash 原子性、pending lock/abandoned、Markdown sleep、core 来源覆盖、Telegram buffer 恢复。
2. **先补测试再重构**：尤其是 Markdown sleep、analysis snapshot policy、AI 三路径缓存、同批 thought 命令、飞书 replay、workflow summary gate。
3. **数据安全高于性能**：core 来源不能被覆盖丢失；whole-day replacement 必须有 affected days 与 dry-run；pending replay 必须可终止。
4. **AI 容灾必须可观测**：Action success 不能代表业务 success；summary 至少输出 `taskStatus/failureDisposition/persistenceStatus/dateConfidence/snapshotSource`。
5. **保留纠偏结论**：不要在实施时继续按“prompt 会破坏 JSON”“AI 并发无限”“严格 JSON 重试不写缓存”“groupTelegramUpdates 已确认顺序 bug”这些不准确假设推进。
