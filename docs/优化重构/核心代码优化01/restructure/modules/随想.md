# 模块级重构方案：随想

## 当前问题

| 问题 | 证据 | 优先级 | 风险等级 |
| --- | --- | --- | --- |
| 随想仍混在通用同步批次中处理 | `runTelegramSync()` 内部分流 `isThoughtBatchKind()` | P1 | P2 |
| source identity 已落地但历史数据仍需验收 | 原始审计发现 `core.thought.telegram_message_id` 承载飞书兼容 ID；当前本地/schema 合同已用 `source_channel/source_chat_id/source_message_id` 作为主身份，`telegram_message_id` 保留 legacy fallback | P1 | P2 |
| Markdown 备份与 DB mirror 的边界容易混淆 | 同步写 DB，Markdown 由备份 workflow 派生 | P2 | P2 |
| 飞书随想与 Telegram 附件能力不完全一致 | 飞书当前不支持 Markdown 文档附件正文 | P2 | P3 |
| 飞书 message_id 需要安全整数代理 | `src/adapters/feishu/sync-batch-logic.adapter.mjs` 用 `buildStableSafeInteger()` 生成兼容旧 bigint 字段的 `messageId` | P1 | P2 |

## 设计缺陷

- 领域概念是“随想”，但部分兼容列和函数名仍带 Telegram 语义。
- 编辑、删除、移动属于随想命令状态机，但当前依赖通用 batch 分流。
- 图片 artifact 与正文 mirror 分属文件系统和 DB，审计链路不统一。
- 飞书真实 ID 是字符串 `sourceMessageId`；当前本地/schema 合同已保存 `source_channel/source_chat_id/source_message_id` 并以其作为主身份，safe integer 代理只作为旧列兼容。真实历史数据迁移和线上回放仍需单独验收。

## 重构方案

### P1：抽取 ThoughtUseCase

新增应用服务：

- `createThought(input)`
- `editThought(input)`
- `deleteThought(input)`
- `moveThought(input)`
- `attachThoughtImages(input)`

输入使用通用字段：

| 字段 | 说明 |
| --- | --- |
| `channel` | telegram / feishu |
| `sourceMessageId` | 原始通道消息 ID |
| `sourceChatId` | 原始 chat ID |
| `body` | 正文 |
| `module` | workout / misc / body_feedback |
| `imageRefs` | 图片引用 |

### P1：新增跨渠道随想 ID

新增 `thought_id`：

```text
thought_id = sha256(channel + ":" + sourceChatId + ":" + sourceMessageId)
```

旧 `telegram_message_id` 保留一轮作为兼容列。

迁移验收不能只验证新数据。当前本地 repository 会优先按 `source_channel/source_chat_id/source_message_id` 查找编辑、删除、移动目标，并保留旧 `telegram_message_id` fallback；飞书历史数据仍可能存在 `buildStableSafeInteger()` 代理写入的 legacy 列。新增 `thought_id` 后必须同时覆盖：

- 旧 Telegram 整数 message_id 的 edit/delete/move。
- 旧飞书 safe integer 代理 ID 的 edit/delete/move。
- 新 `sourceMessageId` / `sourceChatId` / `thought_id` 查找。
- 查不到目标时仍返回 `not_found`，不新建错误随想。

### P2：分离 Markdown 派生

随想同步只写 `core.thought` 和 image refs，不直接承诺 Markdown 文件存在。Markdown 由 `export:markdown` 或备份 workflow 派生，并在任务结果中标记：

- `storageStatus: db_stored`
- `markdownStatus: derived_later`

### P1：飞书 / Telegram 随想差异显式建模

| 维度 | Telegram | 飞书 | 设计要求 |
| --- | --- | --- | --- |
| 原始消息 ID | 整数 `message_id` | 字符串 `message_id` | `sourceMessageId` 必须保留原值 |
| 兼容主键 | 可直接使用 `message_id`；legacy fallback 仍保留 | 原始 `sourceMessageId/sourceChatId` 已作为主身份；safe integer 代理只作旧列兼容 | 新 `thought_id` 包含 channel/chat/sourceMessageId |
| Markdown 附件正文 | 支持 `.md/.markdown` document 覆盖正文 | 当前不支持 | 文档和回执必须说明能力差异 |
| 图片引用 | Telegram file_id/file_unique_id | 飞书 image_key + tenant token 下载 | imageRefs 需带 channel/source |
| 回执 | Telegram Bot API | 飞书 tenant token + `im/v1/messages` | 错误分类分开统计 |

附件 `/Users/soulgo/Downloads/bug 报告.md` 的关键结论应保留：`thought_edit` / `thought_move` 的 DB-only 不是 bug 本身，正确链路是写入 `core.thought` 后由 deploy 严格数据库快照导出 Markdown；不建议把同步阶段直接编辑 Markdown 作为主修复。

## 接口变更影响

| 接口 | 影响 | 兼容策略 |
| --- | --- | --- |
| `runTelegramSync()` | 内部调用 ThoughtUseCase | 外部 JSON summary 保持 `batchResults` |
| `runFeishuSync()` | 不再注入 Telegram placeholder env 处理随想 | 保留 `buildFeishuSyncReport()` 输出 |
| `core.thought` 查询 | 可按 `thought_id` 查询 | 旧 `telegram_message_id` 查询保留 |

## 数据结构影响

建议 additive migration：

```sql
alter table core.thought add column if not exists thought_id text;
alter table core.thought add column if not exists source_message_id text;
alter table core.thought add column if not exists source_chat_id text;
create unique index if not exists ux_core_thought_thought_id on core.thought(thought_id);
```

数据回填：

```text
thought_id = sha256(coalesce(source_channel, 'telegram') + ':' + telegram_chat_id + ':' + telegram_message_id)
source_message_id = telegram_message_id::text
source_chat_id = telegram_chat_id::text
```

飞书历史数据不能只把 `telegram_message_id::text` 当作最终 source message。当前 safe integer 只能保证旧 bigint 主键兼容，不等价于飞书原始字符串 `message_id`。如果历史 ingest payload 中能恢复原始 `sourceMessageId`，应优先回填原值；无法恢复时必须标记为兼容代理值，避免后续把它当作飞书 API 原始 ID 使用。

## 风险评估

| 风险 | 等级 | 证据/原因 | 控制 |
| --- | --- | --- | --- |
| 旧随想编辑命令找不到目标 | P1 | 现有旧数据仍以 `telegram_message_id` 定位 | 查询先按新 `thought_id`，再按旧 `telegram_message_id` fallback |
| Markdown 导出路径变化 | P2 | 随想页面/备份仍依赖旧 `markdown_path` | 保持 `markdown_path` 旧字段，导出层单独迁移 |
| 飞书 ID 映射冲突 | P2 | 飞书真实 ID 是字符串，旧字段是 Telegram bigint 语义 | `thought_id` 必须包含 channel 和 chat |
| 飞书 safe integer 与原始 message_id 断链需保留回归保护 | P1 | 当前 DB/repository 已保存 `sourceMessageId/sourceChatId`，safe integer 代理不再是主身份；真实历史数据仍需确认是否可回填原始 ID | 所有 summary、DB 和导出路径同时保存 `sourceMessageId` |

## Bug 修复方案（本轮审计新发现）

### P2-9：连续随想 create/reply/edit/move 的同批可见性回归保护

**问题概述**

`groupTelegramUpdates()` 当前在解析到普通 thought 消息时会先把当前消息 key 加入 `knownThoughtMessageKeys`，并在 resolver `effects` 中再次加入。这意味着“提前注册必然导致同批后续 thought 找不到前序”不是已证实 bug。当前本地合同已用 fixture 锁住同一批连续发送 `/随想` 后立即 reply edit、explicit edit、delete、move 的可见性；后续抽取 `ThoughtUseCase` 或调整 resolver 顺序时必须保留该测试。

**实施状态（本地）**：已完成本地合同校准。`test/telegram-sync.test.mjs` 中 `groups same-batch thought create followed by reply edit, explicit edit, delete, and move targets` 覆盖 create 后 reply_edit、explicit_edit、delete、move 的 batch 顺序和目标 ID；真实 Telegram/飞书通道端到端仍需验收。

**1. 实施要求**

文件：`src/adapters/telegram/sync-batch-logic.adapter.mjs`
范围：第 136-164 行

不要在无 failing test 的情况下移动 `knownThoughtMessageKeys.add()`。后续正确实施顺序：

1. 保留同批顺序 fixture，确认当前行为。
2. 抽取 `ThoughtUseCase` 时保持 resolver effects 语义不变。
3. 如果 fixture 暴露真实顺序 bug，再调整 key 注册时机。

**2. 测试策略**

- **单元测试**：构造 `/随想 A` 后紧跟 reply edit 的 updates，断言 reply edit 能命中新建 thought。
- **单元测试**：构造 `/随想 A` 后紧跟 `/随想编 <id> ...`、`/删随想 <id>`、`/移动 <id> misc`，断言目标 ID 解析和 batch 顺序稳定。
- **边界测试**：非 thought 消息、album 图片、analysis/help 命令不被误归为 thought。
- **回归测试**：运行 `test/telegram-sync.test.mjs` 中现有 batch 分组用例。

**3. 回滚计划**

若后续调整 resolver 顺序导致 fixture 失败，优先回滚 resolver 变更；不要通过给 `buildThoughtKey()` 增加 timestamp 后缀规避，因为这会破坏 edit/delete/move 的稳定定位。

### P1-2：随想 ID 全链路 `Number()` 丢失大整数精度

**问题概述**

随想链路不止 repository 一处有精度风险。原始审计发现 `parseThoughtEditCommand()`、`parseThoughtDeleteCommand()`、`normalizeMessageId()`、`parseThoughtMoveCommand()` 会把用户输入的目标 ID 转成 `Number()`，`PostgresThoughtRepository.normalizeBigIntValue()` 也会转 `Number()`。当前本地实现已修复 repository 层和 Telegram 命令解析层：超出 `Number.MAX_SAFE_INTEGER` 的字符串/bigint 会保持字符串传给 SQL；`/随想编`、`/随想删`、`/移动` 中的超大目标 ID 会保留原始字符串，不再被 JS number 截断。

**实施状态（本地）**：repository 层和 Telegram 命令解析层已完成本地合同校准；`test/core-repositories.test.mjs` 覆盖 `PostgresThoughtRepository preserves bigint thought ids as SQL strings without precision loss`，`test/telegram-sync.test.mjs` 覆盖 `preserves oversized thought target ids from Telegram commands without precision loss`。真实 Telegram/飞书通道输入超大 ID 的端到端验收仍需后续覆盖。

**1. 代码级修复**

文件：

- `src/adapters/telegram/sync-batch-logic.adapter.mjs`
- `src/adapters/postgres/thought-repository.pg.mjs:299-301`

历史风险示例（不是当前实现）：

```javascript
// 第 299-301 行
function normalizeBigIntValue(value) {
  return Number(value); // 原始风险：超过 MAX_SAFE_INTEGER 时丢失精度
}
```

修改后：

```javascript
function normalizeBigIntValue(value) {
  if (value === null || value === undefined || value === '') return null;
  const text = String(value).trim();
  return /^-?\d+$/.test(text) ? text : null;
}

function normalizeMessageId(value) {
  const text = String(value ?? '').trim();
  if (!/^\d+$/.test(text) || text === '0') return null;
  const number = Number(text);
  return Number.isSafeInteger(number) && String(number) === text ? number : text;
}
```

注意：当前 SQL 中 `core.thought.telegram_message_id` 和 `telegram_chat_id` 已是 `bigint`，不需要把 integer 改 bigint；问题在 JS 层 `Number()` 精度截断。

**2. 测试策略**

- **精度测试**：使用大于 `9007199254740991` 的 message_id 字符串进行写入和读取，验证读取值与原始值完全一致
- **命令解析测试**：`/随想编 9007199254740993 新内容`、`/删随想 9007199254740993`、`/移动 9007199254740993 misc` 均保留字符串 ID，不出现截断
- **类型一致性测试**：验证 `normalizeBigIntValue()` 对 `string`、`number`、`bigint` 三种输入类型均返回可传给 PostgreSQL bigint 的安全字符串或 null
- **查询测试**：使用大整数 message_id 执行 `editThought`、`deleteThought`、`moveThought`，验证 WHERE 条件正确命中
- **飞书 safe integer 代理测试**：确认飞书 `buildStableSafeInteger()` 生成的代理 ID 在新 bigint schema 下仍然兼容
- **真实端到端待验**：Telegram/飞书通道实际输入超大 ID 后，summary、pending、DB mirror 和回执均不截断。

**3. 回滚计划**

若字符串 ID 变更影响现有查询、索引或外部系统（如飞书 API）不兼容：
1. 不执行 schema 降级，`bigint` 保持不变。
2. 如某个旧调用方只能接受 number，临时在边界处仅对 `Number.isSafeInteger()` 的值转换为 number；超出范围返回 `manual_intervention`。
3. 对于飞书场景，继续保留 `sourceMessageId` 原始字符串，不把 safe integer 代理当作真实 Feishu message_id。
4. 回滚后运行 `test/thoughts-page.test.mjs` 和 edit/delete/move fixture。
