# 第四轮系统认知校准报告

> 审核时间：2026-06-19  
> 项目：training_records  
> 审核范围：项目源码、`sql/`、`docs/`、`docs/优化重构/核心代码优化01/`  
> 任务性质：系统认知校准，不新增重构方案，不修改业务代码，不做 Bug 审计

## 校准结论

本轮校准后的判断：当前重构文档已经具备继续作为核心代码优化入口的基础，但原文档更偏“技术重构方案”，对系统业务目标、双通道核心能力、四类图片识别差异、数据库事实源层级和新接手人员阅读路径说明不足。本轮已在现有文档体系内补齐这些内容。

系统真正的核心目标是：把用户在 Telegram 和飞书中自然发送的训练、饮食、体脂秤、睡眠截图，以及随想和身体反馈，低摩擦、可追溯地转成 PostgreSQL 结构化事实，再服务于页面展示、长期复盘和 AI 分析。

## 新发现的业务理解偏差

### 1. 原文档偏向“消息管线重构”，没有先说明系统为何存在

原文档对 `MessageSyncTask`、ChannelAdapter、pending、AI 调度器等技术目标描述充分，但业务上容易让未来读者误以为系统核心是“统一消息同步框架”。实际核心是“个人训练与健康数据采集、结构化、复盘系统”，消息框架只是服务这个目标。

已修正：在 `重构优化文档.md` 增补“系统核心价值”“核心业务、辅助功能和不可破坏功能”“系统业务总览”。

### 2. Telegram 命名问题不是单纯命名债，而是双通道业务一致性问题

当前飞书通过 `runFeishuSync()` 规范化后复用 `runTelegramSync()`，并复用 `ingest.telegram_*` 表。这不是简单的代码命名不雅，而是未来重构时最容易破坏双通道一致性的地方。

已修正：在 `消息链路.md` 明确 Telegram/飞书都是核心采集通道，并列出必须统一、允许差异和绝不能差异的边界。

### 3. AI 识别不能被理解为通用 OCR

训练、饮食、体脂秤、睡眠四类图片的识别目标、结构化结果、日期规则和入库目标不同。原文档描述了 AI fallback 和调度，但对“不同图片类型为什么要这样识别”说明不足。

已修正：在 `AI 容灾与调度优化.md` 增补图片分类、识别目标、结构化结果、入库逻辑和异常处理表。

### 4. `core.training_day` 容易被误读为唯一事实源

实际系统中，`core.measurement/activity/meal/sleep/thought` 才是结构化明细事实，`core.training_day` 是页面和分析读取用的业务日投影。重构时如果直接手写或覆盖 `training_day`，会破坏事实可重建性。

已修正：在 `数据库优化.md` 增补 schema 分层、核心业务表、数据依赖和生命周期说明。

### 5. Markdown 导入不是普通备份功能

`import:markdown` / `reconcile:markdown` 会解析 `训练记录.md` 并写回 `core.*`，属于受保护维护能力。它不是日常主路径，但一旦破坏会造成历史数据覆盖或缺失。

已修正：在 `重构优化文档.md`、`消息链路.md`、`数据库优化.md` 和 `实施checklist.md` 中把 Markdown 导入列为单独验收对象。

## Telegram 与飞书专项核查结果

### 核查结论

两个通道都属于核心采集入口。当前实现通过飞书适配层复用 Telegram 同步管线，业务上必须按“双通道输入、共享业务管线”理解。

### 共同能力

- 图片采集：训练、饮食、体脂秤、睡眠截图。
- 随想采集：新增、编辑、删除、模块迁移、图片附件。
- 分析请求：读取训练、饮食、睡眠、身体反馈后回复来源通道。
- help 和基础回执。
- 失败 summary 与业务状态表达。

### 允许差异

- webhook 鉴权方式。
- 原始消息 ID 类型。
- 图片下载 API。
- 回执消息格式。
- Telegram Markdown 文档附件能力。
- 飞书 tenant token 获取和 inline 图片输入。

### 绝不能差异

- 同一图片类型的识别目标。
- 同一结构化字段的业务含义。
- 同一事实的入库目标。
- 低置信度、缺日期、manual intervention 的处理语义。
- `source_channel`、`source_batch_id`、原始消息追踪信息。
- 分析只读边界。

## AI 识别专项核查结果

### 核查结论

当前代码已经具备图片分类、schema 校验、严格 JSON 重试、provider fallback、低置信度跳过和日期 warning 输出等基础能力。原文档主要遗漏的是“这些能力如何服务四类核心业务图片”。

### 已补充的识别分类

| 类型 | 业务目标 | 入库目标 |
| --- | --- | --- |
| `workout` | 训练动作、组数、重量、次数、时长、消耗等 | `core.activity` |
| `nutrition` | 食物、餐次、热量和营养信息 | `core.meal` |
| `measurement` | 体重、体脂、BMI、肌肉、水分等体脂秤指标 | `core.measurement` |
| `sleep` | 入睡、醒来、总睡眠、评分、睡眠阶段 | `core.sleep` |
| `unknown` | 非目标图片或不可可靠识别图片 | 不写 core |

### 必须保留的 AI 规则

- 不猜测，不用历史数据补齐截图缺失字段。
- `confidence < 0.75` 不写 core。
- 非 JSON 或 schema parse failure 先同 provider 严格 JSON 重试。
- provider/network/timeout/429/5xx/empty content 等可恢复错误才进入 fallback。
- 日期证据必须保留 `dateSources`、`warnings` 和最终 `archivedDate`。

## 数据库专项核查结果

### 核查结论

数据库文档原本已经覆盖了不少结构风险，但业务层级说明不足。本轮明确了三层事实关系：

- `ingest.*`：外部事件、消息、识别和 pending 审计。
- `core.*` 明细：训练、饮食、体脂、睡眠、随想的结构化事实。
- `core.training_day`：从明细聚合得到的业务日投影。

### 核心数据生命周期

图片链路：

```text
通道消息 -> ingest batch/message -> AI recognition -> ingest recognition -> core 明细 upsert -> training_day refresh
```

随想链路：

```text
通道命令/附件 -> artifact/metadata -> core.thought mirror -> 页面展示/分析上下文
```

Markdown 导入链路：

```text
训练记录.md -> parser -> snapshot -> core whole-day replacement -> training_day refresh
```

分析链路：

```text
TrainingSnapshot -> AI analysis -> 通道回复
```

分析链路不应写 core，也不应改 Markdown。
