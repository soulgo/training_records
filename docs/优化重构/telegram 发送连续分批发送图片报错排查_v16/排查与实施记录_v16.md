# Telegram 连续分批发送图片报错排查与实施记录 v16

## Go / No-Go

- **Judgment**: Go
- **Reason**: 现有代码和 workflow 已能定位到“Telegram 回执与 Action summary 审计语义不一致”的具体缺口，修复范围清晰，不需要改变图片识别、入库或页面展示主链路。

## Target Outcome

连续分批通过 Telegram 发送训练图片时，如果某个 batch 存在 AI 识别失败、partial failure、pending replay 或数据库延迟写入，Telegram 回执和 GitHub Action summary 必须显示一致的业务状态；如果 batch 完全成功，则两边都显示成功。核心图片识别规则继续保持严格，不允许把 AI 识别失败伪装成成功。

## Goal Definition

- **Type**: technical / operational / quality
- **Boundary**: 包含 Telegram 图片 batch 状态、Action summary 审计、通知语义、测试和系统文档；不包含 prompt 放宽、数据库 schema 变更、页面展示变更。
- **Non-goals**:
  - 不改变 AI 对截图真实可见数据的严格识别要求。
  - 不把 `partialFailure`、`recognitionErrors` 或 pending retry 静默成成功。
  - 不重写 Telegram webhook、相册 Durable Object 或入库 schema。
- **Deferred work**:
  - 真实截图样本补充为 fixture，以便后续做模型级回归。
  - 将 workflow 内联 summary 脚本抽成可复用工具，降低 YAML 重复。
- **Verification rule**: 先用测试复现 Action summary 对 `partialFailure` 的审计缺口，再修复生产和 dev workflow，最后跑相关测试和 `npm test`。
- **Evidence source**: 代码审计、workflow 测试、Telegram sync runner 测试、全量 Node test。
- **Pass criteria**: `partialFailure` 在 Action summary 中显示为 `partialFailure`，`failureDisposition` 显示 `auto_retry`，failed messageIds 保留；全量测试通过。
- **Confidence note**: 该问题发生在报告/审计层，可用现有 JSON result 构造稳定测试，不依赖外部 Telegram 或 AI 服务。
- **Judgment owner**: 测试套件和用户最终验收。

## Current State

- `runTelegramSync()` 将原始 result 写入 `TELEGRAM_SYNC_RESULT_PATH`，其中 `batchResults` 保留 `messages`，供 after-action Telegram 通知回复到原消息。
- `notifyTelegramSyncResult()` 会读取原始 `batchResults`，并在 `partialFailure`、`recognitionErrors` 或识别数量不完整时发送“部分解析失败”等回执。
- `.github/workflows/telegram-sync.yml` 和 `.github/workflows/telegram-sync-dev.yml` 的 `Write Telegram sync summary` 直接读取原始 result，并使用 `batch.taskStatus ?? batch.status`。
- 原始 result 中没有 `taskStatus` / `failureDisposition`；这些字段只在 `buildTelegramSyncReport()` 里规范化生成。
- 因此同一个 batch 可能在 Telegram 中显示“部分解析失败”，但 Action summary 只显示 `ready + stored`，造成“Action 日志无报错”的错觉。
- 当前截图附件未在仓库文件系统中找到；本轮以代码、workflow、历史 v6/v8/v9 文档和现有测试作为可验证证据。

## Priority Rationale

- 先修审计一致性，因为它直接解释截图现象，且不触碰 AI 识别主链路。
- 保持 Telegram 回执严格，因为该系统核心功能依赖 Prompt 识别图片并入库，不能为了减少“报错”而掩盖真实识别失败。
- 同步修生产和 dev workflow，避免环境间审计口径分裂。

## Dry-Run Findings

- Workflow summary 当前读的是原始 result，无法拿到 `buildTelegramSyncReport()` 才生成的 `taskStatus` 和 `failureDisposition`。
- 不能把 result 文件直接改为规范化 report，因为 after-action Telegram 通知需要原始 `messages` 里的 chatId/messageId。
- 最小路径是在 summary inline script 内动态 import `tools/telegram-sync.mjs`，只用于生成审计视图。
- 生产和 dev workflow 有重复脚本，需要同时修改并用同一个测试覆盖。
