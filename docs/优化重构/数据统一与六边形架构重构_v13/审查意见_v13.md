# 数据统一与六边形架构重构_v13 — 审查意见

## 总体评价

v13 方案集在架构方向上整体正确：PostgreSQL 唯一事实源 + 六边形分层是合理的终态目标。方案的三阶段划分（清理→重构→延伸）逻辑清晰。但将方案与实际系统代码、文档和数据库表结构交叉比对后，发现若干**事实偏差、遗漏模块和可行性风险**，以下逐一说明。

---

## 一、Phase A 审查

### A1.1 `db.json` 定性不准确
**方案描述**：`db.json` 为"0 字节空文件"，应删除。

**实际情况**：根据 `docs/系统架构/系统总览.md` 和 GitHub Actions 配置，`db.json` 是 **Hexo 数据库缓存文件**（构建提速用），由 Hexo 自身管理，GitHub Actions `site-build` composite action 也显式 cache 了它。它不是训练数据存储，也不会被训练系统代码引用。

**建议**：将 `db.json` 从"数据层残留碎片"中移除。它属于 Hexo 构建产物范畴，不应由本次重构处理。保留在 `.gitignore` 中即可。

### A1.2 `runtime/telegram-sync-pending.ndjson` 已有数据库对应表
**方案描述**：评估 `runtime/telegram-sync-pending.ndjson` 是否仍在使用；若在使用则在 Phase B 迁移到 `ingest.telegram_pending_batch` 表。

**实际情况**：`ingest.telegram_pending_batch` 表**已经存在**于 `sql/training_records/ingest.sql` 中，包含完整的字段定义（`pending_id`、`batch_id`、`kind`、`status`、`batch_payload_json`、`failure_category`、`attempt_count`、`next_retry_at` 等）。同时 `src/jobs/pending-store.mjs` 也已经存在对应的持久化逻辑。

**建议**：A1.2 应改为"确认 `runtime/telegram-sync-pending.ndjson` 的写入路径已完全收敛到 `ingest.telegram_pending_batch` 表，并删除 NDJSON 文件及对应读写逻辑"。Phase B7 中的"创建 `ingest.telegram_pending_batch` 表"步骤也应删除——此表已存在。

### A2. 写入路径审计范围不足
**方案描述**：确认所有写入通过 `src/db/training/write.mjs` 完成。

**实际情况**：当前写入路径涉及**两层 facade**：
- `tools/training-db-write.mjs`（re-export 层）→ `src/db/training/write.mjs`（实现层）
- `tools/training-db-core.mjs` 是对外聚合 facade

此外 `tools/training-db-archive.mjs` 和 `src/db/training/archive.mjs` 也执行数据库写入操作。

**建议**：审计搜索范围应扩充为全局搜索所有 `pg.Client`、`client.query` 实例化位置，而非仅限定 `src/db/training/write.mjs`。

### A3. 数据一致性验证——`core.training_day` 缺少睡眠汇总字段
**方案描述**：验证各表数据一致性。

**实际情况**：查看 `sql/training_records/core.sql`，`core.training_day` 表**没有睡眠汇总字段**（`sleep_total_minutes`、`night_sleep_minutes`、`nap_minutes`、`sleep_start_time` 等）。这些字段仅存在于 `archive.training_day` 中。然而 `docs/系统架构/系统总览.md` 和 `docs/内部接口手册.md` 多处提到 `core.training_day` 包含睡眠汇总，这与实际 SQL schema 矛盾。

**建议**：
1. 先澄清 `core.training_day` 是否应包含睡眠汇总字段（逻辑上应该包含，因为 Telegram sleep 图片写入后会"刷新 core.training_day 睡眠汇总"）
2. 如果应该包含，则 `core.sql` 需要补充这些字段（作为 Phase A 前置步骤）
3. 如果不应包含，则需修正系统文档中的多处不实描述

## 二、Phase B 审查

### B0. 最大的遗漏：`tools/` 目录未纳入重构范围
**这是 v13 方案最严重的结构性问题。**

**方案描述**：Phase B 的所有 PR 均围绕 `src/` 目录重组（`src/core/`、`src/adapters/`、`src/app/`、`src/infra/`），完全未提及 `tools/` 目录。

**实际情况**：当前系统有两条平行的模块路径：

| 模块 | `tools/` 版本 | `src/` 版本 | 关系 |
| --- | --- | --- | --- |
| `training-domain.mjs` | `tools/training-domain.mjs` | `src/domain/training/training-domain.mjs` | 两个独立文件 |
| `training-parser.mjs` | `tools/training-parser.mjs` | `src/domain/training/training-parser.mjs` | 两个独立文件 |
| `training-snapshot.mjs` | `tools/training-snapshot.mjs` | `src/domain/training/training-snapshot.mjs` | 两个独立文件 |
| `dashboard-view.mjs` | `tools/dashboard-view.mjs` | `src/site/dashboard-view.mjs` | 两个独立文件 |
| DB facade | `tools/training-db-core.mjs`（聚合 re-export） | `src/db/training/*.mjs`（实现） | facade → 实现 |
| DB write | `tools/training-db-write.mjs`（re-export） | `src/db/training/write.mjs`（实现） | re-export → 实现 |
| Telegram sync | `tools/telegram-sync.mjs`、`tools/telegram-sync-lib.mjs` 等（~20 个文件） | `src/telegram/sync.mjs`、`src/telegram/sync-batch.mjs` | 大量逻辑在 tools/ |
| AI provider | — | `src/ai/*.mjs` | 仅在 src/ |

`tools/` 目录包含大量核心业务逻辑——Telegram 同步主入口、训练分析、数据库 facade、数据生成等。它们是 CLI 入口（npm scripts）的实际执行者。如果把 `src/` 重构为六边形架构但 `tools/` 仍然引用旧路径，会导致系统分裂。

**建议**：
1. 明确 `tools/` 与 `src/` 的关系：是工具的 `tools/` 作为 CLI 入口（thin wrapper），核心逻辑在 `src/`；还是需要将 `tools/` 中的逻辑也迁移到 `src/` 各层
2. 至少需要新增一个 PR，专门处理 `tools/` → 六边形架构的对齐
3. 删除 `tools/` 中与 `src/` 重复的模块（`training-domain.mjs`、`training-parser.mjs` 等），统一到 `src/`

### B1. 核心域实体提取——遗漏独立实体类型
**方案描述**：提取 5 个实体：TrainingRecord、BodyMetric、SleepRecord、HealthDaily、ThoughtRecord。

**实际情况**：当前系统以子表独立管理各数据域：
- `core.measurement` — 体脂秤数据（独立 upsert）
- `core.activity` — 运动明细（独立 upsert）
- `core.meal` — 餐次明细（独立 upsert）
- `core.sleep` — 睡眠明细（独立 upsert）

Telegram 图片批次以**增量 upsert** 方式写入各子表，不会整日替换。这意味着各子表实体需要独立建模。

**建议**：
1. 增加 `Activity` 和 `Meal`（或 `Nutrition`）实体
2. `TrainingRecord` 聚合实体应定位为"日级读模型"（read model），而非各子表的唯一容器
3. 考虑区分"写入实体"（独立子表行）和"读取聚合"（TrainingDay 视图）

### B3. `write.mjs` 拆分——部分拆分已完成
**方案描述**：`src/db/training/write.mjs`（1600+ 行）需拆分为 Repository + Adapter + Service。

**实际情况**：`write.mjs` 已经从单体拆分为多个协作文件：
- `incremental-write.mjs` — Telegram 图片增量写入
- `core-row-writer.mjs` — 各子表行级 upsert（`insertCoreActivities`、`insertCoreMeasurements`、`insertCoreMeals`、`insertCoreSleep`）
- `write.mjs` 本身仍保留事务管理、批次协调、Thought 处理、Markdown 导入逻辑

此外 `read.mjs` 也已拆分为：
- `read.mjs` — 聚合入口
- `read-client.mjs` — Client 创建
- `read-mapper.mjs` — 行映射
- `read-queries.mjs` — SQL 查询

**建议**：
1. 更新方案中的"当前状态"描述，反映已有的拆分进展
2. 重新评估 `write.mjs` 实际剩余行数和工作量（已拆出 incremental-write 和 core-row-writer 后，实际行数可能已在 1000 行以内）
3. PR #3 和 PR #4 的时间估算应相应下调

### B5. AI Provider 适配器——“当前状态”有误
**方案描述**：`src/ai/provider.mjs` 是"Qwen 主 Provider"。

**实际情况**：根据 `docs/系统架构/系统总览.md`（第 86 行）明确记载：`src/ai/provider.mjs` 为"AI provider 工厂，默认 `openai-compatible`"。它并不是 Qwen 专用 Provider，而是一个**工厂/适配器选择器**。

此外 `src/ai/recognition-service.mjs` 是 Telegram 图片识别的核心编排层，方案中未提到它应该放在哪里。它同时依赖 AI Provider、数据库识别缓存、schema 校验器，职责复杂。

**建议**：
1. 修正 B5 中对 `provider.mjs` 的定性
2. 新增对 `src/ai/recognition-service.mjs` 的定位说明（属于应用层 Use Case 还是适配器层？）
3. `src/ai/schema-validator.mjs` 和 `src/ai/errors.mjs` 也应明确归属

### B9. 依赖注入容器——可能过度工程化
**方案描述**：创建 `src/infra/di-container.mjs`，注册所有 Repository、Adapter、Use Case。

**实际情况**：当前系统是**基于 npm scripts + GitHub Actions 的 Job 型系统**，并非长期运行的服务进程。每个 Job 独立启动 Node.js 进程、创建 pg Client、执行任务后退出。这种情况下：
- 不存在跨请求的依赖复用需求
- DI 容器在每次 Job 启动时创建一次后即被丢弃
- 简单的工厂函数（`createPgClient(config)` 传给各模块）已能满足当前需求

**建议**：
1. 评估 DI 容器的实际收益：当前是否已有因依赖混乱导致的测试困难或配置分散问题？
2. 如果确实需要，采用轻量方案：一个 `createApp(config)` 工厂函数足矣，不必追求完整的 DI 容器模式
3. 将 PR #8 中 DI 容器的优先级下调，或与"统一配置"合并为一个更小的 PR

### B10. 配置源统一——方案与 Checklist 不一致
**方案 Phase B 文档中**没有 B10 节（B7 和 B8 后直接跳到 B9）。

**实施 Checklist 中**却有 B10"配置源统一"：
- 创建 `src/infra/config.mjs`
- 添加配置校验
- 更新 GitHub Actions workflow

**实际情况**：当前配置分散在多个文件中：
- `src/db/training/config.mjs` — 数据库配置
- `tools/training-db-config.mjs` — 数据库配置 re-export
- 各模块通过 `options.env` 直接读取 `process.env`

**建议**：在 Phase B 文档正文中补充 B10 节的内容。

### B11. 遗留代码清理——删除列表不完整且有风险
**方案描述**：删除 `src/db/training/write.mjs`、`read.mjs` 等。

**实际情况**：这些文件由 `tools/training-db-core.mjs` 和 `tools/training-db-write.mjs` 通过 re-export 对外暴露。直接删除会导致依赖断裂。

此外 `src/domain/training/` 目录中也包含 `training-exporter.mjs`（导出 Markdown 的领域逻辑），`tools/training-db-core.mjs` 直接引用它。这个文件在删除列表中未被单独提及。

**建议**：
1. 补充 `tools/` 中所有 re-export 文件的清理计划
2. 补充 `tools/` 中与 `src/` 重复模块的清理计划
3. `src/domain/training/training-exporter.mjs` 应明确归属（领域服务还是适配器）

### B 整体时间估算过于乐观
**方案描述**：Phase B 总计 6-8 周。

**实际情况**：考虑到以下未计入的工作量：
- `tools/` 目录对齐（未列入任何 PR）
- 现有 20+ 个 `tools/telegram-sync-*.mjs` 文件的重组
- 测试数据库搭建 + 所有测试编写
- 与 GitHub Actions CI/CD 的集成验证
- 生产环境数据迁移验证

**建议**：调整为 10-14 周更为现实。

## 五、关键风险提示

1. **`tools/` 与 `src/` 的双轨问题**：如果只重构 `src/` 而不同步清理 `tools/`，会导致系统出现两套模块体系，增加维护成本而非降低。

2. **重复模块的去重风险**：当前 `tools/training-domain.mjs` 和 `src/domain/training/training-domain.mjs` 是两个独立文件——需要确认它们的内容是否完全一致（同步问题），然后决定保留哪一个。

3. **Telegram sync 链路是系统最复杂的部分**：涉及 ~20 个 `tools/` 文件加 `src/telegram/`、`src/ai/`、`src/db/training/` 多层协作。重构这个链路需要对数据流有极其精确的理解，任何拆分错误都可能导致生产数据丢失。

4. **`core.training_day` 缺少睡眠汇总字段**：这个 schema 与文档的不一致可能意味着代码中存在运行时 ALTER TABLE 或 CTE 动态生成这些字段的逻辑。在重构前需要先理清这一点。
