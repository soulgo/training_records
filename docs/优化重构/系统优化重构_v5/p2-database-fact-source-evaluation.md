# P2-2 database 事实源评估

## 结论

当前**不建议**把 PostgreSQL 切换为默认事实源。

### 原因

1. Markdown 仍承担人工维护与数据库故障回退语义，切换默认事实源会改变现有补偿路径。
2. `runtime/telegram-sync-pending.ndjson` 仍是当前补偿重放的核心运行期产物，数据库主事实源化会放大 pending 对账成本。
3. 现有导入 / 导出流程虽然可用，但当前仍依赖回退与补偿机制兜底，尚未达到“数据库可单独作为唯一真源”的稳定度。
4. 页面构建与 Telegram 同步链路都已建立在“Markdown 可回退”的稳定预期上，贸然切换会增加回归面。

## 评估项

### Markdown 与 DB 的主从关系

- 当前建议维持 **Markdown 作为人工可读源与故障回退源**，数据库作为结构化读写与查询源。
- 现阶段更适合把 DB 视为增强型事实源，而不是完全替代 Markdown 的默认真源。

### 导入 / 导出一致性

- 导入与导出链路已有基础，但仍需持续验证以下点：
  - `TrainingSnapshot` 结构是否在 Markdown 与 DB 之间完全等价。
  - 历史图片批次、随想批次与手工编辑是否能在导出后保持同等语义。
  - 任何补偿队列重放后，导出结果是否与原始 Markdown 保持一致。

### fallback 与对账成本

- fallback 机制是当前稳定性的关键，不应因“想统一事实源”而削弱。
- 若切换默认事实源，需要额外引入：
  - 全量历史对账
  - 增量对账任务
  - 失败重试与人工审计流程
  - 回滚到 Markdown 的明确协议

## 未来切换前置条件

如未来要评审切换默认事实源，建议先满足以下条件：

1. 导入 / 导出双向快照对账长期稳定。
2. pending 重放能覆盖所有失败路径且可审计。
3. Markdown fallback 只作为灾备，而不是主恢复路径。
4. 训练快照、Dashboard、分析与随想导出均能在 DB-only 情况下稳定运行至少一个完整周期。
5. 明确 GitHub Actions / Worker / 本地脚本的回滚方式。

## 当前建议

- **不切换默认事实源**。
- 继续以 Markdown 作为稳定回退面。
- DB 继续作为主结构化读写与分析来源，但不改变现有默认链路。
