# Telegram Sync 重构方案（第八轮）

> 目标：把 Telegram Sync 从“脚本拼装式同步”逐步收敛成“任务驱动、状态清晰、可恢复、可审计”的流程。

---

## 1. 当前问题

### 1.1 同步入口过多

当前相关入口包括：

- `workflow_dispatch` 手工触发
- `repository_dispatch` 的 `telegram_update`
- `push` 到 `main` 后由 workflow 自动触发
- `pending replay` 补偿流程
- 数据回填脚本与同步脚本

入口多本身不是问题，但现在很多入口会走到相似甚至相同的业务逻辑，维护者需要记住太多路径。

### 1.2 状态流转分散

Telegram Sync 目前涉及的状态和副作用分散在多处：

- batch 结果结构
- pending 队列
- runtime 日志
- PostgreSQL ingest/core/archive
- Telegram 通知文本
- 各类测试用例

这会让排查变成“串多个地方看上下文”，而不是“看一个任务就知道它发生了什么”。

### 1.3 失败恢复虽然有，但表达方式不统一

现在系统已经有了 `queued`、`ready`、`stored`、`skipped`、`deferred`、`resolved` 以及 `partialFailure` 这类恢复/处理状态，这是很好的基础；但问题在于：

- 不同失败原因的表达不完全一致
- 部分失败与整体失败的处理方式还需要继续收敛
- 通知和日志之间的状态语义不够统一

---

## 2. 重构目标

1. **统一任务模型**：同一类输入统一用同一个状态机处理。
2. **统一失败语义**：可重试、不可重试、待人工处理分别清晰定义。
3. **统一日志输出**：让 batch、message、recognition、persist 的结果能串起来。
4. **统一补偿机制**：pending replay 不要变成特殊分支，而应成为标准流程的一部分。

---

## 3. 推荐结构

### 3.1 把 Sync 看作标准任务流

建议把每次同步抽象成一个 `SyncTask` 或 `SyncBatch`，至少包含：
- `taskId`
- `sourceType`
- `sourceId`
- `batchId`
- `status`
- `retryCount`
- `failureReason`
- `createdAt`
- `updatedAt`

这样做的好处是：

- 每个任务都有可追踪身份
- replay 与首次处理可以复用同一处理器
- 失败恢复不再依赖“记得是哪条脚本跑出来的”

---

### 3.2 状态机建议

建议统一这些核心状态，并与现有实现保持一致：

- `queued`
- `processing`
- `ready`
- `stored`
- `skipped`
- `deferred`
- `partialFailure`
- `resolved`
- `failed`

并明确每个状态的含义：

- `queued`：已入队，等待处理
- `processing`：正在识别或同步
- `ready`：结果可写入
- `stored`：已落库
- `skipped`：明确不处理或不符合条件
- `deferred`：当前条件不足，延后处理
- `partialFailure`：部分成功，部分失败
- `resolved`：补偿后成功闭环
- `failed`：不可恢复或超过重试阈值

---

### 3.3 任务与副作用解耦

建议把同步处理拆成三段，并尽量和现有代码里的识别、归档、落库职责对齐：
1. **识别层**：只负责把输入变成标准化结果
2. **归档层**：只负责决定日期、批次归属和存储策略
3. **落库层**：只负责持久化主数据与审计数据

当前系统已经部分具备这个分层，但仍然混杂在脚本和辅助函数里。继续收敛后，代码可读性和可测试性都会更好。

---

## 4. 重点优化方向

### 4.1 partial failure 的标准处理

建议把 `partialFailure` 作为正式一等状态，而不是只作为日志提示。

当 batch 中出现：

- 某张图识别成功，某张图识别失败
- 某些图片 ready，但部分 message 无法解析
- 同批次日期或内容存在局部冲突

应满足：

- 成功部分尽量先入库
- 失败部分进入 pending/replay
- 通知中明确显示 `x/N` 和失败 messageId
- 任务状态保持可追踪

### 4.2 replay 复用首次处理逻辑

replay 最容易变成“第二套实现”，这会带来很大维护负担。

建议：

- replay 不写独立业务逻辑
- replay 只改变输入来源与重试上下文
- 处理器内部逻辑保持一致

也就是说，第一次处理和补偿处理只应有“入口不同”，不应有“核心逻辑不同”。

### 4.3 审计信息统一

建议让每个任务至少记录：

- 输入批次
- 识别状态
- 日期来源
- 失败原因
- replay 次数
- 最终落库结果

这样后续排查时，既能看到“发生了什么”，也能看到“为什么会这样”。

---

## 5. 建议的落地点

### 5.1 统一 batch 结构

建议保留现有结果结构，但增加更明确的内部语义层：

- 输入层：message、photo、document、caption
- 识别层：AI 输出、校验结果、错误原因
- 归档层：archivedDate、dateEvidence、conflict 判定
- 落库层：ingest / core / archive 写入状态

### 5.2 统一通知文本

Telegram 通知建议固定输出以下信息：

- 本批状态
- 识别数量 `x/N`
- 是否 partial failure
- 是否进入 pending/replay
- 最终 archivedDate
- 是否存在日期冲突或缺失

这会显著降低人工查看日志的成本。

### 5.3 统一失败级别

建议至少分三类：

- **可自动重试**：AI 返回异常、临时网络失败、短暂数据库异常
- **需人工介入**：日期冲突、结构性字段缺失、输入明显不合法
- **直接跳过**：不满足归档条件、明确无效输入

---

## 6. 风险与回滚

### 风险

- 把状态机做得过细，会让系统复杂度反而上升
- replay 逻辑如果和首次处理没有真正共用，容易引入双实现
- 审计字段太多会增加日志噪音

### 回滚建议

- 先只统一状态名和通知语义，不一次性重构全部存储结构
- replay 先共用处理函数，再考虑更高层抽象
- 保留现有脚本入口一段时间作为兜底

---

## 7. 验证清单

- 单图、相册、补发、重放是否都能走统一任务描述
- `partialFailure` 是否能稳定进入 pending/replay
- 通知文本是否能让人只看一条消息就知道本次处理结果
- replay 是否真的复用了首次处理逻辑
- 失败后是否能快速定位到 messageId / batchId / failureReason

---

## 8. 推荐结论

Telegram Sync 重构的重点不是新增识别能力，而是把已有能力组织好。

如果只做一件事，建议优先做：

1. 统一任务状态机
2. 统一 partial failure 语义
3. 统一 replay 的复用逻辑

这样可以在不改业务口径的前提下，显著提升维护性和可恢复性。
