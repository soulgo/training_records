# 部署与构建优化方案（第八轮）

> 目标：压缩 `dev/main` 的部署链路耗时，减少重复构建、重复回填、重复校验，让发布流程更稳定、更可预测。

---

## 1. 当前问题

### 1.1 构建链路过长

当前部署链路通常包含：

- 依赖安装
- 数据同步 / 回填 / 对账
- 测试
- Hexo 构建
- 静态站点发布
- Cloudflare Worker / Pages 相关发布

问题不在某一步特别慢，而在于**多个步骤串联后累计耗时明显**，而且其中有一部分步骤在大多数提交里其实并不会产生有效变化。

### 1.2 dev/main 的重复逻辑较多

当前仓库里，`main` 是主要发布目标，相关 workflow 既会在 `main` push 时触发，也支持 `workflow_dispatch`；`telegram-sync.yml` 还会在 `repository_dispatch` 的 `telegram_update` 场景下执行。虽然目标不同，但多个流程共享了相同的构建与同步脚本，因此仍会出现步骤重叠。这样会导致：

- 维护两套 workflow 成本高
- 改一次构建逻辑需要同步多处
- 容易出现环境差异引发的“只在某条线失败”问题

### 1.3 慢步骤没有被充分分级

当前比较典型的问题是：

- 必须执行的步骤和“有变化才执行”的步骤没有完全分开
- 慢测试与快速测试的边界不够显式
- 数据回填、Markdown 对账、Hexo 初始化等重步骤仍会频繁进入主链路

---

## 2. 优化目标

1. **缩短主部署链路**：尽量把大多数提交的部署时间压到更稳定的区间。
2. **减少重复工作**：把数据同步、构建、测试中重复且无效的部分剥离出去。
3. **统一 dev/main 的公共流程**：环境差异放到少量配置里，不要复制一整套逻辑。
4. **保留可回滚性**：任何优化都应尽量是“先跳过、后执行”，而不是不可逆重构。

---

## 3. 推荐方案

### 3.1 将构建拆成三层

#### 第 1 层：输入准备

只做最小必要的准备工作，例如：

- 安装依赖
- 检查环境变量
- 恢复缓存
- 判定是否需要跑数据同步

这一层应该尽量轻，不做实际站点生成。

#### 第 2 层：内容与数据构建

负责：

- 数据回填
- Markdown 对账
- 训练数据导出
- Hexo 所需数据生成

建议将这里视为“可跳过的构建前置”，只在输入变化时执行。

#### 第 3 层：站点构建与发布

负责：

- Hexo generate
- 静态文件输出
- Pages / Worker 发布

这一层要尽可能单一，减少额外的脚本分叉。

---

### 3.2 dev/main 只保留环境差异

建议把差异收敛到这些维度：

- 目标分支
- API/数据库连接串
- 是否执行完整测试
- 是否执行生产部署
- 是否发通知

不要让 dev/main 分别维护两套构建逻辑。最好是同一套 workflow，通过输入参数或环境变量决定执行策略。

---

### 3.3 数据同步步骤只在必要时执行

建议把以下任务纳入“变化检测”后再执行：

- backfill / reconcile
- 训练数据导入导出
- 归档或重建类脚本

可以使用以下判断条件：

- 相关源文件 hash 是否变化
- 是否新增训练记录或归档
- 上一次同步结果是否为 unchanged
- 关键输入是否与上次部署一致

这样可以把大部分“没有新数据”的提交从慢流程里剥离出去。

---

### 3.4 慢测试和快测试分层

建议把测试分成：

- **快测试**：运行频率高，主要用于提交时校验
- **完整测试**：包含完整渲染、完整 Hexo 初始化、较重的集成校验

默认部署只跑快测试，完整测试改为：

- nightly job
- 手动触发
- 影响站点渲染的关键改动时才执行

这样可以显著减小普通提交的部署耗时。

---

## 4. 建议的落地点

### 4.1 workflow 分层

建议最终形成如下结构：

- `build-check`：依赖安装、缓存恢复、环境检查、快测试
- `build-data`：仅在需要时执行数据同步和导出
- `build-site`：Hexo 构建和静态发布
- `deploy`：发布到 Pages / 相关平台

### 4.2 缓存统一

需要统一管理以下缓存：

- Node 依赖缓存
- Hexo database / 输出缓存
- 构建中间产物缓存

原则是：缓存必须能解释“为什么快”，而不是只是存在。

### 4.3 失败策略统一

建议对部署失败定义清晰的层级：

- 输入准备失败：直接终止
- 数据同步失败：标记为可恢复/可延后
- 构建失败：终止发布
- 部署失败：保留构建产物，方便重试

---

## 5. 风险与回滚

### 风险

- 把过多步骤跳过可能导致数据没有及时同步
- 缓存 key 设计不好会造成错误复用
- 环境差异参数化后，如果配置管理不清晰，容易出现 dev/main 行为不一致

### 回滚建议

- 保留原有 workflow 一段时间作为兜底
- 所有“快速跳过”都应允许通过手动参数强制执行
- 先在 dev 验证，再切 main

---

## 6. 验证清单

- 普通提交是否比以前明显更快
- 没有新增数据时，数据同步是否能快速跳过
- Hexo 缓存是否稳定命中
- dev/main 的发布逻辑是否仍然一致
- 构建失败后是否能保留足够上下文用于排查

---

## 7. 推荐结论

部署与构建优化的核心不是“再找一个更快的命令”，而是：

1. 把链路分层
2. 把重复逻辑收敛
3. 把慢步骤变成按需执行
4. 把 dev/main 的差异压缩到最小

如果只做一件事，建议优先做“数据同步步骤的变化检测 + 快速跳过”，因为这是最容易落地、收益也最直接的点。

---

## 8. 当前已落地项

- `.github/actions/site-build/action.yml` 新增 `sync_db_mode`，支持 `auto`、`always`、`never` 三种数据库同步策略。
- `sync_db_mode: auto` 会在无训练记录、随想、数据库脚本、SQL、依赖文件等数据相关变更时跳过 `sync:db`。
- `.github/workflows/deploy-pages.yml` 与 `.github/workflows/deploy-cloudflare-pages-dev.yml` 均显式使用 `sync_db_mode: 'auto'`。
- `.github/workflows/ci-tests.yml` 保留常规 `test` job 跑 `npm run test:fast`，并新增 `full-test` job，在 `schedule` 或 `workflow_dispatch` 时跑 `npm test`。
