# 自适应图片解析入库 v15

本方案将截图识别管线从"华为健康专属封闭管道"升级为"任意健康 APP 自适应提取引擎"。v15 只做一件事：通过 **App Profile + 通用 prompt**，让 AI 把截图上真实可见的时间、标签、数值和单位映射到系统现有 schema 字段。

## 问题陈述

当前系统有稳定的固定 core schema，但缺少一层可维护的"不同 APP 截图 → 现有字段"映射记忆。换成 Apple Health / Keep / 小米运动 / 咕咚等 APP 后，即使截图里有体重、活动热量、睡眠时长这类现有字段，AI 也可能因为字段叫法、时间位置、单位和页面语义不同而漏提或错映射。

v15 的目标不是扩展数据库字段，也不是改变页面展示，而是提升已有字段的跨 APP 识别适配能力。

## 目标边界

1. AI 只提取截图上真实可见的时间和现有系统字段需要的数据。
2. 现有 schema 中看不出来的字段输出 `null` 或空数组，不猜测、不补造。
3. 不新增 PostgreSQL core 表字段，不改变页面展示数据和展示口径。
4. 新增 APP 适配时，优先修改 `prompts/_source/app-profiles.json` 和测试 fixture，不改写库主链路。
5. 顶层 `detectedApp` 用于记录截图来源 APP，便于审计和后续 profile 调整。

## AI 记忆的定义

这里的"记忆"不依赖模型不可控的会话记忆，而落在仓库可维护、可测试、可回滚的配置和样例中：

- **App Profile**：记录不同 APP 的常见页面类型、字段别名、单位、时间位置和截图特征，例如 Apple Health 的 `Active Energy` 映射到 `records.dailyWorkoutSummary.activityCaloriesKcal`。
- **字段别名记忆**：把不同 APP 对同一指标的不同叫法映射到现有字段，例如 `Weight`、`体重`、`当前体重` 都映射到 `weightKg`。
- **时间提取记忆**：记录不同截图类型的主日期、测量时间、活动开始时间、入睡/醒来时间优先级；看不出可靠时间时留空。
- **失败样例记忆**：把识别失败或错映射的截图整理成测试 fixture，后续通过 prompt/profile 更新修正。

落点：

- `prompts/_source/app-profiles.json`：维护 APP 名称、页面特征、字段别名、单位换算和时间优先级。
- `prompts/_source/recognition-rules.json`：保留通用规则，并引用 App Profile 中的映射思想。
- `test/fixtures/telegram-recognition/`：保存典型识别期望，尤其是"可见字段应提取、不可见字段应留空"的回归样例。

## 核心设计

```
Telegram 截图（任意健康 APP）
  │
  ▼
AI Vision（通用 prompt + App Profile）
  ├─ detectedApp: "Apple Health"       ← 自动识别 APP 来源
  ├─ 核心字段映射                       ← 字段别名、单位、时间位置、页面类型
  └─ 现有 schema 字段                   ← 只输出系统已支持字段
  │
  ▼
normalizeRecognitionPayload()
  │
  ▼
analyzeTelegramBatch()
  │
  ▼
core writer
  │
  ▼
PostgreSQL core.* 固定列
```

固定 schema 继续承载核心指标（体重、睡眠时长、活动热量等），保证页面、分析和查询逻辑不被打散。AI 的职责是把不同 APP 的页面语义映射回这些稳定字段。

## 各层改动

### 1. Prompt 通用化

**文件**：`prompts/_source/recognition-rules.json`

改动：

- 删除华为专属 workout `type` 提示。
- 新增 `adaptiveExtraction` 章节。
- 明确 `detectedApp`、现有字段映射、不可见字段留空、单位换算和时间优先级。
- measurement / workout / nutrition / sleep 规则末尾增加"只提取截图真实可见数据，无法可靠识别填 `null`"的守护规则。

示例规则：

```json
{
  "adaptiveExtraction": {
    "title": "自适应提取规则",
    "rules": [
      "先识别截图来自哪个健康 APP，输出到 `detectedApp`；无法可靠识别来源时填 `null`。",
      "优先把截图上真实可见的数据映射到现有核心 schema 字段，不新增 core 字段，不改变页面展示口径。",
      "如果现有字段在截图中看不出来，填 `null` 或空数组，不要臆造、不要从其他图片推断。",
      "如果某个 APP 的指标与核心字段语义相同但名称不同，使用 App Profile 的字段别名、单位换算和时间优先级映射到核心字段。"
    ]
  }
}
```

### 2. App Profile

**文件**：`prompts/_source/app-profiles.json`

结构包含：

- `appAliases`
- `pageTypes`
- `fieldAliases`
- `unitConversions`
- `timePriority`

当前已覆盖：

- `华为健康`
- `Apple Health`

后续新增 APP 时，优先增加 profile 和 fixture，再运行 `node tools/prompt-generator.mjs` 重新生成 prompt。

### 3. Schema 契约

**文件**：`src/core/ai/telegram-recognition-schema.mjs`

顶层增加：

```js
detectedApp: { type: ['string', 'null'] }
```

并同步：

- 顶层 `required` 增加 `'detectedApp'`
- `RECOGNITION_SCHEMA_VERSION` 从 `v1` 升级到 `v2`

schema version 升级会让识别缓存自动失效，确保新 prompt + schema 契约立即生效。

### 4. 识别归一化

**文件**：`src/app/use-cases/image-recognition.use-case.mjs`

要求：

- `normalizeRecognitionPayload()` 保留顶层 `detectedApp`。
- 旧返回缺少 `detectedApp` 时归一化为 `null`。
- 现有字段归一化逻辑保持不变，包括类型转换、null 处理和睡眠字段补齐。

### 5. Batch 审计字段

**文件**：`src/adapters/telegram/sync-batch-logic.adapter.mjs`

要求：

- batch 输出增加 `detectedApp` 字段。
- 取第一个通过置信度门槛的非空 `recognition.detectedApp`。
- measurement / workout / nutrition / sleep 仍只消费现有 schema 字段。
- `detectedApp` 只用于日志、审计和后续按 APP 分析识别效果，不进入 core 固定列。

```
Apple Health 睡眠截图

  └─ records.sleep.sleepScore: null       ← 截图不可见，留空

  │
  ▼

  │
  ▼

```

## 向后兼容性

| 场景 | 影响 |
|---|---|
| 现有华为截图 | 核心字段提取口径保持兼容 |
| 识别缓存 | `schemaVersion v1 -> v2` 自动触发缓存失效 |
| DB 迁移 | 不需要 |
| 前端展示 | 不改变 |
| 新 APP 适配 | 主要改 App Profile、prompt 源文件和测试 fixture |

## 验收标准

- 现有华为健康截图核心字段提取结果与当前行为一致。
- 非华为 APP fixture 能保留 `detectedApp` 并映射可见核心字段。
- 新 APP 截图中看不出来的现有字段保持 `null` 或空数组。
- `ingest.telegram_recognition.recognition_json` 保留 `detectedApp`。
- 不新增 core 表字段，不改变页面展示。
- `npm test` 全部通过。
