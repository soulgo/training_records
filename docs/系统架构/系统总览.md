# 系统架构总览

本项目是一个以 `TrainingSnapshot` 为统一中间层的训练记录系统。线上核心链路是：从 PostgreSQL `core.*` 读取训练数据，生成 `source/_data/training.json` 和 `source/_data/dashboardView.json`，再由 Hexo + `themes/cactus` 渲染为静态站点并发布到 GitHub Pages。`训练记录.md` 是数据库派生的人工可读备份。

系统支持 Telegram 和飞书两个消息通道。Telegram Bot update 可经 Cloudflare Worker 转发为 GitHub `repository_dispatch`，由 GitHub Actions 执行 `npm run sync:telegram`；飞书事件经独立 Cloudflare Worker 验签后触发 `feishu_update`，由 GitHub Actions 执行 `npm run sync:feishu`。两个通道共用现有同步主编排、AI 图片识别、随想写入、训练分析和 PostgreSQL 入库逻辑；飞书只新增通道适配、图片下载、消息发送、Worker 和 workflow 入口。`/thought` / `/随想` 支持写入 `core.thought.body`；Telegram 还支持 Markdown 文档附件正文。正常图片成功路径会增量 upsert 本批次数据并刷新目标日期汇总，不整日替换同日其它模块；数据库不可用时追加待补偿队列。Markdown 由定时备份 workflow 从数据库导出。

以下内容基于当前仓库中的源码、配置、SQL、GitHub Actions 和 Hexo 主题静态分析。GitHub/Cloudflare 控制台设置、Secrets/Variables 实际值、PostgreSQL 实例运行状态均无法从本地仓库直接确认，本文标记为”待人工确认”。

### Cloudflare Worker

`cloudflare/sync-dispatch-worker.mjs` 是当前 main/dev 的统一 webhook 边缘入口：

1. 校验 HTTP method 为 `POST`。
2. 根据 `X-Telegram-Bot-Api-Secret-Token` 判断 Telegram；根据飞书 Lark headers 或飞书事件请求体判断飞书。
3. Telegram 请求交给 `handleTelegramWebhook()`；飞书请求交给 `handleFeishuWebhook()`。
4. 无法判断 channel 时返回 `400 unknown_channel`。

`cloudflare/telegram-sync-dispatch-worker.mjs` 仍负责 Telegram 通道细节：

1. 校验 `X-Telegram-Bot-Api-Secret-Token` 与 `TELEGRAM_SECRET_TOKEN`。
2. 对 `/help`、`帮助`、`命令`、`指令`、`使用说明` 直接调用 Telegram `sendMessage` 回发命令清单，不触发 GitHub Actions。
3. 对带图片的 update，使用 Durable Object binding `TELEGRAM_ALBUM_BUFFER` 按 chat 聚合约 3 秒。
4. 调用 GitHub API `/repos/{owner}/{repo}/dispatches`，发送 `GITHUB_DISPATCH_EVENT_TYPE_TELEGRAM`，main 为 `telegram_update`，dev 为 `telegram_update_dev`。

`cloudflare/feishu-sync-dispatch-worker.mjs` 仍负责飞书通道细节：

1. 使用 `X-Lark-Request-Timestamp`、`X-Lark-Request-Nonce`、`X-Lark-Signature` 和 `FEISHU_ENCRYPT_KEY` 做 HMAC-SHA256 签名验证。
2. 校验飞书事件中的 `token` 与 `FEISHU_VERIFICATION_TOKEN`。
3. 对 `url_verification` 返回飞书 `challenge`。
4. 只处理 `im.message.receive_v1`；其它事件直接忽略。
5. 对图片消息使用 Durable Object binding `FEISHU_IMAGE_BUFFER` 按 chat 聚合约 3 秒。
6. 调用 GitHub API `/repos/{owner}/{repo}/dispatches`，发送 `GITHUB_DISPATCH_EVENT_TYPE_FEISHU`，main 为 `feishu_update`，dev 为 `feishu_update_dev`。

`wrangler.toml` 和 `wrangler.dev.toml` 都指向 `cloudflare/sync-dispatch-worker.mjs`，并绑定 `TELEGRAM_ALBUM_BUFFER` 与 `FEISHU_IMAGE_BUFFER`。Cloudflare 控制台中的实际 Secret、变量、路由和域名绑定状态仍需部署时人工确认。

## 数据流

### 页面构建数据流

1. `npm run build:data` 执行 `tools/generate-training-data.mjs`。
2. `generateTrainingData` 根据 `TRAINING_SNAPSHOT_SOURCE` 调用 `buildTrainingSnapshot`：
   - `database`：`tools/training-db-read.mjs` 读取 PostgreSQL `core.*`，线上推荐配置。
   - `markdown`：`tools/training-parser.mjs` 解析 `训练记录.md`，仅用于本地兼容或显式维护。
3. 生成统一 `TrainingSnapshot`。
4. 写出 `source/_data/training.json`。
5. 调用 `buildDashboardViewModel` 写出 `source/_data/dashboardView.json`。
6. 写出 `训练数据解析.md` 作为排查输出。
7. 根据 `TRAINING_BUILD_ARCHIVE_WRITE=auto|true|false` 决定是否调用 `training-db-archive.mjs`：`false` 或 `database + strict + auto` 会在主输出已生成后跳过 archive 写库；允许写入时失败会追加 `runtime/training-db-sync.ndjson`，不阻断主输出。
8. `npm run build:site` 执行 `tools/run-hexo-command.mjs generate`。
9. Hexo 使用 `_config.yml`、`source/` 和 `themes/cactus` 生成 `public/`。
10. GitHub Pages workflow 上传并部署 `public/`。

### 消息通道自动同步数据流

1. Telegram Bot update 进入 Cloudflare Worker 或由 `getUpdates` 轮询；飞书 `im.message.receive_v1` 事件进入飞书 Cloudflare Worker。
2. Webhook 模式下 Telegram Worker 会直接回复帮助消息；其它消息 dispatch 到 GitHub `repository_dispatch: telegram_update`，触发 `.github/workflows/telegram-sync.yml`。
3. 飞书 Worker 验签并校验 token，图片事件可先进入 `FEISHU_IMAGE_BUFFER`；随后 dispatch `repository_dispatch: feishu_update`，触发 `.github/workflows/feishu-sync.yml`。
4. `telegram-sync.yml` 设置 `TELEGRAM_SYNC_TRANSPORT=webhook` 并运行 `npm run sync:telegram`；`feishu-sync.yml` 设置 `FEISHU_SYNC_TRANSPORT=webhook` 并运行 `npm run sync:feishu`。
5. Telegram 入口读取 dispatch payload 或调用 Telegram API；飞书入口读取 `client_payload.feishu_updates`，把飞书消息标准化为 Telegram-compatible batch，并保留 `sourceChannel/sourceMessageId/sourceChatId/eventId`。
6. `tools/telegram-sync-lib.mjs` 和 `src/adapters/telegram/sync-batch-logic.adapter.mjs` 解析命令、图片、随想和分析请求；飞书适配层复用这套命令解析。
7. 图片批次调用 `src/ai/recognition-service.mjs`，经 `src/ai/provider.mjs` 和 `openai-compatible-provider.mjs` 请求 AI Chat Completions；当前稳定识别 `measurement`、`workout`、`nutrition`、`sleep` 四类业务截图。飞书图片下载后以内联 data URL 发送给 AI。
8. 可选读取 PostgreSQL `ingest.telegram_recognition` 作为识别缓存，取决于 `TELEGRAM_RECOGNITION_CACHE_ENABLED`；缓存读取失败会降级为 cache miss，继续调用 AI。
9. 如果完整配置 `TELEGRAM_RECOGNITION_FALLBACK_*`，主 AI timeout、HTTP 429/5xx、空内容或网络失败后会自动切到备用 OpenAI-compatible provider；该备用链路作用于共享图片识别，飞书 workflow 也复用这些变量。
10. ready 图片批次优先通过 `tools/training-db-write.mjs` 在同一事务内先写 `ingest.*`，再增量 upsert 本批次的 `core.measurement`、`core.activity`、`core.meal`、`core.sleep`，最后用单条 CTE upsert 刷新当前 `archivedDate` 的 `core.training_day` 汇总；本批没有出现的 workout/nutrition 模块不会覆盖历史模块，core 子表记录对应 `source_channel`。
11. 正常 `ready + stored` 图片批次不写 `训练记录.md`；Markdown 由定时备份 workflow 从数据库导出。
12. PostgreSQL 写入失败时，待补偿记录追加到 `runtime/telegram-sync-pending.ndjson`。
13. `/thought` 和身体反馈批次写入 `core.thought`；Telegram 命令消息携带 `.md` / `.markdown` 文档附件时，会下载第一个 Markdown 附件，按 UTF-8 去 BOM/trim 后覆盖 caption 正文，单个附件上限为 5MB。飞书文本 `/随想` 当前是 DB-first 新建随想，不支持 Markdown 文档附件。Markdown 文章和图片引用由备份 workflow 派生。
14. `/analysis` 读取 `TrainingSnapshot`，调用 AI 生成回复，通过当前通道回发；按文档和代码语义不写 Markdown、`source/_posts` 或 PostgreSQL。
15. 若仓库内容变化，workflow 提交 `训练记录.md`、`source/_posts`、`source/images`，后续由 push 触发 deploy workflow；若只有 DB 内容变化，会异步 dispatch 独立 deploy workflow 并启用严格数据库快照模式。
16. dispatch 模式下同步 summary 会用 `buildTelegramSyncReport()` 或 `buildFeishuSyncReport()` 将原始 result 规范化为业务审计视图，输出 `taskStatus`、`failureDisposition`、图片计数和失败 message id；GitHub Action 绿色只代表 workflow 执行成功，业务上的 `partialFailure`、`auto_retry`、`pending_replay` 仍需以 summary 和通道回执为准。

## 部署方式

### 本地开发

1. `npm ci`
2. `npm run build:data`
3. `npm run server`
4. Hexo server 从 `source/`、`source/_data/` 和 `themes/cactus` 渲染本地页面。

本地是否连接 PostgreSQL 取决于 `TRAINING_DB_ENABLED`、`TRAINING_DB_URL` 和 `TRAINING_SNAPSHOT_SOURCE`。验证线上口径时应使用 `TRAINING_SNAPSHOT_SOURCE=database`。

### GitHub Pages

`deploy-pages.yml` 在 main 分支站点相关文件变更后触发，调用 `.github/actions/site-build`。该 action 执行依赖安装、安全数据库修复、构建数据、Hexo 生成、上传 `public/` 并部署 GitHub Pages，不执行 Markdown 回灌数据库。

`source/CNAME` 当前为 `soulgo.chat`。GitHub Pages 自定义域名已启用。

### Telegram 与飞书 webhook

Telegram Cloudflare Worker 由 `deploy-cloudflare-worker.yml` 通过 Wrangler 部署。Worker 接收 Telegram webhook 后转发到 GitHub repository dispatch。

飞书 Cloudflare Worker 使用 `wrangler.feishu.toml` 和 `deploy-cloudflare-feishu-worker.yml` 部署。它接收飞书事件订阅请求，完成 URL verification、签名验证、token 校验和图片 burst 缓冲后，转发为 `repository_dispatch: feishu_update`。部署步骤见 [飞书通道部署](../部署维护/飞书通道部署.md)。

dev 环境使用统一 Worker `sync-dispatch-dev` 和 `wrangler.dev.toml`，同一个入口识别 Telegram secret header、飞书 Lark header 或飞书请求体结构，再分别派发 `telegram_update_dev` 或 `feishu_update_dev` 到 `.github/workflows/sync-dev.yml`。

`soulgo.chat` 的 DNS 由 Cloudflare 托管（NS: jason/gemma），已通过 CNAME `soulgo.github.io` + 橙云代理（CDN proxy）加速 GitHub Pages 访问。SSL/TLS 模式为 Full (Strict)，已开启 Auto Minify（JS/CSS/HTML）、Brotli、HTTP/3、0-RTT、Early Hints。缓存规则按资源类型分层：字体 1 年、图片 30 天、CSS/JS 7 天、HTML 5 分钟 + stale-while-revalidate。Page Rule 配置 Cache Everything + Always Online。详见 [GitHub 与 Cloudflare 配置](../部署维护/GitHub与Cloudflare配置.md) 第 8 节和 [Cloudflare CDN 代理加速 v17](../优化重构/Cloudflare_CDN代理加速_v17/re_optimization_v17.md)。

## 自动化流程

1. **CI Tests**：代码或配置变更后运行完整 `npm test`。
2. **Deploy GitHub Pages**：站点相关变更后构建 `source/_data`、Hexo 静态文件并部署 Pages。
3. **Telegram Sync**：生产 Telegram update 后同步数据、提交必要内容变更，并在 DB 内容变化时异步触发部署。
4. **Feishu Sync**：生产飞书事件后同步数据、提交必要内容变更，并在 DB 内容变化时异步触发部署。
5. **Dev Sync**：dev Telegram/飞书事件都进入 `sync-dispatch-dev`，再由 `.github/workflows/sync-dev.yml` 按渠道同步并触发 dev Pages 部署。
6. **Deploy Cloudflare Worker**：Worker 或 Wrangler 配置变更后部署生产 Telegram Worker；生产飞书 Worker 通过独立手动 workflow 部署，dev 统一 Worker 通过 `deploy-cloudflare-worker-dev.yml` 部署。
7. **共享 site-build action**：统一 Node setup、Hexo `db.json` cache、可选依赖安装、安全 `sync:db`、测试、构建和 Pages deploy 步骤。
