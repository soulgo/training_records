# 内部接口手册

本文档记录当前训练记录系统中适合被内部复用、自动化调用或后续开放的稳定接口。内容以当前仓库实现为准，不承诺语义化版本兼容；如果代码行为发生变化，应同步更新本文档。

## 1. 接口分级与约定

### 1.1 稳定性标记

| 标记 | 含义 | 调用建议 |
| --- | --- | --- |
| `可对外` | 适合被外部自动化、Webhook 或后续开放服务调用 | 可作为集成入口，调用方仍需按本文档处理失败 |
| `内部稳定` | 仓库内跨模块复用的主要接口 | 可被工具脚本、测试和内部模块依赖 |
| `内部实现` | 为当前实现服务的细分函数、运行时文件或持久化细节 | 不建议外部直接依赖，变更成本较低 |

### 1.2 通用约定

- Node.js 代码使用 ESM，导入路径以仓库根目录为基准。新架构模块路径：核心域 `src/core/`、应用层 `src/app/use-cases/`、适配器 `src/adapters/`、基础设施 `src/infra/`。兼容层 `src/db/training/` 和 `tools/` 保持向后兼容。
- 日期字段优先使用 `YYYY-MM-DD`；Telegram 原始时间使用 Unix 秒；飞书原始消息时间可能是毫秒字符串；生成时间和数据库更新时间使用 ISO 字符串或 PostgreSQL `timestamptz`。
- 训练数据的 canonical 结构是 `TrainingSnapshot`；线上事实源是 PostgreSQL `core.*`。Markdown、Telegram/飞书识别结果最终都应归一到该结构或其日级子结构，但 Markdown 只作为备份或显式兼容输入。
- 数据库开关由 `TRAINING_DB_ENABLED` 和 `TRAINING_DB_URL` 控制。未启用或缺少 URL 时，多数数据库读写接口返回空快照或 `skipped`，不会自动创建数据库。
- 文档中的示例不包含真实 token、真实数据库 URL 或真实 Chat ID。

## 2. CLI / npm scripts

### 2.1 数据生成与站点构建

| 命令 | 稳定性 | 实现入口 | 作用 | 主要输入 | 主要输出 |
| --- | --- | --- | --- | --- | --- |
| `npm run build:data` | `可对外` | `src/app/use-cases/generate-training-data.use-case.mjs` | 从 Markdown 或数据库构建训练快照和看板数据 | `训练记录.md`、`TRAINING_SNAPSHOT_SOURCE`、数据库环境变量 | `source/_data/training.json`、`source/_data/dashboardView.json`、`训练数据解析.md` |
| `npm run build:site` | `可对外` | `tools/run-hexo-command.mjs generate` | 调用 Hexo 生成静态站点 | `source/`、`themes/`、`source/_data/` | `public/` |
| `npm run build` | `可对外` | `package.json` | 先生成数据，再生成站点 | 同上 | `source/_data/*`、`训练数据解析.md`、`public/` |
| `npm run server` | `内部稳定` | `tools/run-hexo-command.mjs server` | 生成数据并启动 Hexo 本地服务 | 同 `build:data` | 本地 Hexo server |
| `npm run clean` | `内部稳定` | `tools/run-hexo-command.mjs clean` | 调用 Hexo clean | 无特殊输入 | 清理 Hexo 生成产物 |

`build:data` 的数据源选择：

- 未设置 `TRAINING_SNAPSHOT_SOURCE` 时，本地兼容默认读取 `训练记录.md`；线上推荐设置为 `database`。
- 设置 `TRAINING_SNAPSHOT_SOURCE=database` 时读取 PostgreSQL `core.*`。
- 如果数据库源不可用或缺少可渲染数据，并且数据库配置存在，`generateTrainingData` 仅在非严格模式下回退到 Markdown 并向 `stderr` 写提示；DB-only 部署会启用严格模式。
- 每次生成数据后会尝试写入 `archive.*` 归档；归档失败时不会中断主输出，会写入 `runtime/training-db-sync.ndjson`。

### 2.3 Markdown 与数据库互导

| 命令 | 稳定性 | 实现入口 | 作用 | 主要输入 | 主要输出 |
| --- | --- | --- | --- | --- | --- |
| `npm run import:markdown` | `内部稳定` | `tools/import-training-markdown.mjs` | 解析 `训练记录.md` 并覆盖写入 `core.*` | Markdown、数据库环境变量 | `{ status, days }` 或 `skipped` |
| `npm run reconcile:markdown` | `内部稳定` | `tools/reconcile-training-markdown-to-core.mjs` | 显式人工维护时把 Markdown 回写 `core.*`；失败时返回 `deferred` | Markdown、数据库环境变量 | JSON 结果 |
| `npm run export:markdown` | `内部稳定` | `tools/export-training-markdown.mjs` | 从数据库快照派生 `训练记录.md` 和随想 Markdown 备份 | PostgreSQL `core.*` | 覆盖 `训练记录.md` 和 `source/_posts/*-telegram-thought-*.md` |

注意：

- `import:markdown` / `reconcile:markdown` 以 Markdown 解析结果为准，会按日期重写 `core.training_day`、`core.measurement`、`core.activity`、`core.meal`、`core.sleep`。
- `sync:db` 默认只跑安全同步；只有 `--phase markdown` 或 `--phase all` 才会执行 Markdown 对账入库。
- 整日替换语义只用于 Markdown 导入、archive 回填和手工对账：按目标日期删除 measurement/activity/meal/sleep 子表，再 upsert `core.training_day` 并批量插入子表。
- Telegram 普通图片成功路径使用增量 upsert：只写本批次包含的 `core.measurement`、`core.activity`、`core.meal`、`core.sleep`，并刷新当前 `core.training_day` 汇总，不删除同日其它模块。
- archive 回填和 Markdown 对账都有快速跳过路径；无缺失日期或 Markdown 与 core 等价时返回 `unchanged`。
- `export:markdown` 严格从数据库导出；数据库快照不可用或不完整时失败，不回退旧 Markdown。

## 3. HTTP Webhook

### 3.1 Cloudflare Worker Telegram Webhook

| 项 | 内容 |
| --- | --- |
| 稳定性 | `可对外` |
| 实现入口 | `cloudflare/telegram-sync-dispatch-worker.mjs` |
| 部署入口 | `wrangler.toml` 的 `main = "cloudflare/telegram-sync-dispatch-worker.mjs"` |
| 方法 | `POST` |
| 请求体 | Telegram Bot API Update JSON |
| 必填 Header | `X-Telegram-Bot-Api-Secret-Token: <TELEGRAM_SECRET_TOKEN>` |
| 成功响应 | `202` JSON；帮助消息为 `200` JSON |

Worker 不直接识别图片或写训练数据。它会先校验 Telegram secret；帮助消息会直接调用 Telegram `sendMessage` 回发命令清单，其它 update 会转发为 GitHub `repository_dispatch`，由 GitHub Actions 执行 `npm run sync:telegram`。如果缺少 `GITHUB_TOKEN` 或 GitHub dispatch 失败，Worker 会尽量回复原 Telegram 消息，提示“GitHub Action 未能启动”。

GitHub dispatch 请求：

```json
{
  "event_type": "telegram_update",
  "client_payload": {
    "telegram_updates": [
      { "update_id": 123, "message": {} }
    ]
  }
}
```

Worker 环境变量：

| 变量 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `GITHUB_TOKEN` | 普通 dispatch 必填 | 无 | 调用 GitHub repository dispatch 的 token；帮助消息不依赖它 |
| `TELEGRAM_BOT_TOKEN` | 帮助消息必填 | 无 | Worker 直接回复 `/help`、`帮助`、`命令` 等消息 |
| `TELEGRAM_SECRET_TOKEN` | 是 | 无 | 与 Telegram webhook secret header 对比 |
| `GITHUB_OWNER` | 否 | `soulgo` | GitHub 仓库 owner |
| `GITHUB_REPO` | 否 | `training_records` | GitHub 仓库名 |
| `GITHUB_API_BASE_URL` | 否 | `https://api.github.com` | GitHub API base URL |
| `TELEGRAM_ALBUM_BUFFER` | 否 | 无 | Durable Object binding，用于图片 burst 聚合 |

响应约定：

| HTTP 状态 | 响应示例 | 触发条件 |
| --- | --- | --- |
| `202` | `{ "ok": true, "dispatched": true, "updateId": 123 }` | 单条 update 已 dispatch |
| `202` | `{ "ok": true, "buffered": true, "updateId": 123, "albumKey": "42:images" }` | 图片 update 已进入 Durable Object 缓冲 |
| `200` | `{ "ok": true, "handled": "help", "updateId": 123 }` | 帮助消息已直接回发 Telegram |
| `400` | `{ "ok": false, "error": "invalid_json" }` | 请求体不是合法 JSON |
| `401` | `{ "ok": false, "error": "unauthorized" }` | secret header 不匹配 |
| `405` | `{ "ok": false, "error": "method_not_allowed" }` | 非 `POST` 请求 |
| `500` | `{ "ok": false, "error": "missing_github_token" }` | 非帮助消息需要 dispatch，但 Worker 缺少 GitHub token |
| `502` | `{ "ok": false, "error": "github_dispatch_failed", "status": 500, "body": "..." }` | GitHub dispatch 失败 |

### 3.2 Telegram 相册聚合 Durable Object

| 项 | 内容 |
| --- | --- |
| 稳定性 | `内部稳定` |
| 实现类 | `TelegramAlbumBuffer` |
| Binding 名称 | `TELEGRAM_ALBUM_BUFFER` |
| 聚合键 | `${chat.id}:images` |
| 延迟 | 约 `3000ms` |

行为：

- 只处理 `POST`。
- 内部请求体为 `{ "update": <Telegram Update> }`。
- 相同 `update_id` 在同一缓冲批次内去重。
- 派发前按 `update_id` 升序排序。
- alarm 触发后统一发送 `client_payload.telegram_updates`，随后删除缓冲的 `updates`。
- 同一 chat 的连续图片会先进同一个短窗口；真正的相册和单图拆分由 `groupTelegramUpdates()` 根据 `media_group_id` 和消息内容完成。
- 如果未配置该 binding，Worker 会退回逐条 dispatch，相册不会聚合。

### 3.3 Cloudflare Worker Feishu Webhook

| 项 | 内容 |
| --- | --- |
| 稳定性 | `可对外` |
| 实现入口 | `cloudflare/feishu-sync-dispatch-worker.mjs` |
| 部署入口 | `wrangler.toml` / `wrangler.dev.toml` 的 `main = "cloudflare/sync-dispatch-worker.mjs"`，统一 Worker 内部调用 `handleFeishuWebhook()` |
| 方法 | `POST` |
| 请求体 | 飞书事件订阅 JSON；开启加密策略时为 `{"encrypt":"..."}` |
| 必填 Header | 明文事件需要 `X-Lark-Request-Timestamp`、`X-Lark-Request-Nonce`、`X-Lark-Signature`；加密事件不强制要求签名头 |
| 成功响应 | `202` JSON；`url_verification` 为 `200` challenge JSON |

Worker 不直接识别图片或写训练数据。它会使用 `FEISHU_ENCRYPT_KEY` 解密飞书加密回调或验证明文事件签名，使用 `FEISHU_VERIFICATION_TOKEN` 校验事件 token；图片事件进入 `FEISHU_IMAGE_BUFFER` 短窗口缓冲，其它 `im.message.receive_v1` 事件直接转发为 GitHub `repository_dispatch`，由 GitHub Actions 执行 `npm run sync:feishu`。

GitHub dispatch 请求：

```json
{
  "event_type": "feishu_update",
  "client_payload": {
    "feishu_updates": [
      { "header": {}, "event": {} }
    ]
  }
}
```

Worker 环境变量：

| 变量 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `GITHUB_TOKEN` | 是 | 无 | 调用 GitHub repository dispatch 的 token |
| `FEISHU_ENCRYPT_KEY` | 是 | 无 | 飞书事件订阅签名校验 |
| `FEISHU_VERIFICATION_TOKEN` | 是 | 无 | 飞书事件 token 校验 |
| `GITHUB_OWNER` | 否 | `soulgo` | GitHub 仓库 owner |
| `GITHUB_REPO` | 否 | `training_records` | GitHub 仓库名 |
| `GITHUB_DISPATCH_EVENT_TYPE_FEISHU` | 否 | `feishu_update` | 飞书 GitHub dispatch 事件类型；dev 为 `feishu_update_dev` |
| `FEISHU_IMAGE_BUFFER` | 否 | 无 | Durable Object binding，用于飞书图片 burst 聚合 |

响应约定：

| HTTP 状态 | 响应示例 | 触发条件 |
| --- | --- | --- |
| `202` | `{ "ok": true, "dispatched": true, "eventId": "evt_xxx" }` | 单条事件已 dispatch |
| `202` | `{ "ok": true, "buffered": true, "eventId": "evt_xxx", "bufferKey": "oc_xxx:images" }` | 图片事件已进入 Durable Object 缓冲 |
| `200` | `{ "challenge": "..." }` | 飞书 URL verification |
| `400` | `{ "ok": false, "error": "invalid_json" }` | 请求体不是合法 JSON |
| `401` | `{ "ok": false, "error": "unauthorized" }` | 签名校验失败 |
| `401` | `{ "ok": false, "error": "invalid_token" }` | 事件 token 不匹配 |
| `405` | `{ "ok": false, "error": "method_not_allowed" }` | 非 `POST` 请求 |
| `500` | `{ "ok": false, "error": "missing_github_token" }` | Worker 缺少 GitHub token |
| `502` | `{ "ok": false, "error": "github_dispatch_failed", "status": 500, "body": "..." }` | GitHub dispatch 失败 |

## 4. 消息通道命令接口

### 4.1 授权与分组

| 项 | 内容 |
| --- | --- |
| 稳定性 | `可对外` |
| 分组入口 | `groupTelegramUpdates(updates, options)` |
| 运行入口 | `runTelegramSync(options)` |
| 飞书分组入口 | `groupFeishuUpdates(events, options)`，内部复用 `groupTelegramUpdates` |
| 授权 | Telegram 仅处理 `TELEGRAM_ALLOWED_CHAT_IDS` 中的 chat；飞书仅处理 `FEISHU_ALLOWED_CHAT_IDS` 中的 chat |
| 命令注册 | `src/telegram/command-registry.mjs` |

Telegram 只处理 `message` 和 `edited_message`。飞书当前处理 `im.message.receive_v1` 中的 text/post/image。未授权 chat 会生成 `status: "ignored"`、`reason: "unauthorized chat"`，不会识别图片、写文件或写数据库。

普通图片消息会被归为 `kind: "image"`：

- 相册按 `media_group_id` 合并为一个 batch。
- 单张图片 batchId 为 `single-<message_id>`。
- 图片可以来自 `photo`，也可以来自 image 类型的 `document`。

### 4.2 图片识别批次

| 项 | 内容 |
| --- | --- |
| 稳定性 | `可对外` |
| 输入 | Telegram 图片消息/相册，或飞书 image 事件 |
| AI schema | `buildRecognitionSchema()` |
| 归档目标 | PostgreSQL `ingest.*` + `core.*` 增量写入；失败时进入 pending replay，不写 `训练记录.md` 兜底 |
| 识别服务 | `src/ai/recognition-service.mjs` |
| Prompt metadata | `prompts/*.md` 顶部可含 `prompt-metadata` header，运行时会剥离后再发送给模型 |
| 识别缓存 | 默认关闭；开启后按 `file_unique_id + promptVersion + schemaVersion + model` 复用结果 |

批次分析结果主要字段：

```json
{
  "status": "ready",
  "kind": "image",
  "batchId": "single-123",
  "archivedDate": "2026-05-23",
  "measurement": {},
  "activities": [],
  "workoutDailySummary": null,
  "nutrition": { "meals": [], "totalCalories": null, "details": [] },
  "sleep": { "records": [], "totalSleepMinutes": null },
  "warnings": [],
  "issues": [],
  "confidence": 0.95
}
```

失败和跳过：

- 识别置信度低于 `0.75` 时记录 issue。
- 同一批次识别出多个不同截图日期时返回 `skipped`。
- 无可靠截图日期或文件名日期时返回 `skipped`。
- `ready + stored` 成功时以数据库为主事实源，只增量 upsert 本批次数据，不改写 `训练记录.md`。
- 数据库写入失败时，图片批次会追加到 `runtime/telegram-sync-pending.ndjson` 等待重放，不写 Markdown 兜底。
- cache key 形如 `telegram:file_unique_id:<file_unique_id>:prompt:<prompt_version>:schema:<schema_version>:model:<model>`，prompt/schema/model 任一变化都会自动 miss。飞书图片当前以内联下载方式进入识别链路，并保留 `sourceMessageId` 供审计。

### 4.3 随想命令

| 命令 | 稳定性 | 作用 | 说明 |
| --- | --- | --- | --- |
| `/thought <正文>` | `可对外` | 新增随想 | 默认模块 `workout` |
| `/随想 <正文>` | `可对外` | 新增随想 | `/thought` 中文别名 |

- 正文、模块、标签、Telegram message id 和删除状态写入 `core.thought`。

## 6. AI 接口契约

### 6.1 图片识别 JSON Schema

| 项 | 内容 |
| --- | --- |
| 稳定性 | `可对外` |
| 入口 | `buildRecognitionSchema()` |
| 使用位置 | `tools/telegram-sync.mjs` 调用 `${AI_BASE_URL}/chat/completions` |
| prompt | 默认 `prompts/telegram-training-image-recognition.md`，可用 `TELEGRAM_RECOGNITION_PROMPT_PATH` 覆盖 |

AI 返回内容必须是符合 schema 的 JSON 字符串。顶层字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `imageType` | `measurement \| workout \| nutrition \| sleep \| unknown` | 图片类型 |
| `detectedApp` | `string \| null` | 截图来源 APP；无法可靠识别时为 `null`，仅用于识别审计和后续适配 |
| `detectedDate` | `string \| null` | 截图画面内可靠日期，格式 `YYYY-MM-DD` |
| `dateEvidence` | `string` | 日期证据说明 |
| `records.measurement` | `object \| null` | 体脂测量 |
| `records.activities` | `Activity[]` | 活动明细 |
| `records.meals` | `Meal[]` | 餐次汇总 |
| `records.totalCalories` | `number \| null` | 当日总热量 |
| `records.details` | `string[]` | 餐次明细 |
| `records.dailyWorkoutSummary` | `object \| null` | 当日活动总览 |
| `records.sleep` | `object \| null` | 睡眠明细 |
| `confidence` | `number` | 识别置信度 |
| `warnings` | `string[]` | 风险提示 |

调用注意：

- `detectedDate` 只能来自截图画面内日期；caption、普通文本或文件名不应伪装为截图日期。
- 系统相册、文件详情、分享预览页里可见的文件名/标题/路径日期，以及活动总览顶部的大号日期，都属于截图画面内日期。
- Telegram 消息年份只允许用于补全截图里可见的月日，不能单独产生 `detectedDate`。
- `dateEvidence` 如果只说明来自 filename/caption/text，运行时不会把它作为截图日期。
- `sleep` 图片的日期会按 `wakeTime` 或 `detectedDate` 代表的醒来日期减一天归档；AI 不输出归档日期。
- 识别请求遇到 HTTP `429`、`500`、`502`、`503`、`504` 会最多尝试 3 次。

### 7.2 Telegram 同步

#### `runTelegramSync(options = {})`

| 项 | 内容 |
| --- | --- |

| 文件 | `tools/telegram-sync.mjs` |
| 返回 | `Promise<TelegramSyncResult>` |

主要可注入依赖：

- `env`
- `rootDir`
- `now`
- `fetchTelegramUpdates`
- `recognizeBatch`

- `exportTrainingMarkdown`
- `writeThoughtPost`
- `fetchTelegramFile`

返回结构：

```json
{
  "changed": true,
  "fallbackUsed": false,
  "updatesFetched": 1,
  "lastProcessedUpdateId": 123,
  "readyBatches": 1,
```

### 8.2 `core.*`

| 表 | 稳定性 | 主键 | 职责 |
| --- | --- | --- | --- |
| `core.training_day` | `可对外` | `archived_date` | 每日训练、饮食、活动汇总 |
| `core.measurement` | `可对外` | `measurement_key` | 体脂秤测量明细 |
| `core.activity` | `可对外` | `activity_key` | 运动活动明细 |
| `core.meal` | `可对外` | `meal_key` | 餐次热量明细 |
| `core.sleep` | `可对外` | `sleep_key` | 睡眠明细和健康指标 |
| `core.thought` | `可对外` | `telegram_message_id` | 消息通道随想正文、模块、图片引用和删除状态镜像；字段名保留 Telegram 历史兼容 |

写入约定：

- `core.training_day` 是父表，`measurement`、`activity`、`meal`、`sleep` 通过 `archived_date` 外键关联，删除训练日会级联删除明细。
- Telegram/飞书图片批次更新某一天时，会先确保 `core.training_day` stub 存在，再 upsert 本批次包含的 measurement、activities、nutrition 或 sleep 明细，并从子表刷新当天汇总，`source_channel` 标记真实来源。
- `nutrition_details_json` 只在本批次包含 `nutrition.details` 时更新；否则保留该日期既有明细。
- Markdown 导入会按日期替换 `core.training_day`、`core.measurement`、`core.activity`、`core.meal`、`core.sleep`。
- `core.thought` 独立于训练日表，以 `telegram_message_id` 定位；Telegram 使用原始 message id，飞书使用稳定数字代理 ID。删除为软删除。

### 8.3 `ingest.*`

| 表 | 稳定性 | 主键 | 职责 |
| --- | --- | --- | --- |
| `ingest.telegram_batch` | `内部稳定` | `batch_id` | 消息通道批次分析结果、状态、hash 和完整 payload；飞书本轮复用该表 |
| `ingest.telegram_message` | `内部稳定` | `message_id` | 消息通道原始消息摘要和图片 file id；飞书使用稳定数字代理 message id |
| `ingest.telegram_recognition` | `内部稳定` | `message_id` | AI 图片识别原始 JSON |

写入约定：

- `persistNormalizedBatch` 以 batch JSON 的 SHA-256 作为 `payload_hash`。
- 已存在且 hash 相同的 batch 返回 `unchanged`。
- 写入过程包在事务中，core 写入失败时会执行 `ROLLBACK`，不会提交半批次。
- `telegram_message` 和 `telegram_recognition` 通过 `batch_id` 级联关联 batch。
- `getLastProcessedTelegramUpdateId` 读取 `telegram_message.update_id` 最大值，作为轮询 offset 的依据。
- 同一 `batch_id + payload_hash` 再次写入时返回 `unchanged`，不会重复刷新 core 或 archive。

### 8.4 `archive.*`

| 表 | 稳定性 | 主键 | 职责 |
| --- | --- | --- | --- |
| `archive.training_parse_snapshot` | `内部稳定` | `source_hash` | Markdown 原文 hash 去重后的完整解析快照 |
| `archive.training_parse_run` | `内部稳定` | `run_id` | 每次数据生成的运行留痕 |
| `archive.training_day` | `内部稳定` | `archived_date` | 归档日汇总 |
| `archive.training_measurement` | `内部稳定` | `measurement_hash` | 归档体脂明细 |
| `archive.training_activity` | `内部稳定` | `activity_hash` | 归档运动明细 |
| `archive.training_meal` | `内部稳定` | `meal_hash` | 归档餐次明细 |
| `archive.training_sleep` | `内部稳定` | `sleep_hash` | 归档睡眠明细和健康指标 |

归档失败不影响 `build:data` 的主输出；失败信息会追加到 `runtime/training-db-sync.ndjson`。

## 11. 常见失败模式

| 场景 | 表现 | 处理 |
| --- | --- | --- |
| Telegram secret 不匹配 | Worker 返回 `401 unauthorized` | 检查 Telegram webhook secret 与 Cloudflare `TELEGRAM_SECRET_TOKEN` |
| Worker 缺少 GitHub token | Worker 返回 `500 missing_github_token` | 配置 Cloudflare secret `GITHUB_TOKEN` |
| 帮助消息回复失败 | Worker 返回 `502 telegram_help_failed` | 检查 Cloudflare secret `TELEGRAM_BOT_TOKEN` 和 Telegram API 状态 |
| GitHub dispatch 失败 | Worker 返回 `502 github_dispatch_failed` | 检查 token 权限、仓库 owner/repo、GitHub API 状态 |
| GitHub Action 阶段失败 | Telegram 回复 `GitHub Action 执行失败：<阶段>` | 打开回复中的 run URL 查看失败步骤 |
| 飞书签名或 token 不匹配 | Feishu Worker 返回 `401 unauthorized` 或 `401 invalid_token` | 检查 `FEISHU_ENCRYPT_KEY`、`FEISHU_VERIFICATION_TOKEN` 是否与飞书开放平台一致 |
| 飞书 dispatch 未触发 | Worker 返回 `missing_github_token` 或 GitHub 没有 `feishu_update` / `feishu_update_dev` run | 检查 Worker `GITHUB_TOKEN`、`GITHUB_OWNER`、`GITHUB_REPO`、`GITHUB_DISPATCH_EVENT_TYPE_FEISHU` |
| AI 识别失败 | `sync:telegram` / `sync:feishu` stderr 出现 image recognition failed | 检查 `AI_*`、图片 URL或飞书资源下载、模型 schema 支持 |
| 图片无可靠日期 | batch `status: "skipped"` | Telegram 可用 document 方式发送带日期文件名的图片；飞书需要保证截图画面有日期 |
| Markdown 附件随想失败 | batch `thoughtWriteStatus: "failed"`，`failureReason` 包含 empty/too large/download | 确认附件是 `.md` / `.markdown`，非空、UTF-8 可读且不超过 5MB；下载失败时检查 Telegram API |
| 数据库未启用 | DB 接口返回 `skipped: disabled` 或空快照 | 设置 `TRAINING_DB_ENABLED=true` 并配置 `TRAINING_DB_URL` |
| 数据库暂时不可用 | 批次 `persistenceStatus: pending_replay` | 等数据库恢复后再次运行 `sync:telegram` 或 `sync:feishu` 重放队列 |
| 随想数据库写入失败 | Telegram/飞书回复“已记录，数据库待补偿” | 修复数据库后重放 pending；正文以 `core.thought` 为准 |
| 数据库快照不可渲染 | 抛出 `database snapshot is empty or missing measurements` | 检查 `core.*` 是否已有训练日和体脂数据；不要用旧 Markdown 覆盖数据库 |
| `/analysis` 无法生成 | Telegram/飞书回发失败原因 | 检查 `AI_*`、`TRAINING_SNAPSHOT_SOURCE` 和数据库/Markdown 数据 |
